# Back-end Prism

Complementa o [guia da raiz](../../AGENTS.md). Solução `Prism.slnx`, quatro projetos `net10.0` no padrão zanveri (`Prism.Api`, `Prism.Application`, `Prism.Infrastructure`, `Prism.Core`) e três de teste em `tests/`. A base veio do etio; leia as skills `back-end-*` antes de editar.

## Comandos

```bash
dotnet build src/api/Prism.slnx            # zero avisos
dotnet test src/api/Prism.slnx
dotnet restore src/api/Prism.slnx --force-evaluate   # depois de mudar um PackageReference; os packages.lock.json entram no mesmo commit
```

A API não tem valores padrão. Para rodá-la à mão são obrigatórias `PRISM_API_TOKEN`, `PRISM_DATA_DIR` e `PRISM_ALLOWED_ORIGIN`; `PRISM_PARENT_PID` é opcional (a API encerra quando esse processo deixa de existir). Pronta, ela escreve `PRISM_API_READY <porta>` na saída padrão, que é a única coisa que vai ao console; o log fica em `<PRISM_DATA_DIR>/logs/prism-.log`. Ao iniciar, antes da linha de pronto, ele recebe a versão da API (RN-VERSAO-004): `A API do Prism iniciou na versão <versão>.`, lida do `AssemblyInformationalVersionAttribute` do assembly de entrada, que o `dotnet publish -p:Version=` preenche (fora de uma publicação vale o padrão do SDK, `1.0.0+<commit>`). Só a versão, sem caminho de máquina, token nem nome de usuário; o `ProcessHostingTests` confere. Quem chama usa `http://127.0.0.1:<porta>` com `Authorization: Bearer <token>`: o filtro de host recusa `localhost`.

O restore usa só o nuget.org (RN-ABERTO-002): o `nuget.config` limpa as fontes da máquina e amarra todo pacote a ele, e não há credencial a configurar. Pacote que só existe fora do nuget.org não entra; se um dia entrar, o mapeamento de fontes do `nuget.config` é o lugar de amarrá-lo à fonte dele.

**Identificadores de runtime e lock files** (RN-ABERTO-006). O `Directory.Build.props` declara os quatro para os quais a API é publicada (`win-x64`, `linux-x64`, `osx-x64`, `osx-arm64`), e o `packages.lock.json` de cada projeto traz os quatro alvos: `dotnet publish -r <id>` restaura sem mexer neles, e pode levar `-p:RestoreLockedMode=true`. O `dotnet restore -r <id>` manda o identificador na propriedade `RuntimeIdentifiers`, no plural, que trocaria a lista inteira: o `TreatAsLocalProperty` do `Directory.Build.props` faz valer a lista de lá, e o identificador pedido fica em `PrismRuntimeIdentifier`.

**Driver da IBM: só para compilar.** O `Prism.Infrastructure.csproj` referencia sempre os três pacotes (`Net.IBM.Data.Db2` para `win-x64`, `-lnx` para `linux-x64`, `-osx` para `osx-arm64`; o de macOS só existe para arm64), todos com `PrivateAssets="all"`: o da plataforma entra só na compilação (`IncludeAssets="compile"`), e os outros dois ficam de fora (`ExcludeAssets="all"`). **Nenhum arquivo do pacote vai para a saída de build nem para a publicação** (RN-DRIVER-001 e RN-ABERTO-001): nem o `IBM.Data.Db2.dll`, nem a pasta nativa `clidriver` (cerca de 120 MB), nem o `TestConn` de `tools/`, nem as licenças. Quem baixa o driver é o usuário, pela tela de Drivers, e a API o carrega de `<PRISM_DATA_DIR>/drivers` (ver "Drivers sob demanda"). Com o `PrivateAssets` o pacote só aparece no lock file da Infrastructure, e nenhum outro projeto compila contra um tipo da IBM. Uma referência condicionada ao identificador mudaria as dependências do projeto a cada plataforma, e um lock file só não serviria às quatro. Quem escolhe o pacote é o identificador pedido; sem pedido (`dotnet build` e `dotnet test` de quem desenvolve), o da máquina. Onde não há pacote (`osx-x64`), a constante `PRISM_IBM_DRIVER` não existe: os arquivos do Db2 e do Informix e o registro dos dois clients ficam de fora (`#if`), e abrir ou testar uma conexão desses bancos responde 422 `DATABASE_CONNECTION_FAILED` com "O Prism para osx-x64 ainda não conecta em Db2 e Informix: a IBM não publica o driver para ela." Para compilar e testar assim em qualquer máquina: `-p:IbmDriverRuntime=osx-x64`. `Api/PublishTests` publica a API para as quatro plataformas e confere que a pasta não tem arquivo nenhum da IBM. **Uma saída de build antiga (`bin/`) pode ainda ter a `clidriver` e o assembly de antes desta mudança**: o build não apaga o que deixou de copiar. Apague `bin/` e `obj/` uma vez; o teste `Driver_IsLoadedFromTheFolderTheDriverManagerInstalledItIn` acusa a sobra.

## O mediador (`Prism.Core/Mediator`)

É do próprio Prism, e não um pacote (decisão 8 da raiz): `IRequest<T>`, `IRequestHandler<,>`, `IMediator` e `AddMediator(assembly)`, que registra por varredura do assembly todo handler (também os `internal`) e todo `IValidator<T>`. Sem notificações e sem pipeline configurável; o que o Prism não usa não existe.

- **Validação e depois handler.** `Send` roda todos os validators do tipo do command; havendo falha, lança uma `FluentValidation.ValidationException` com as falhas de todos, cada uma uma vez, e o handler não roda. A exceção é a que o `GlobalValidationExceptionFilter` traduz em 422, e o mediador não a registra no log.
- **Tudo `Scoped`**: o mediador, os handlers e os validators. O handler é resolvido no escopo de quem pediu o `IMediator`, o da requisição, e pode depender de serviço `Scoped`; pedir o `IMediator` da raiz do contêiner falha. O mediador precisa de `ILogger<>` registrado (o host sempre tem).
- **Command sem handler** lança `InvalidOperationException` dizendo qual.
- **Handler que lança** (RN-LOG-001): o mediador registra no `Error` o nome do tipo do command e a exceção, e a relança igual. O command nunca vai ao log, porque leva senha e SQL: nada de `{@request}` nem `ToString()` ali. O `OperationCanceledException` sobe sem registro.

## A porta de entrada (`Prism.Api`)

A ordem do pipeline está em `UseApi` (`DependencyInjection.cs`): exceção não tratada (500 `INTERNAL_SERVER_ERROR` fixo, exceção inteira no log) → filtro de host → roteamento → CORS → `LaunchTokenMiddleware` → `VaultGateMiddleware` → endpoints. O CORS vem antes do token porque o preflight do navegador não leva token. Controllers novos entram em `Prism.Api/Controllers/`; o application part de `AddApi` os acha mesmo no `ApiHost` dos testes.

JSON: o padrão do MVC (camelCase) escreve `ID` como `id` e `FolderID` como `folderID`. Não há configuração a copiar do etio, e as telas dependem dessa grafia.

`HostErrors` guarda os erros da porta de entrada e a escrita deles (`application/problem+json`). `VaultLocked()` é a escrita do `VaultErrors.From(Locked)` (Application), a mesma que um handler devolve quando o cofre fecha no meio da operação.

## Usuários, entrada e barreira do cofre

- `VaultGateMiddleware` (RN-API-005) responde 401 `VAULT_LOCKED` a todo caminho sob `/api/user` com o cofre fechado, sem diferenciar maiúsculas (o roteamento também não diferencia). Fica depois do token: sem token a resposta é `AUTHENTICATION_REQUIRED`. Uma rota nova de dados do usuário só precisa começar por `api/user/`.
- Os controllers de `api/public/...` não levam `[AllowAnonymous]`: não há autenticação do ASP.NET, e a porta é o `LaunchTokenMiddleware`.
- `VaultErrors.From(EVaultError)` (Application) é a única tradução das recusas do serviço do cofre para o erro da API. Todo handler que fala com o cofre a usa.
- Criar usuário valida tudo no validator (422 `USERNAME_INVALID`, `PASSWORD_INVALID`, com `errors.UserName` e `errors.Password`; a tela põe a primeira letra em minúscula). Entrar **nunca** responde 422: só normaliza o nome (`Trim().ToLowerInvariant()`) e entrega ao cofre, que responde 401 `INVALID_CREDENTIALS` com a derivação de uma senha errada (RN-COFRE-006) para nome de dispositivo do Windows, com caminho, vazio ou ausente. A única outra recusa da entrada é 409 `VAULT_FORMAT_UNSUPPORTED`, para o cofre de formato mais novo (RN-VERSAO-005, ver "O cofre").
- A checagem de nome de arquivo do cofre é uma só, `VaultFileName.IsAllowed` (Infrastructure, pública): o `VaultFileClient` a aplica antes do disco e o `UserNameRules` (Application) a reaproveita. Nomes de dispositivo (`con`, `prn`, `aux`, `nul`, `com1`-`com9`, `lpt1`-`lpt9`, com ou sem extensão) são recusados nela.
- `null` explícito num campo do corpo (`{ "userName": null }`) não chega ao validator: o MVC o recusa antes, com 400 do `[ApiController]` (campo omitido vale vazio e segue o fluxo normal). A tela só manda texto.
- A senha do usuário tem uma regra só, `UserPasswordRules.MustBeAValidPassword` (RN-COFRE-010: 8 a 128 caracteres, contados em unidades UTF-16 como o campo de texto conta, sem regra de composição; 422 `PASSWORD_INVALID`), aplicada pelo `CreateUserValidator` (campo `Password`) e pelo `ChangePasswordValidator` (campo `NewPassword`, RN-COFRE-013): a senha nova da troca segue EXATAMENTE a da criação de conta, e o `ChangePasswordValidatorTests` compara os dois validators caso a caso. A senha atual da troca não é validada. A rota é `PUT api/user/password` (`UserPasswordController`, 204 sem corpo); o que ela faz no cofre, e os três códigos de recusa (`INVALID_PASSWORD`, `PASSWORD_INVALID`, `PASSWORD_UNCHANGED`), estão em "O cofre". **O corpo tem teto de 16 KiB** (`[RequestSizeLimit]`: duas senhas de até 128 caracteres cabem com folga), e a requisição que o passa é recusada antes de o handler rodar, sem derivar nada. **O status que sai hoje é 500 `INTERNAL_SERVER_ERROR`, e não 413**: o `UseExceptionHandler` troca o `BadHttpRequestException` do Kestrel pelo 500 fixo, em TODA rota que lê um corpo (defeito anterior à troca de senha, à espera da leva final); o teste afirma que a requisição não foi lida como uma troca (nem 204 nem 422), e não o 500. As recusas de negócio que a tela mostra no campo (`errors` e `errorCodes` por campo) vêm de `ApiErrorDto.CreateUnprocessableEntityOnField`, que a senha da conexão (RN-CONN-004) e a troca de senha usam.

## O cofre (`Prism.Infrastructure/Vault`)

É a primeira integração e o modelo das próximas: `Models/`, `Clients/` (o `VaultFileClient`, com o único `try` no `Send`, e o `VaultCrypto` estático que ele usa) e `Services/`. A Application fala só com o `IVaultService`: `Read()` devolve o documento do cofre aberto, `SaveAsync(documento => documento with { ... })` grava, e a falha é um `EVaultError`, que a Application traduz para o erro da API.

- `IVaultService` é `Singleton` e descartável: guarda a chave e o documento do cofre aberto, e o descarte do host o fecha (RN-COFRE-008). Os demais services continuam `Transient`.
- O client é síncrono: o arquivo tem poucos KB e a cifra é em memória. A abertura da cifra passa por ele (`IVaultFileClient.Open`), e não direto pelo `VaultCrypto`, porque o `AesGcm` só recusa por exceção e senha errada é resposta esperada.
- O serviço libera o semáforo com `using`, sem `try`/`finally`, e dispara `Locked` depois de liberar. A função entregue ao `SaveAsync` não chama o serviço de volta.
- O log do client nunca recebe a exceção: a mensagem de uma `IOException` traz o caminho do arquivo, que tem o nome do usuário. Vão a classe do erro, o `HResult` e um pseudônimo do usuário.
- Arquivo ilegível ou adulterado responde `InvalidCredentials`, como senha errada; `Unavailable` é só falha de disco. A única exceção ao 401 único é o formato mais novo (abaixo): ele não está ilegível.
- Cofre que uma queda deixou só no `.bak` volta a ser o arquivo principal na leitura seguinte (RN-COFRE-005), inclusive na conferência de existência do `CreateAsync`. Um `.tmp` ao lado é ignorado, e a gravação seguinte o trunca. A exceção é o `.bak` de formato mais novo (abaixo): esse não é promovido.
- **Formato mais novo** (RN-VERSAO-005). O `VaultFileClient.Read` lê o número do formato do cabeçalho antes de tudo, inclusive antes de promover o `.bak`, e um número maior que `VaultCrypto.Version` volta como `EVaultFileError.NewerFormat`; o `VaultService.Unlock` o traduz em `EVaultError.FormatUnsupported` antes de qualquer derivação de chave, então a resposta é a mesma com a senha certa e com a errada (a recusa vem antes de a senha ser olhada), e a API responde 409 `VAULT_FORMAT_UNSUPPORTED` (`VaultErrors.From`; as rotas `api/user/...` nunca o veem, porque o cofre já está aberto, mas o mapeamento existe e o teste que percorre todos os valores do `EVaultError` o cobre). Só o campo `version` é lido para essa decisão (`VaultHeader`, um `JsonElement`, sem diferenciar maiúsculas), e não o `VaultFile`: um formato futuro pode ter outra forma, e uma leitura completa o recusaria como corrompido. Formato 0, negativo, texto, decimal, nulo, ausente ou grande demais para um `long` é cofre corrompido (401); o mais novo NÃO é "ilegível". Nada é aberto, promovido nem regravado: o principal manda (principal mais novo com `.bak` atual é 409 e nada se toca), e sem o principal um `.bak` mais novo fica onde está. Criar usuário por cima continua `UserAlreadyExists`, sem tocar no arquivo (o `Create` trata toda falha de leitura, menos disco, como "já existe"). Consequência aceita: um `.bak` que nem é JSON deixou de ser promovido a principal (dava no mesmo 401 antes e depois).
- **Formato 2 e a migração do formato 1** (RN-VERSAO-005, RN-SCRIPT-002). O formato 2 acrescentou os scripts ao documento (`VaultDocument.Scripts`); o 1 (`VaultCrypto.OldestVersion`) ainda se lê. O `IsWellFormed` do client aceita os dois na leitura (o principal e o `.bak`), e o `Write` só grava o atual (o anterior volta `Corrupt`, sem tocar o disco). A leitura confere ainda que o número da leitura completa é o mesmo do cabeçalho (`ReadFormat`, que só aceita número JSON): a leitura do `JsonSerializerDefaults.Web` aceita número em texto, e `"2"` passaria por um cofre do formato 2. **A migração é no `VaultService.Unlock`**, depois de a senha conferir e o documento abrir: o documento passa pelo `VaultMigration.Upgrade` (do 1 para o 2, a lista de scripts, que o JSON antigo não tem e a leitura entrega nula, vira vazia) e o arquivo é regravado no formato 2 com a MESMA senha, o MESMO sal e os MESMOS parâmetros, e a mesma chave do cofre embrulhada de novo, com o conteúdo cifrado de novo (o número do formato é parte do dado autenticado das duas cifras); por isso a chave derivada da senha fica viva até o fim da entrada (e é zerada em todos os caminhos), em vez de sair do `OpenKey`. A gravação é a de sempre, e o arquivo de antes fica no `.bak`, byte a byte. **A falha do disco na migração não impede a entrada** (a entrada não precisa gravar): o cofre abre com o arquivo migrado na memória, a primeira gravação seguinte o escreve inteiro no formato 2 (com o do formato 1 no `.bak`), e sem gravação no meio a entrada seguinte migra de novo; o aviso (`Warning`) leva os dois números e a classe da falha, sem senha, usuário nem exceção. **A cura do `.bak` não roda na entrada que migrou** (o `.bak` acabou de virar o arquivo de antes) e **não troca um `.bak` de formato anterior com o mesmo sal** (`HasTheSameWrapping`): é o arquivo de antes da migração, da mesma senha (a troca de senha sempre sorteia outro sal), e sem essa exceção a entrada seguinte o apagaria. O `VaultFormatOneSampleTests` abre `tests/Prism.UnitTesting/Vault/Samples/vault-format-1.json`, um cofre do formato 1 gravado antes da regra (gerado pelo próprio código, com Argon2id de 8 MiB e uma passada), e prova a migração, a entrada seguinte sem regravar, a falha do disco e a troca de senha depois dela; o `ScriptsTests` (integração) o embute também (`EmbeddedResource` que aponta para o mesmo arquivo) e o abre pela rota de entrada. A senha dele é a constante fictícia do teste, de um cofre de exemplo com dados inventados: sem ela o arquivo não serve de prova. O arquivo não se regera; regerá-lo apaga a prova de que o formato antigo continua abrindo. O que segue vale do mesmo jeito para os formatos 3 e 4 (abaixo); o 4 é o atual.
- **Formato 3 e a migração do formato 2** (RN-VERSAO-005, RN-ABAS-006). O formato 3 (o atual até a seção 33) acrescentou a área de trabalho ao documento (`VaultDocument.Workspace`, um `VaultWorkspaceRecord`: as abas gravadas, `VaultWorkspaceTabRecord`, e o índice da ativa). O `VaultMigration.Upgrade` faz os passos que faltam, em ordem: do 1 para o 2, a lista de scripts vazia; do 2 para o 3, a área de trabalho vazia (`VaultWorkspaceRecord.Empty`: nada volta na entrada seguinte); um cofre do formato 1 passa pelos dois. O `IsWellFormed` aceitava do 1 ao 3 e o `Write` só gravava o 3. O `VaultFormatTwoSampleTests` abre `Vault/Samples/vault-format-2.json`, um cofre do formato 2 gravado pelo código do formato 2 antes desta mudança (usuário `exemplo.formato2`, a MESMA senha fictícia do exemplo do formato 1, uma pasta, uma conexão e um script inventados), e prova a migração (os scripts ficam, a área de trabalho vem vazia, o `.bak` é o arquivo de antes), a entrada seguinte sem regravar e a primeira área de trabalho gravada depois; o `WorkspaceTests` (integração) o embute também e o abre pela rota de entrada. Não se regera.
- **Formato 4 e a migração do formato 3** (RN-VERSAO-005, RN-SCRIPT-011). O formato atual é o 4 (`VaultCrypto.Version`), que acrescentou as pastas de scripts ao documento (`VaultDocument.ScriptFolders`, uma lista de `VaultScriptFolderRecord`: id, pasta pai, nome e datas; no FIM do record do documento, para as construções de antes só ganharem a lista nova) e a pasta ao registro do script (`VaultScriptRecord.FolderID`, no fim, nula na raiz). O `VaultMigration.Upgrade` ganhou o passo do 3 para o 4 (a lista de pastas de scripts vazia; o `FolderID` que o JSON de antes não tem já chega nulo, e todo script fica na raiz), e o cofre do 1 e do 2 passa por todos, em ordem. O `IsWellFormed` aceita do 1 ao 4 e o `Write` só grava o 4. O `VaultFormatThreeSampleTests` abre `Vault/Samples/vault-format-3.json`, um cofre do formato 3 gravado pelo código do formato 3 antes desta mudança (usuário `exemplo.formato3`, a MESMA senha fictícia dos outros exemplos, e o que o formato 3 tinha: a pasta com ambiente, cor e confirmação, a conexão somente leitura com a verificação própria, um script com ícone e cor e um genérico, e a área de trabalho com duas abas), e prova a migração (o documento inteiro igual, as pastas de scripts vazias, os scripts na raiz, o `.bak` é o arquivo de antes), a entrada seguinte sem regravar e a primeira pasta de scripts gravada depois, com um script dentro; o `ScriptFoldersTests` (integração) o embute também e o abre pela rota de entrada. Não se regera. Os testes das amostras do 1 e do 2 fixam `VaultCrypto.Version` em 4, e o documento esperado deles tem a lista vazia; os de unidade que fingem um formato mais novo usam `VaultCrypto.Version + 1`, e os de integração (`UsersAndSessionsTests`, que não enxergam o `VaultCrypto`), o `5`. **Um formato 5** sobe o `Version`, acrescenta o passo no `VaultMigration.Upgrade`, um exemplo do formato 4 em `Vault/Samples` (gravado pelo código antes da mudança, por um teste de uma vez só que não se versiona) e muda o `5` desses testes de integração.
- **Campo opcional novo, sem subir o formato** (RN-PASTA-005). O ambiente da pasta (`VaultFolderRecord.EnvironmentName` e `EnvironmentColor`) entrou no formato 2, sem migração: a leitura do documento (`JsonSerializer.Deserialize<VaultDocument>`, opções padrão) entrega nulo ao parâmetro do construtor que o JSON não tem, e nulo é "pasta sem ambiente", então o cofre gravado antes abre como está e a gravação seguinte escreve os dois campos. Os dois ficam no FIM do registro, com padrão nulo, para nenhuma construção existente mudar. O `VaultFolderEnvironmentTests` prova com um cofre do formato 2 montado à mão (o conteúdo com os cinco campos que o registro tinha, cifrado como o `CreateAsync` cifra): abre com a pasta sem ambiente, é regravado com ele e o devolve na entrada seguinte. Ele escreve o número 2 de propósito (e não `VaultCrypto.Version`): com o formato 3 ele passa a provar também a migração desse cofre. Consequência aceita: um app anterior a esta mudança que abra o cofre ignora os dois campos (a leitura não recusa campo desconhecido) e, se gravar, os perde. Campo novo que não tenha um "ausente" que valha como nulo, ou que mude o que já está gravado, sobe o formato (o passo acima). **A cor da pasta e o ícone e a cor do script** (RN-PASTA-007 e RN-SCRIPT-006: `VaultFolderRecord.Color`, depois do ambiente, e `VaultScriptRecord.Icon` e `Color`, depois das datas) entraram do mesmo jeito, no formato 3: nulo é "sem cor" e o ícone padrão, e o `VaultFolderColorAndScriptIconTests` prova com um cofre do formato 3 montado à mão sem os três campos (abre com eles nulos, é regravado com eles e os devolve na entrada seguinte). Ele e o `VaultProtectionsTests` escrevem o número 3 de propósito, como o `VaultFolderEnvironmentTests` escreve o 2: com o formato 4 eles passam a provar também a migração desse cofre. **As proteções e a verificação periódica** (seção 32: `VaultFolderRecord.ConfirmCommands` e `ReadOnly`, depois da cor; `VaultConnectionRecord.ConfirmCommands`, `ReadOnly`, `VerificationEnabled`, `VerificationInterval` e `VerificationQuery`, depois das datas) entraram do mesmo jeito, no formato 3: nulo é o padrão (sem confirmação, sem somente leitura, a verificação ligada a cada 30 segundos com a consulta do banco), e **o padrão se grava nulo** (`ConnectionRecords.ToRecord`, `ProtectionRules.ToRecord` e `NormalizeConfirmation`), para a conexão gravada antes e a de agora sem nada escolhido serem iguais; o `VaultProtectionsTests` prova com um cofre do formato 3 montado à mão sem os sete campos.
- O `VaultCrypto.DeriveKey` aceita senha vazia (o Argon2 da biblioteca a recusa com exceção): ela vira um byte zero, que nenhuma senha criada produz, para o 401 de quem entra em branco custar a mesma derivação e não virar 500.
- Os parâmetros de derivação do cabeçalho têm teto (256 MiB, 8 passadas, paralelismo 8), na leitura e na gravação. Os tetos e os tamanhos do sal, do nonce e da tag moram num lugar só, `Vault/Clients/VaultHeaderLimits`, que o `VaultFileClient` e o arquivo da exportação de conexões (`ConnectionFileClient`, RN-TRANSF-010) conferem antes de derivar. Subir o padrão da RN-COFRE-002 além disso exige subir o teto ali na mesma mudança. O dado autenticado é `VaultCrypto.AssociatedData(prefixo, versão, kdf)`: o cofre usa `prism-vault` (`VaultPrefix`), e o arquivo da exportação, `prism-connections`.
- **Trocar a senha** (RN-COFRE-013: `PUT api/user/password` → `ChangePasswordHandler` → `IVaultService.ChangePasswordAsync`). É uma operação só do serviço, com o semáforo tomado: conferir a senha atual, recusar a nova igual a ela, **recifrar o cofre** e gravar. Uma conferência feita antes, no handler, poderia ser de um cofre que outro usuário já trocou quando a gravação acontecesse. **A conferência é a de sempre**: `CheckPassword` (privado) é o único jeito de conferir a senha do usuário, e `ReadIfPasswordMatchesAsync` (revelar senha), `ChangePasswordAsync` e `SaveWithPasswordAsync` (o somente leitura, RN-PROT-003, em "Proteções e verificação periódica") o usam: uma derivação com o sal e os parâmetros do ARQUIVO (a senha errada custa o que custa uma entrada errada, e a prova é a contagem do `Derive` do teste, e não o relógio) e a MESMA contagem de cinco erros seguidos (RN-CONN-003). **Os códigos** (todos 422, com o campo em `errors` e `errorCodes` pelo nome da propriedade em PascalCase, como as outras rotas os devolvem; a tela os lê com a primeira letra em minúscula): a senha atual errada é `INVALID_PASSWORD` no `CurrentPassword`, o MESMO código da revelação de senha (`UserErrors.CurrentPasswordInvalid`, com o título dela); a senha nova inválida é `PASSWORD_INVALID` no `NewPassword`, que é do validator, antes do handler e sem derivação, e por isso nunca conta erro; a nova igual à atual é `PASSWORD_UNCHANGED` no `NewPassword`, só depois da conferência (a atual errada e igual à nova é a de senha errada), e acertar zera a contagem mesmo assim. O quinto erro seguido de senha atual, somando os da revelação, fecha o cofre e responde 401 `VAULT_LOCKED`, e não o 422. **O que muda no arquivo (a chave do cofre GIRA, RN-COFRE-003)**: mudam `kdf.salt` (16 bytes novos), `kdf.memoryKiB`, `kdf.iterations` e `kdf.parallelism` (**nunca mais fracos que os do arquivo**: campo a campo, o maior entre o do arquivo e o das opções (`NewKdf(open.File.Kdf)`); um cofre criado com parâmetros mais fracos passa a ter os atuais, e um criado com parâmetros mais fortes não é rebaixado), `wrappedKey` (uma chave do cofre NOVA de 256 bits, gerada por `newKey` (o `VaultCrypto.NewKey`, o mesmo gerador da criação, que entra no serviço pelo construtor como a derivação, para o teste ver o buffer), cifrada com a chave derivada da senha nova, nonce novo) e `payload` (o mesmo documento, cifrado com a chave nova, nonce novo). `version` e `algorithm` ficam. O dado autenticado das duas cifras é `prism-vault|<version>|<algorithm>|<memoryKiB>|<iterations>|<parallelism>|<sal em base64>`, em UTF-8, então o conteúdo TEM de ser cifrado de novo com o cabeçalho novo (senão o cofre ficaria ilegível). Por isso quem tem a senha antiga e uma cópia do arquivo de antes da troca tira da cópia a chave ANTIGA, e ela não decifra o conteúdo novo, nem o gravado depois, nem o `.bak`: o `ChangePassword_TheKeyOfAnOldCopyDoesNotDecryptTheNewContent` exerce o ataque de verdade (a chave abre a cópia antiga e não abre o arquivo novo). A chave antiga é zerada da memória DEPOIS de o `_open` trocar, e **nenhum caminho guarda a chave em variável através do semáforo**: toda operação (`Save`, `ChangePassword`, `Close`) lê o `_open` depois de tomá-lo, então uma gravação comum que entra na fila durante a troca sela com a chave e o cabeçalho novos (há um teste determinista, que a põe na fila sem esperar por tempo). O cofre continua aberto, com a mesma instância do documento: a troca não sobe a `Generation` nem dispara `Locked`, então as sessões com os bancos não caem nem têm a abertura recusada, e a revelação da senha de uma conexão segue funcionando (com a senha nova). **Gravação e falha** (RN-COFRE-005): a primeira gravação é a de sempre (`client.Write`: temporário, `File.Replace`, `.bak`, com a nova tentativa descrita abaixo), e o `_open` só é trocado depois dela; se ela falha (disco, `.tmp` que não dá para criar, parâmetros acima do teto, ou nem a nova tentativa resolveu), a resposta é 503 `VAULT_UNAVAILABLE`, a chave nova é zerada sem nunca ter chegado ao `_open`, e o arquivo e a memória seguem com a senha e a chave antigas; uma exceção antes da gravação deixa o mesmo estado e solta o semáforo. Depois da primeira vem uma **segunda gravação do mesmo arquivo**, cujo `File.Replace` deixa o `.bak` byte a byte igual ao principal novo: sem ela o `.bak` seria o principal de antes, com a chave e o embrulho ANTIGOS, e como o app promove o `.bak` quando o principal some (RN-COFRE-005) a senha antiga voltaria a abrir o cofre. Se só a segunda falha, a troca continua valendo (sucesso, 204) e o `VaultService` registra um aviso (`Warning`) que diz só o que se sabe: a cópia de segurança PODE não estar atualizada (a falha pode ter parado entre as duas trocas de nome, e então o `.bak` já é o novo), e será refeita na próxima entrada ("Cura do `.bak` na entrada", abaixo). O aviso leva só a classe da falha, sem aspas: sem senha, sem nome de usuário e sem exceção, RN-LOG-001. As duas chaves derivadas, a cópia da chave do cofre que a conferência abre e a chave antiga são zeradas. O `ChangePasswordCommand` sobrescreve o `ToString()`.
- **O que a troca de senha NÃO protege** (RN-COFRE-013). **Uma cópia antiga do arquivo do cofre continua abrindo o conteúdo ANTIGO com a senha ANTIGA**: um backup, o histórico de uma pasta sincronizada, um `.bak` de outra época que alguém guardou. A troca protege o que é gravado DEPOIS dela e o conteúdo do arquivo novo (já cifrado com a chave nova), e não o que já está em cópias antigas: a chave que uma cópia antiga entrega, com a senha antiga, abre aquela cópia e nada do que veio depois. Quem trocou a senha porque a antiga vazou tem de apagar as cópias antigas que ele mesmo guardou. E há uma janela curta, entre as duas gravações da troca, em que o `.bak` ainda é uma cópia antiga: se a segunda gravação falhar, ele fica assim até a próxima entrada, que o refaz.
- **Nova tentativa na gravação** (RN-COFRE-013). A troca de arquivos de TODA gravação do cofre (a criação, a gravação comum, as duas da troca de senha e a cura do `.bak`) é tentada de novo, até cinco vezes e com 50, 100, 200 e 400 ms de espera (750 ms no total: é o máximo que a nova tentativa segura o semáforo do cofre), quando o arquivo está em uso por outro programa (antivírus, cópia de segurança): `UnauthorizedAccessException` e, no Windows, o `IOException` de código Win32 32 ou 33 (compartilhamento ou trava), 1175 (o arquivo a ser substituído não pôde ser removido: é o `.bak` aberto por outro programa) e 1176 e 1177 (o substituto não pôde ser renomeado; o 1177 é o principal já renomeado para o `.bak`). **A chamada inteira do `Write` se repete no mesmo `Send`** (o único `try` do client): o temporário é escrito de novo e a troca é refeita, então a troca parada entre as duas trocas de nome (1177) é completada pela tentativa seguinte, que não acha o principal e move o temporário para o lugar dele. Nada se repete depois de uma troca que valeu (ela não lança); disco cheio, caminho que sumiu e o resto têm o desfecho de sempre (`Unavailable`, sem nova tentativa); o token da requisição, que o serviço entrega a todo `Write`, interrompe as novas tentativas (a primeira sempre acontece). Cada nova tentativa vai ao log como `Information`, com a classe da exceção e sem a mensagem. As costuras de teste são o `FileSwap` e o `RetryWait` do client (`internal init`), para o "arquivo em uso" não depender do sistema operacional nem de tempo; nos testes que precisam de uma falha de disco permanente, a pasta no lugar do temporário também é tentada de novo (é acesso negado) e custa os 750 ms.
- **Cura do `.bak` na entrada** (RN-COFRE-013). A cada entrada bem-sucedida (`UnlockAsync`, que é também o desbloqueio) o serviço confere, depois de a senha conferir, se o `.bak` existe e está embrulhado pela MESMA senha do principal, comparando o sal da derivação e a chave embrulhada dos dois cabeçalhos (`HasTheSameWrapping`), e NÃO o arquivo inteiro: depois de uma gravação comum o `.bak` é a versão anterior, diferente do principal e com o mesmo embrulho, e isso não se refaz. Se o embrulho difere (a segunda gravação de uma troca falhou, ou a energia caiu entre as duas), regrava o principal, uma vez: o `File.Replace` põe o principal, que já tem a senha nova, no lugar do `.bak`. O `ReadBackup` do client lê só o `.bak`, sem promovê-lo nem tocá-lo; um `.bak` ilegível (`Corrupt`) ou de formato mais novo (`NewerFormat`, RN-VERSAO-005) não é tocado, porque a regravação o sobrescreveria. A entrada que falha (senha errada, usuário inexistente) não olha o `.bak` (RN-COFRE-006), e a falha da cura não impede a entrada: vai ao log como `Warning` ("a cópia de segurança do cofre não pôde ser refeita na entrada") e a entrada seguinte tenta de novo.
- `AddInfrastructure` registra um `Serilog.ILogger` de reserva (`TryAdd`), porque o `ApiHost` dos testes não chama `UseSerilog`.

## Sessões com os bancos (`Prism.Infrastructure/Databases`)

A segunda integração, no mesmo formato do cofre (`Models/`, `Clients/`, `Services/`). A Application fala só com o `IDatabaseSessionService`; os drivers ficam atrás do `IDatabaseClient`, e nenhum tipo do fornecedor sai de `Clients/`.

- **`AdoDatabaseConnection` é a base dos três bancos** (`DbConnection`, `DbCommand`, `DbDataReader`). Tem o único `try` da integração, o `Send`, por onde passam também abrir, cancelar e descartar. O banco novo herda dela e informa: `CreateConnection`, as consultas de catálogo (SQL com as colunas na ordem que o comentário de cada propriedade diz, parâmetros posicionais sem nome, booleano como `boolean` ou 0/1; ver "Catálogo estendido"), `PingSql`, `CountSql`, `ToFailure` (mensagem com detalhe e dica, SQLSTATE e posição), `BeginReadOnlySql` e `IsWriteRefusal`. O client de cada banco é uma linha: `new XConnection(settings, logger).OpenAsync(cancellationToken)`. Os ganchos opcionais, que só o banco que precisa sobrescreve: `SettingsRefusal` (o que o driver não aceita nos dados da conexão, dito antes de chamá-lo), `TriesAsRead`, `IsTransactionControl`, `HasSeveralStatements` e `MayBeCounted` (o que o texto do comando decide), `MayHaveOpenedATransaction`, `MayLeaveATransactionOpenWhenItFails` e `ProbeTransactionAsync` (a rede de segurança), `CancelReturnsEmptyResult` e `BlocksTheCallingThread` (o que o driver faz ao ser cancelado e se ele é síncrono), `ColumnKind`, `ReadCell` e `ConfigureUserCommand` (como o resultado é lido). O que cada um vale no Db2 e no Informix está em "Db2 e Informix", abaixo.
- **`IsOpen` não é só o estado que o driver informa.** A base marca a conexão que ela mesma descartou (`_discarded`): o driver da IBM continua respondendo "aberta" depois do descarte de uma conexão que ele não conseguiu fechar, e o registro de sessões seguiria mandando comandos a ela. **A marca só sobe depois de o descarte do driver voltar.** Posta antes, ela fazia o comando em andamento pular a conferência de transação (que pergunta por `IsOpen`), e o descarte do Npgsql, que depende de o comando seguir até o fim, não voltava.
- **Um comando por execução, enviado como está** (RN-SQL-001 e 003). No PostgreSQL o driver não divide nem reescreve o texto (`Npgsql.EnableSqlRewriting` desligado no construtor estático de `PostgresConnection`, antes do primeiro comando do processo): mais de um comando por envio é recusa do próprio banco, que não executa nenhum. Com a divisão ligada, um `UPDATE` antes de um `SELECT` grande era desfeito, sem erro, quando o cursor fechava. Consequência para as consultas do próprio Prism: parâmetro só posicional (`$1`), nunca `@nome`. No Db2 e no Informix o driver divide o envio e não há como desligar isso: quem recusa mais de um comando é a base, pelo gancho `HasSeveralStatements`, com `EDatabaseFailure.MultipleStatementsNotSupported` (422 `MULTIPLE_STATEMENTS_NOT_SUPPORTED`), e o comando vai sem os `;` soltos em volta (ver "Db2 e Informix").
- **Controle de transação é recusado na base, sem ir ao banco** (`SqlText.IsTransactionControl`, `EDatabaseFailure.TransactionControlNotSupported`, que a rota traduz em 422 `TRANSACTION_CONTROL_NOT_SUPPORTED`): `BEGIN`, `START TRANSACTION`, `COMMIT`, `END`, `ROLLBACK`, `ABORT`, `SAVEPOINT`, `RELEASE` e `PREPARE TRANSACTION` como primeira palavra, depois do que o banco pula antes de um comando: espaços, comentários (o `--` acaba na quebra de linha ou no retorno de carro) e `;` soltos. `;BEGIN` chegava ao banco e abria uma transação que desfazia a gravação seguinte. `PREPARE TRANSACTION` só conta quando o que vem depois é o identificador dela, uma constante de texto em qualquer das formas do PostgreSQL (`'...'`, `$marca$...$marca$`, `E'...'`, `U&'...'`); `PREPARE transaction AS ...` prepara uma consulta. Palavra com caractere de fora do ASCII nunca é palavra reservada (`BEGINé`, e `begın` com o i sem pingo do turco, porque o banco só iguala maiúsculas e minúsculas do ASCII): vai ao banco, e o erro de sintaxe é dele. A recusa é um gancho (`IsTransactionControl`), e o `SqlText` lê o comando no dialeto do banco (`ESqlDialect`): o que é comentário e o que é controle de transação muda de um para o outro (ver "Db2 e Informix").
- **A rede de segurança da recusa** (RN-SESSAO-005): depois de um comando em modo completo que voltou sem conjunto de resultados e com `RecordsAffected` negativo (comando utilitário, que é como um `BEGIN` volta; leitura e DML não pagam nada), a base pergunta ao banco se a conexão ficou dentro de uma transação (`ProbeTransactionAsync`, que responde `Idle`, `InTransaction` ou `Failed`; por padrão a resposta é `Idle`, que é a do Db2, e o Informix tem a dele). Se ficou, a transação é desfeita ali mesmo, pelo mesmo fim da transação da tentativa (`ROLLBACK`; se ele não passa com a conexão viva, a conexão fecha e a sessão sai do registro), e a resposta é `TransactionControlNotSupported`. No PostgreSQL a sonda é o `BeginTransactionAsync` público do Npgsql: ele lança, sem enviar nada, quando a resposta do servidor ao último comando disse que há transação aberta (o driver não mostra esse estado de outro jeito: `FullState` não o tem, `Npgsql.Internal.TransactionStatus` é interno, e reflexão não se usa); sem transação, o `RollbackAsync` do pedido envia `BEGIN` e `ROLLBACK` numa ida só (0,55 ms por comando utilitário em rede local), sem aviso nem erro no log do servidor. **A sonda que falha não recusa o comando**: quando ela roda, o banco já confirmou o comando, e responder recusa faria a pessoa executá-lo de novo e gravar duas vezes. Só diz "há transação" (`InTransaction`) a recusa do `BeginTransactionAsync`, que acontece antes de qualquer envio, e só com a conexão aberta: decidem o ponto em que a exceção sai e o estado da conexão, nunca o texto dela, que muda com a versão e o idioma do driver. A classe da exceção não separa nada ali: o Npgsql 10.0.3 recusa com a mesma `InvalidOperationException` a transação aberta, a conexão fechada, a descartada (`ObjectDisposedException`, que deriva dela) e a ocupada por um leitor, que não acontece porque a base só pergunta depois de fechar o cursor do comando. Por isso a regra "conexão que não está aberta nunca é há transação" mora na base (`EndStrayTransactionAsync`), para a sonda de qualquer banco. O que falha depois do `BeginTransactionAsync` é a ida e volta da própria sonda (`Failed`), e a resposta continua sendo o sucesso do comando, sem o aviso de transação aberta no log: a conexão que caiu (também quando o servidor recusa o `BEGIN` da sonda, porque aí o próprio Npgsql a derruba) não recebe mais nada e sai do registro pelo `IsOpen`; a que continua viva (o servidor recusou o `ROLLBACK` da sonda) pode ter ficado dentro da transação da sonda, e a base a limpa pelo mesmo fim (`ROLLBACK`, ou a conexão fechada se ele não passa). O `RollbackAsync` vem antes do descarte porque ele lança e o descarte não: é como a base fica sabendo que a ida e volta falhou. Quem administra o banco enxerga a sonda: cada comando utilitário soma 1 em `pg_stat_database.xact_rollback` e aparece como um par `BEGIN`/`ROLLBACK` no log de quem usa `log_statement`. O aviso 25P01 de um `ROLLBACK` solto (evento `Notice`) não serve de sonda: `SET client_min_messages = error`, que o usuário pode executar a qualquer momento, o esconde, e todo `CREATE TABLE` passaria a ser recusado. Cada transação pega pela rede deixa no log um aviso próprio (`Warning`, "Um comando deixou uma transação aberta na conexão: ela foi desfeita, e o comando foi recusado."), sem SQL e sem pilha: é o sinal de que falta uma forma no `SqlText`. O gancho de um banco não lança: a chamada ao driver passa pelo `TryAsync` da base, em que a exceção do driver é a resposta procurada e por isso não vai para o log como conexão que falhou (a recusa do banco vai, como as outras; a que é resposta de rotina do gancho, `IsRoutineRefusal`, vai como depuração). `ExecuteWithoutRefusalAsync` é `internal`, e não privado, só para o teste da rede chegar ao banco com um `BEGIN`.
- **Auto-commit de verdade** (RN-SESSAO-005, RN-SQL-004 e 013). Só comando de leitura fica com cursor aberto entre páginas, e quem diz que é leitura é o banco. O comando que começa como leitura (`MayBeRead`: `SELECT`, `WITH`, `VALUES`, parêntese; no PostgreSQL também `TABLE`, `SHOW`, `EXPLAIN`) e não é um `WITH` que grava (`SqlText.WithModifiesData`: começa por `WITH`, com ou sem parênteses na frente, e tem `INSERT`, `UPDATE`, `DELETE` ou `MERGE` como palavra inteira, fora de texto, de `$marca$`, de identificador entre aspas e de comentário; `updated_at` e `is_deleted` não contam, e um `$` logo depois de um caractere de palavra é parte do identificador, como em `k$a$b`, e não abertura de `$marca$`; caractere de palavra é letra, dígito e `_` do ASCII e todo caractere a partir de U+0080, que é como o PostgreSQL lê identificador e marca: `é$a$` é um nome, e `$é$ ... $é$` é um texto) é tentado dentro de `BeginReadOnlySql` (`BEGIN TRANSACTION READ ONLY`), com o leitor aberto: as linhas por página (200, ou o `pageSize` da busca, RN-SQL-016) e uma leitura a mais, que diz se há outra página sem contar nada. Se o banco recusa a tentativa por gravar (`IsWriteRefusal`: 25006, ou 25001 para o que não roda em transação), ela é desfeita e o comando roda em modo completo; qualquer outro erro da tentativa é o erro do comando. Modo completo, que é também o de tudo o que não começa como leitura: fora de transação, lido até o fim, guardando as primeiras linhas (as da página) e contando o resto em `QueryPage.TotalRows`, com `HasMore` falso. Quando a resposta sai, o banco já confirmou.
- **O fim de um comando lido até a última linha faz parte dele** (`FinishCursorAsync`, dentro do `Send` do comando). O banco só confirma depois de entregar a última linha, e o que ele recusa ali (uma chave estrangeira adiada, por exemplo) é a falha do comando, com o SQLSTATE dele; responder com as linhas seria mostrar o que o banco não gravou. No modo completo a recusa só aparece quando o resultado é lido até o fim: no Npgsql o último `ReadAsync` devolve `false` no `CommandComplete`, e o erro vem depois, no `NextResultAsync`. Na tentativa paginada ela vem no `COMMIT` que fecha a transação quando a leitura chega ao fim, na primeira página ou no "carregar mais" que traz a última. O `COMMIT` existe pelo que a transação só de leitura deixa passar e precisa ficar (`set_config`, gravação em tabela temporária). Depois de um `COMMIT` recusado o PostgreSQL já desfez a transação: o `ROLLBACK` da limpeza volta só com um aviso, e a conexão continua aberta.
- **O cursor abandonado (`DisposeCursorAsync`) não falha e sempre desfaz a transação**: `Cancel()` e `ROLLBACK`, quando o cursor fecha antes da última linha (outro comando, ociosidade, fechar a sessão) e quando o comando falhou. Sem o `Cancel`, o descarte do leitor do Npgsql lê e joga fora o resto do resultado. Um erro que o banco deixou mais adiante num resultado que ninguém leu até lá (divisão por zero na linha 300, gravação recusada na linha 251) aparece no "carregar mais" que chega até ele; se o cursor é abandonado antes, vai para o log, e nunca vira o erro do comando seguinte nem faz uma leitura ser tomada por comando que grava. Isso vale só para o cursor abandonado, de que nada foi dado como gravado: o erro do fim de um comando lido até a última linha é o do item acima. O `ROLLBACK` é a saída do bloco (`TransactionEnd`), que roda mesmo quando o descarte do leitor lança. Se ele não passa com a conexão viva, a base fecha a conexão (ela ficaria presa numa transação abortada), e o registro tira a sessão cuja conexão não está mais aberta, depois de qualquer operação e do fechamento por ociosidade. Qualquer comando novo na conexão (inclusive catálogo e verificação) abandona o cursor anterior, no `RunAsync`, antes de ser enviado; se essa limpeza fechou a conexão, o comando não é enviado e responde "A conexão com o banco foi encerrada, e o comando não foi enviado", no lugar do erro do driver para uma conexão descartada.
- **O que a tentativa custa e não resolve.** Uma função volátil chamada por uma leitura roda duas vezes até o primeiro ponto de gravação: a primeira é desfeita, mas o que ela fez fora da transação (dblink, tabela estrangeira, linguagem não confiável, espera) aconteceu duas vezes. Se a função só grava depois da linha 200, quem recebe a recusa do banco é o "carregar mais", com um aviso, e nada é gravado; a conexão guarda esse comando, e executá-lo de novo vai direto ao modo completo. Um `WITH` que grava não passa mais pela tentativa (roda até o fim), então a gravação em tabela temporária por ele fica; o que continua passando pela transação só de leitura sem ser recusado são as funções com efeito na sessão (`set_config`, `pg_notify`, travas consultivas), exceção escrita na especificação. Limite conhecido do `SqlText`, sem código para ele: com `standard_conforming_strings = off` na sessão (o padrão do PostgreSQL é `on`), a barra invertida escapa a aspa também dentro de um texto comum (`'a\''`), e o `SqlText`, que só conhece a barra em `E'...'`, lê esse texto errado e pode perder o que vem depois; um `WITH` que grava em tabela temporária depois de um texto assim pode ser tomado por leitura, e o que ele gravou é desfeito quando o cursor fecha antes do fim (em tabela comum o banco recusa a tentativa, e o comando roda até o fim). Entre páginas a sessão fica em transação no banco: vale o `idle_in_transaction_session_timeout` do servidor (a sessão cai e a tela abre outra) e a tabela fica com trava de leitura até o cursor fechar, no máximo cinco minutos. Cada leitura custa duas idas ao banco a mais (`BEGIN` e `COMMIT`): 1,8 ms contra 0,5 ms numa consulta pequena em rede local.
- **Medido numa tabela de 200.000 linhas (120 MB), PostgreSQL local**: primeira página em 5 a 6 ms, com a memória do processo igual antes e depois; fechar o cursor no meio, 50 a 60 ms; `UPDATE ... RETURNING` das 200.000 linhas, 830 ms, com 200 linhas na resposta e a memória igual.
- **Cancelar** (RN-SQL-010) só age com comando em andamento, na conexão e no serviço: um cursor aberto e parado continua legível até o fim. Cada comando em andamento tem a própria fonte de cancelamento, ligada à da requisição e entregue a todo envio ao banco: o cancelamento que chega antes de o comando do usuário ser enviado (enquanto o `BEGIN` da tentativa vai ao banco) faz com que ele nem seja enviado. No PostgreSQL a fonte é o único pedido de cancelamento (`CancelCommand` vazio): um segundo, pelo `Cancel` do comando, poderia atingir o `ROLLBACK` da limpeza ou o comando seguinte. O padrão da base chama também o `Cancel` do comando, para o driver que não observa a fonte enquanto espera uma linha. Um comando que terminou antes de o cancelamento chegar é sucesso: no PostgreSQL quem diz que cancelou é a exceção do driver. O estado `_canceled` da base só decide o resultado no banco cujo driver não lança quando o cancelamento chega durante a leitura (`CancelReturnsEmptyResult`, ligado no Db2 e no Informix), e só o de uma leitura em andamento: quem o confere é o `RunAsync`, depois do `Send` do comando, e nunca a sonda de transação nem a limpeza, que rodam fora dele (um cancelamento tardio fazia a sonda responder "cancelado" com a chamada tendo passado). O `CancellationToken` da requisição interrompe o comando do mesmo jeito. Duas respostas de cancelamento não vêm do banco: "O comando foi cancelado.", quando o comando nem foi enviado e a conexão continua aberta; e "O banco não respondeu ao cancelamento a tempo, e a sessão foi encerrada. O Prism não sabe se o comando foi concluído...", quando o Npgsql esperou os dois segundos do `Cancellation Timeout`, não teve resposta e derrubou a conexão: nesse caso o comando pode ter sido concluído e confirmado no banco depois (um `UPDATE` que ignora o cancelamento por três segundos é confirmado), e a sessão sai do registro. Nos drivers da IBM há uma terceira, "O cancelamento chegou enquanto o comando devolvia as linhas. O que ele gravou até ali está confirmado, e pode ser só uma parte do comando: o Prism não sabe se ele foi concluído...", com a sessão aberta; no Informix, quando esse comando tinha deixado uma transação aberta, a resposta é a recusa "O comando deixou uma transação aberta, e o Prism a desfez..." (ver "Db2 e Informix").
- **O desfecho do cancelamento e o `executed`** (RN-SQL-010, RN-SESSAO-005, Ruling 135). A tela decide por estes campos, nunca pelo texto. `DatabaseFailure.Outcome` (`ECancelOutcome`) vai no corpo de `SQL_EXECUTION_FAILED` como `outcome`, e só quando houve pedido de cancelamento para aquele comando (a rota `queries/cancel`, que vale também para a contagem e o "carregar mais", o fechamento da sessão, a requisição abortada): quem decide é o `RunAsync`, pela marca `_canceled` e pela fonte do comando. Sem pedido não há desfecho (o 57014 de um `statement_timeout` é erro comum), e o erro do próprio comando que chega com o cancelamento a caminho também não leva. `canceled`: o banco disse que interrompeu o comando (`IsInterruption`: 57014 no PostgreSQL e no Db2, o nativo -213 no Informix, e, nos dois bancos da IBM, a exceção sem nenhum erro do banco (`CameWithoutErrorInformation`, ver o "Salvar" da coluna inteira), lido da exceção, e não do `_lastNativeError`, que o pedido de cancelamento em outra thread também escreve), ou "O comando foi cancelado." (o cancelamento sem resposta do banco com a conexão aberta, e a leitura que o driver da IBM só cortou). `unknown`: "O banco não respondeu ao cancelamento a tempo...", e também a interrupção que o driver da IBM dissesse depois de o leitor do comando executado até o fim abrir (`_executed`: o comando já rodou, e a interrupção não prova nada). `partial`: "O cancelamento chegou enquanto o comando devolvia as linhas...". `DatabaseFailure.Executed` vai como `executed: true` em `TRANSACTION_CONTROL_NOT_SUPPORTED` quando o comando rodou e a base desfez a transação que ele deixou aberta (a rede de segurança, e a resposta do Informix cancelado enquanto devolvia as linhas): o cursor anterior já fechou. A recusa pelo texto, antes de executar, não leva a extensão, e o cursor anterior continua. **A prova do "O comando foi cancelado." sem SQLSTATE**, que é o que pode gravar e não pode ser `canceled`: no Npgsql 10.0.3 o cancelamento sem a resposta 57014 só sai com a conexão aberta do `ThrowIfCancellationRequested` do começo do `ExecuteReader`, antes de enviar; o `ReadAsync` e o `NextResultAsync` não conferem o pedido (só registram o envio de um pedido ao servidor), e o tempo esgotado depois dele derruba a conexão (`unknown`). No PostgreSQL o 57014 é sempre comando desfeito: o servidor só confirma no `Sync`, depois da última linha, e o pedido que chega enquanto ele devolve as linhas de um `UPDATE ... RETURNING` (que o executor já terminou) é descartado ali, e o comando é confirmado: a resposta é sucesso. `Cancel_WhileAWriteReturnsItsRows_IsCanceledOnlyWhenNothingWasWritten` (PostgreSQL) cancela em cada fase, com o servidor na espera `ClientWrite` no `pg_stat_activity`, e escreve cada resposta na saída. No driver da IBM o cancelamento sem resposta do banco só sai das versões assíncronas do ADO.NET (`DbCommand.ExecuteReaderAsync`, que o driver não sobrescreve, confere o pedido antes de chamá-lo; o `ReadAsync` dele é usado com o pedido só nas leituras), e o comando executado até o fim é lido sem o pedido.
- **Comando do usuário não tem tempo limite** (`CommandTimeout = 0`): quem o interrompe é o usuário. Catálogo e verificação ficam com o padrão do driver.
- **O PostgreSQL lê o resultado do usuário em texto** (`AllResultTypesAreUnknown`, como o psql), pelos ganchos opcionais `ConfigureUserCommand`, `ColumnKind` e `ReadCell`. Nos tipos do C# o Npgsql recusa o resultado inteiro quando não tem tipo para uma célula: `SELECT * FROM pg_class` (e `pg_proc`, `pg_attribute`, `pg_type`, `pg_constraint`, `pg_index`, `pg_namespace`, `pg_stats`), `age()`, `numeric` acima de 28 dígitos ou NaN, data antes de Cristo. Consequência para a tela: data e hora do PostgreSQL chegam como o servidor escreve (`2026-01-01 00:01:00`, com `+00` no `timestamptz`); as dos outros bancos passam pelo `CellFormatter` (`yyyy-MM-dd HH:mm:ss.ffffff`). O `kind` da coluna sai do nome do tipo, por tabela exata (`daterange` não é data). Db2 e Informix ficam no padrão (`GetValue` e o `CellFormatter`), menos nos tipos em que o C# perde o que o banco guarda (ver "Db2 e Informix").
- **A mensagem do banco vai inteira para a tela e nunca para o log** (RN-SQL-009 e RN-LOG-001). No PostgreSQL ela é a `MessageText` e, quando o banco manda, o `DETAIL` e o `HINT`, cada um na sua linha (`IncludeErrorDetail` ligado: sem ele o usuário não sabe qual chave se repetiu). Por isso mesmo nenhuma chamada de log recebe a exceção, a mensagem ou o SQL: o `Send` registra a classe da exceção e o SQLSTATE, e o serviço, a sessão, a operação, a duração, as linhas e o tipo da falha. Log novo nesta pasta segue a mesma lista. O `Send` desembrulha a exceção de conjunto (`AggregateException`) que traz dentro uma só recusa do banco ou um só cancelamento: o driver da IBM entrega assim o erro que acontece durante a leitura das linhas, e sem isso a tela recebia "One or more errors occurred" e o log, uma pilha.
- **Um `NpgsqlDataSource` por conexão, descartado com ela** (`DisposeDriverAsync`): `new NpgsqlConnection(texto)` guarda a string de conexão, com a senha, num registro estático do driver até o processo acabar, mesmo com `Pooling = false`. O custo é o driver reler o catálogo de tipos a cada conexão: abrir leva cerca de 18 ms em rede local, contra 7 ms.
- **A mensagem de uma falha do PostgreSQL que não veio do servidor diz a causa uma vez só** (`PostgresConnection.CauseText`, RN-SQL-009, com teste). O host que não resolve chega como uma `NpgsqlException` cuja exceção interna (`SocketException`) diz a mesma frase ("Name or service not known"), e a mensagem juntava as duas ("Name or service not known: Name or service not known"). Se uma das duas já contém a outra, fica a que diz mais; senão, as duas, a da exceção primeiro. A regra de que a mensagem do banco chega à tela como veio continua: só o texto repetido sai. O Db2 e o Informix não juntam a causa à mensagem.
- **`IDatabaseSessionService` é `Singleton` e `IAsyncDisposable`**: o descarte do contêiner fecha as sessões (RN-SESSAO-004), e quem monta um contêiner com ele o descarta com `DisposeAsync`. Uma operação por vez em cada sessão: executar e carregar mais tentam a vez sem esperar (`SessionBusy`); as consultas de catálogo esperam, com o `CancellationToken` da requisição (RN-SESSAO-002).
- **`OpenAsync(connectionID, settings, vaultGeneration, cancellationToken)`**: quem chama lê `IVaultService.Generation` ANTES das credenciais. A conferência da geração e o registro acontecem sob a mesma trava que o fechamento do cofre usa para tirar as sessões do registro; se a geração mudou, a conexão recém-aberta fecha e a falha é `EDatabaseFailure.VaultChanged` (a rota responde 401 `VAULT_LOCKED`).
- **O aviso `Locked` do cofre** tira do registro, na hora e com a geração lida sob a trava, as sessões de outra geração (as do cofre que acabou de abrir, numa troca de usuário, ficam) e fecha as conexões em outra thread.
- **Fechar uma sessão** interrompe o comando e a contagem que rodam nela. O cancelamento vai em outra thread e se repete; a espera pela vez tem teto de dez segundos, e depois dele a conexão é abandonada (o descarte fica com o driver, sem ninguém à espera): com a rede morta o Npgsql leva cerca de 30 segundos para desistir de um cancelamento, e o descarte de uma conexão com comando em andamento só volta quando o comando acaba. O teto usa o `TimeProvider`. **Risco conhecido do abandono no PostgreSQL**: descartar a conexão do Npgsql com um comando em andamento é uso do mesmo conector por dois caminhos ao mesmo tempo. No Windows, medido com um `CALL` em andamento: o comando responde um erro interno do driver ("Index was out of range"), o descarte não volta, e a conexão fica aberta no banco até a API encerrar. Já era assim antes dos drivers da IBM; o conserto é do fechamento da sessão, e não da base.
- **Sessão cuja conexão caiu sai do registro**: depois de uma falha, `IDatabaseConnection.IsOpen` diz se a conexão ainda serve. A chamada que percebeu responde `ExecutionFailed` com a mensagem do banco, e a seguinte, `SessionNotFound`.
- **"Contar total" abre outra conexão** com as credenciais guardadas na sessão e roda `CountSql` sobre o último comando que devolveu linhas, dentro da transação só de leitura (contar é executar o comando de novo, e assim ele não grava outra vez). Se esse comando gravou, o total já veio em `TotalRows` e é o que a contagem devolve, sem ir ao banco. Não toma a vez da sessão. Quem a interrompe: a requisição abortada, o `Cancel` da sessão, o fechamento dela e o do cofre (uma fonte de cancelamento por sessão, trocada a cada `Cancel`). A posição do erro não vem (seria a do comando embrulhado).
- **Cursor ocioso** (RN-SQL-007): um temporizador do `TimeProvider` por sessão, rearmado a cada página com `hasMore`; ao disparar, confere a hora da última leitura antes de fechar (adiantado, volta a contar o que falta). Enquanto ele fecha o cursor (dezenas de milissegundos), a sessão responde `SessionBusy`. **Só a página com `hasMore` é leitura.** No fim de cada operação (`WatchCursorAsync`) o registro pergunta à conexão se o cursor continua aberto (`IDatabaseConnection.HasOpenCursor`, o leitor aberto entre páginas na base). Toda operação que vai ao banco fecha o cursor anterior antes de ser enviada, e a que falha também (o erro do banco, o cancelamento, a queda da conexão, a transação desfeita com `executed`): sem cursor, o temporizador para. A que não leu e o deixou aberto não chegou a ele (a recusa antes de ir ao banco: `CONNECTION_READ_ONLY`, `FILTER_INVALID`, o controle de transação sem `executed`, `MULTIPLE_STATEMENTS_NOT_SUPPORTED`; uma recusa nova entra na regra sem mudar nada aqui), e o prazo continua o da última leitura: a recusa não o adia nem conta como leitura. Ela não só deixa o temporizador como estava: o aviso que chega enquanto uma operação tem a vez desiste, contando com ela, então a recusa confere o prazo ao terminar (`CloseCursorIfIdleAsync`, o mesmo do aviso) e fecha o cursor se ele já venceu. Antes, a recusa parava o temporizador, e o cursor ficava aberto (no PostgreSQL, dentro da transação só de leitura, com a trava de leitura) até o comando seguinte ou o fim da sessão. `DatabaseSessionServiceTests` prova com a conexão de mentira, cujo `HasOpenCursor` segue o da base e cuja recusa antes do banco (`Refusal`) não o toca: a recusa do filtro e a da conexão, um minuto depois da leitura, não adiam o fechamento aos cinco minutos; o aviso que chega no meio da recusa não se perde; e a falha de um comando que foi ao banco para o temporizador. Os testes da recusa do somente leitura estão em "Proteções e verificação periódica", abaixo.
- Comando sem linhas devolve `RowsAffected` zero quando o driver informa -1 (DDL): todo `QueryOutcome` tem a página ou as linhas afetadas.
- Chave estrangeira no PostgreSQL: a consulta deixa de fora as cópias que o catálogo cria para cada partição da tabela referenciada (a restrição cujo pai é da mesma tabela), e mantém a que a partição herda da tabela dela.

## Db2 e Informix (`IbmDatabaseConnection`, `Db2Connection`, `InformixConnection`)

Os dois são atendidos pelo mesmo driver da IBM (`IBM.Data.Db2`, sobre o `clidriver` nativo), o Informix pela porta DRDA (9089, e não a 9088 do protocolo nativo). O que eles têm em comum fica em `IbmDatabaseConnection`; cada um informa o dialeto, o catálogo e a consulta de verificação. Tudo abaixo foi provado contra o Db2 12.1 e o Informix 14.10 em contêiner; a nota da sonda (`docs/superpowers/notes/2026-10-09-sonda-ibm.md`) tem a receita das imagens.

- **A conexão fica em auto-commit o tempo todo, e o Prism nunca abre transação nela** (`BeginReadOnlySql` nulo). O Db2 não tem transação só de leitura; a do Informix (`SET TRANSACTION READ ONLY`) existe, mas não em banco sem log, onde `BEGIN WORK`, `COMMIT` e `ROLLBACK` são erro (-256). Por isso a base não manda nenhum dos três numa leitura, e quem diz se o comando grava é o texto dele.
- **Só uma leitura só fica paginada** (`SqlText.IsSingleRead`, RN-SQL-013): começa por `SELECT`, `WITH`, `VALUES` ou parêntese, é um comando só e não tem `INSERT`, `UPDATE`, `DELETE` nem `MERGE` como palavra inteira (no Db2 um `SELECT` grava por `FROM FINAL`, `NEW` ou `OLD TABLE (...)`; com o cursor aberto a gravação ficava pendente até ele fechar). **No Db2 também não tem `TABLE (`**, com qualquer espaço ou comentário entre as duas partes: é como se chama uma função de tabela, e a criada com `MODIFIES SQL DATA` grava sem que o texto do `SELECT` mostre. **No Db2 só é leitura o que o banco e o driver leem como leitura**: com um comentário de bloco dentro de outro as duas leituras do texto divergem (ver o item do `;`, abaixo), a palavra de gravação que só uma delas vê tira a paginação, e a leitura que para o driver não começa por `SELECT` também (ele a mandaria como comando sem linhas, e o banco responde SQL0084N). O custo é aceito: toda leitura do Db2 com função de tabela (`TABLE(MON_GET_...)`, `TABLE(VALUES ...)`) perde a paginação e vem com o total. No Informix `TABLE(FUNCTION f())`, `TABLE(f())` e `TABLE(MULTISET(SELECT f() ...))` com uma função que grava são recusados pelo banco (-675), e a leitura continua paginada. O resto roda até o fim: `CALL`, `EXECUTE PROCEDURE` e `EXECUTE FUNCTION`, o bloco, o `SELECT` que grava. **"Contar total" só conta o que é leitura só** (`MayBeCounted`): sem transação só de leitura, quem impede a subconsulta da contagem de gravar é o texto, e um texto montado para fechar a subconsulta, gravar e abrir outra chegava ao banco; o resto nem vai.
- **O driver divide o envio em cada `;` e executa os pedaços um por um**, cada um confirmado ao terminar, e só roda o seguinte quando o leitor avança ou é descartado; um erro num pedaço do meio não impede os seguintes, e só o erro do primeiro para tudo. `UPDATE a; SELEC 1; UPDATE b` respondia o erro com os dois `UPDATE` gravados, e no Informix `UPDATE ...; BEGIN WORK` respondia sucesso e deixava a conexão dentro de uma transação. Por isso **o envio com mais de um comando é recusado antes de ir ao banco** (`SqlText.HasSeveralStatements`, 422 `MULTIPLE_STATEMENTS_NOT_SUPPORTED`, RN-SQL-001): outro comando depois de um `;`, fora de aspas e de comentário. O `;` do fim e o comentário depois dele não contam. **O bloco com `;` no corpo é um comando só.** No Db2, o que começa por `CREATE [OR REPLACE] PROCEDURE`, `FUNCTION` ou `TRIGGER`, a rotina acrescentada a um módulo (`ALTER MODULE ... ADD` ou `PUBLISH PROCEDURE` ou `FUNCTION`) e o bloco composto (`BEGIN ... END`): o driver manda inteiro o texto que ele lê começando assim (conferido com espaços, quebras de linha e comentários comuns entre as palavras), e o banco, que só executa um comando por envio, recusa o que vier depois do fim do bloco sem executar nada. **O driver não lê o comentário de bloco como o Db2**: o banco aceita um comentário dentro de outro, e o driver o encerra no primeiro `*/`. Com `/* a /* b */ c */` antes das palavras do bloco, ou entre `CREATE`, `OR`, `REPLACE` e `PROCEDURE`, o banco vê o bloco e o driver não: ele dividia no `;`, e `/* a /* b */ c */ ALTER MODULE m PUBLISH PROCEDURE q (); UPDATE ...` respondia sucesso com o protótipo publicado e o `UPDATE` gravado. Por isso no Db2 o `SqlText` lê das duas formas o texto que vai ao driver (`asTheDriver`): só é bloco o que as duas leituras começam pelas palavras dele, e fora do bloco basta uma delas ver um `;` ao lado de um comando para o envio ser recusado, inclusive o `;` que só o driver vê, dentro de um comentário aninhado. Nada legítimo se perde: o bloco com um comentário aninhado na frente já não era executado. Com o comentário aninhado depois da palavra `PROCEDURE`, de `ALTER MODULE` ou de `BEGIN`, as duas leituras veem o bloco, o driver manda inteiro, e quem recusa o que vem depois é o banco. No Informix, `CREATE [OR REPLACE] [DBA] PROCEDURE` e `FUNCTION`, até o `END PROCEDURE` ou `END FUNCTION`: ali o driver também manda tudo, mas **o servidor do Informix executa mais de um comando por envio**, e por isso depois do fim o `;` volta a separar; a rotina externa (a que tem `EXTERNAL NAME '...'` no cabeçalho, antes do primeiro `;`, com o texto entre aspas logo depois do par, a única forma que o banco aceita: não tem corpo nem fim, e o `END PROCEDURE` de outra rotina mais adiante no envio não faz dela um bloco; o par sozinho não conta, porque `SELECT external name FROM t` lê uma coluna com o apelido dela) e o gatilho (as ações dele se separam por vírgula, e `;` no corpo é erro de sintaxe) não são bloco. **O comando vai ao driver sem os `;` soltos em volta** (`SqlText.Statement`, pelo gancho `ConfigureUserCommand`): o pedaço vazio da frente fazia o banco recusar o envio, e o comentário depois do `;` do fim era recusado depois de o comando já estar gravado. O comando executado até o fim lê todos os resultados (`NextResultAsync` em laço) antes de responder: um `CALL` com vários conjuntos devolve o primeiro. **Limites do driver, sem conserto daqui**: ele não reconhece `CREATE DBA PROCEDURE` como bloco e o divide (com `;` no corpo a criação responde erro de sintaxe; sem `;`, funciona); divide pelo `;` de dentro de um comentário entre chaves do Informix (o primeiro pedaço vai com o comentário aberto, o banco o recusa, e nada é executado). O `;` de dentro de um comentário aninhado do Db2 ele também dividiria, e esse envio a API recusa antes, como mais de um comando.
- **Controle de transação por banco** (`SqlText.IsTransactionControl(sql, dialeto)`, RN-SQL-003). No Db2, `BEGIN` seguido de mais alguma coisa é um bloco composto (`BEGIN ATOMIC ... END`), que o banco executa e confirma inteiro, e `RELEASE` só é de transação com `SAVEPOINT`; `COMMIT`, `ROLLBACK`, `SAVEPOINT` e `RELEASE SAVEPOINT` são recusados, embora com o driver em auto-commit não mudem nada. **Os comentários são lidos como cada banco os lê**: o de linha (`--`) do Db2 e do Informix só acaba na quebra de linha (`\n`), e não no retorno de carro como no PostgreSQL (com a regra errada, uma aspa depois do `\r` escondia o `;` seguinte); o de bloco do Db2 pode ter outro dentro (provado: `SELECT /* a /* b */ c */ 1` funciona, `/* a /* b */ c */ COMMIT` executa o `COMMIT`), e o do Informix acaba no primeiro `*/`; só o Informix tem comentário entre chaves (`{ ... }`). A recusa do controle de transação segue a leitura do banco, que é quem executa; a contagem de comandos e a leitura só, no Db2, seguem também a do driver (item acima). Nenhum dos dois tem escape por barra invertida em texto (provado no Db2 12.1 em modo padrão, pelo driver cru: `SELECT 'a\b'` devolve os três caracteres `a\b`; `SELECT 'a\'` devolve `a\`; em `SELECT 'a\''` a aspa dobrada fica dentro do texto, que não fecha, SQL0010N; um valor com barra gravado por `CHR(92)` é achado pelo literal com a barra como está e só a aspa dobrada; e o driver lê do mesmo jeito ao dividir o envio). Lido com a regra do banco errado, um `BEGIN WORK` ficaria escondido.
- **A rede de segurança só existe no Informix.** No Db2 nenhum comando deixa a conexão em transação: o auto-commit é do driver, que confirma depois de cada comando. No Informix `BEGIN WORK` abre uma transação que o auto-commit do driver não fecha, e ela pode vir de dentro de uma rotina (`EXECUTE PROCEDURE`, e também `EXECUTE FUNCTION`, que devolve linhas) ou de um envio de dois comandos que a recusa não reconhecesse. Por isso **a sonda roda depois de todo comando executado até o fim**, tenha ele dado certo (`MayHaveOpenedATransaction` devolve sempre verdadeiro) ou falhado (`MayLeaveATransactionOpenWhenItFails`), inclusive o que foi cancelado enquanto devolvia as linhas; a leitura paginada não paga. Custa duas idas ao banco por comando: medido num banco na mesma máquina, um `UPDATE` de uma linha foi de 0,65 ms para 1,64 ms. A sonda é um `BEGIN WORK` com prazo de cinco segundos: se passa, não havia transação, e ela desfaz a que abriu (`ROLLBACK WORK`); com -256 o banco não tem log, e transação não existe (`Idle`); qualquer outro erro é a sonda que falhou (`Failed`), e o comando continua sendo sucesso. Com -535 ("já há uma transação") **ela pergunta de novo**, depois de executar a leitura de verificação: o servidor também responde -535, sem transação nenhuma, logo depois de um `SELECT` em modo completo que falhou na primeira linha (divisão por zero, linha travada), porque o cursor dele ficou aberto do lado do servidor, e qualquer comando o fecha. Só a transação de verdade responde -535 outra vez (`InTransaction`); se a leitura do meio falha, a sonda falhou. As duas respostas que a sonda procura (-535 e -256) saem no log como depuração, e não como informação (`IsRoutineRefusal`, gancho da base): num banco sem log a segunda vem depois de cada comando. O número vem do `NativeError` do driver, guardado pelo `ToFailure` do Informix (`_lastNativeError`): o SQLSTATE dele é `IX000` para quase tudo, e o texto da mensagem não decide nada. O `sysmaster` não serve de sonda: só mostra a transação depois da primeira gravação. O comando que falha pode deixar a transação aberta: uma função que faz `BEGIN WORK`, grava, devolve linhas e lança (lançar antes de devolver linhas, ser interrompido na execução e o bloco seguido de `; BEGIN WORK`, que o servidor recusa com -535, não deixam). Por isso a sonda roda também depois do comando em modo completo que falhou com a conexão viva (`MayLeaveATransactionOpenWhenItFails`, ligado só no Informix): a transação é desfeita, e o log recebe "Um comando que falhou ou foi cancelado deixou uma transação aberta na conexão: ela foi desfeita.". A resposta do comando que falhou continua sendo o erro do banco. A do comando cancelado enquanto devolvia as linhas diria que o que ele gravou está confirmado, e o que ele gravou dentro da transação acabou de ser desfeito: ali a resposta é a recusa (`TransactionControlNotSupported`, 422 `TRANSACTION_CONTROL_NOT_SUPPORTED`, o mesmo código da rotina que termina sem ser cancelada), com o texto "O comando deixou uma transação aberta, e o Prism a desfez: nada do que ele gravou dentro dela ficou. ...". **Rede morta durante a sonda**: a resposta do comando que acabou de rodar fica presa até a rede voltar ou a conexão cair, porque o prazo de cinco segundos não limita uma chamada do driver bloqueada na rede; é limitação conhecida, da mesma família do abandono do PostgreSQL com a rede morta.
- **O driver é síncrono** (`BlocksTheCallingThread`): as chamadas `Async` só voltam quando o banco responde. O `Send` as roda em outra thread (`Task.Run`), menos o pedido de cancelamento, que não espera o banco. **Essa thread roda com a cultura invariável**: o driver escreve datas e números com a cultura da thread (com `ar-SA`, 2026-10-09 saía `1448-04-28`, e o `DECFLOAT` com a vírgula e os sinais árabes), e chega a lançar ao ler um `DECIMAL`.
- **Cancelar** (RN-SQL-010). O `Cancel` do comando que chega durante a execução lança (57014 no Db2, -213 no Informix), e o banco desfaz o comando. O que chega durante a leitura das linhas, ou com o cursor parado, fecha o cursor em silêncio: as linhas só param de vir, e nada no leitor diz que foi corte e não fim. Por isso `CancelReturnsEmptyResult` vale nos dois, com três respostas na base: a leitura (paginada, de catálogo, contagem) que voltou com a marca de cancelamento de pé responde "O comando foi cancelado."; o comando executado até o fim **sem linhas**, que já rodou no banco quando o leitor abriu sem exceção, é sucesso; e o comando executado até o fim **com linhas**, com o cancelamento pedido antes de a última sair, responde que o Prism não sabe se ele foi concluído, sem página e sem total (a função do Informix que grava a cada `RETURN ... WITH RESUME` ficava com parte gravada e confirmada, e o `FINAL TABLE` do Db2 com tudo gravado e o total cortado). No Informix, se a conferência depois desse comando acha uma transação que ele deixou aberta, ela é desfeita e a resposta é a recusa que diz isso, e não a de gravação confirmada (ver a rede de segurança, acima). O que terminou antes de o cancelamento ser pedido continua sendo sucesso. A marca vale enquanto o cursor do comando estiver aberto, inclusive no "carregar mais". **O `Cancel` do driver só interrompe o comando que já está executando no banco**: o pedido que chega um instante antes (o comando ainda está saindo da API) se perdia, e a consulta rodava até o fim. Por isso `IbmDatabaseConnection.ExecuteReaderAsync` (gancho da base) repete o pedido a cada 100 ms enquanto a execução não volta, na própria thread do temporizador; `Cancel_RightAfterTheCommandStarts_StopsIt_EveryTime` varre esse instante.
- **Células** (`ReadCell`, RN-SQL-011). `DECIMAL` e `DECFLOAT` saem em texto (`GetString`): o `decimal` do C# tem 28 dígitos, e com 31 o driver corta as casas ou lança. `TIMESTAMP` do Db2 sai do tipo do driver (`GetDB2TimeStamp`), com todas as casas: acima de 7 o `GetValue` lança. `DATE` sai só com a data. O resto é `GetValue` e o `CellFormatter`. O ponto decimal e o calendário vêm da cultura invariável com que o driver é chamado. No Informix `BOOLEAN` chega como número (0 ou 1) e `INTERVAL` chega inteiro, como texto (`123 04:05:06`, `2-03`). `DECIMAL` acima de 31 dígitos nem é entregue pela DRDA (-9275).
- **Catálogo.** No Db2, `SYSCAT`, com os nomes como estão (sem aspas ficam em maiúsculas); o nome de esquema com menos de oito caracteres vem completado com espaços (`RTRIM`). De sistema: `SYS%`, `NULLID` e `SQLJ`. No Informix "esquema" é o dono (RN-ARVORE-004): só os donos de tabela, visão ou rotina aparecem, e de sistema é o `informix`, dono do catálogo. **Tudo o que o usuário `informix` cria aparece como "sistema"**: quem conecta com ele e cria tabelas sem dizer o dono as vê no esquema de sistema, antes das `sys*`, e não num esquema próprio. O `CASE` de textos de tamanhos diferentes volta completado com espaços no Informix (`TRIM`). O tipo da coluna é decodificado de `coltype` e `collength` no próprio SQL.
- **Mensagem de erro** (RN-SQL-009): a de `DB2Exception.Errors`, com o prefixo que diz de onde veio (`[IBM][DB2/LINUXX8664]`, `[IBM][IDS/UNIX64]`, `[IBM][CLI Driver]`), e o SQLSTATE do primeiro erro. Não há posição. O número nativo do Informix (-206, -535) não faz parte do texto que o driver entrega, e a tela não o mostra. Para alguns números o driver troca o texto do Informix pelo do Db2 de mesmo número (-349 chega como "SQL0349N ... NEXT VALUE", e é "Database not selected yet").
- **String de conexão**: pelo `DB2ConnectionStringBuilder`, por propriedades, sem pool e com prazo de 15 segundos. **Host, senha, banco e usuário com `;` são recusados antes de o driver ser chamado** (`SettingsRefusal`, gancho da base): o driver separa os dados da conexão por `;`, as aspas do construtor não isolam o valor (a senha com `;` nunca conectava, e a resposta era "Invalid argument"), e a recusa diz qual campo, sem repetir o valor e sem ir para o log. Com aspas, apóstrofo, chaves, espaço, `=` e `@` o valor vai ao servidor como está; `banco@servidor` e `//host/banco` chegam como nome de banco. Nada além de host e porta escolhe o destino, e `ConnectionRules.SameServer` não mudou.
- **De onde o driver é carregado.** O assembly `IBM.Data.Db2` e a `clidriver` não estão ao lado da API: ficam na pasta do driver instalado, e quem os entrega ao .NET são os dois ganchos do `DriverPackageClient` (ver "Drivers sob demanda"). No Windows o próprio assembly da IBM acha a `clidriver` ao lado dele mesmo (`clidriver\bin\db2app64.dll`). **No Linux e no macOS** ele pede a biblioteca nativa só pelo nome (`libdb2.so`, `libdb2.dylib`): o construtor estático de `IbmDatabaseConnection` (`NativeLibrary.SetDllImportResolver`) a procura ao lado da API, onde ela ficava, não acha, responde "não sei", e a busca do .NET segue até o gancho `ResolvingUnmanagedDll`, que a carrega de `clidriver/lib` na pasta do driver, sem `LD_LIBRARY_PATH`. O resolvedor do construtor estático fica onde está: só pode haver um `SetDllImportResolver` por assembly. O que o sistema precisa ter é a `libxml2` (`libxml2.so.2`), que a imagem `runtime-deps` do .NET não traz: sem ela, abrir uma sessão de Db2 ou de Informix responde 422 com "Unable to load shared library 'libdb2.so' or one of its dependencies", e o PostgreSQL segue funcionando. Conferido no Ubuntu 24.04; não foi exercitado no macOS (arm64) nem numa distribuição que só traga a libxml2 2.14 ou mais nova (`libxml2.so.16`).
- **O que um comando do usuário faz com a própria sessão e o Prism não trata**: no Informix, `CREATE DATABASE x` e `DATABASE x` trocam o banco da sessão (a árvore continua mostrando o anterior), e `CLOSE DATABASE` a deixa sem banco: a sonda falha, a limpeza falha, e a base descarta a conexão (o driver nem consegue fechá-la; a sessão fica no servidor até a API encerrar). No Informix, `SET ISOLATION` (com `DIRTY READ`, `COMMITTED READ LAST COMMITTED` e `REPEATABLE READ`) e `SET TRANSACTION ISOLATION LEVEL` são aceitos e não valem para os comandos seguintes: pela porta DRDA o nível de isolamento de cada comando vem do driver, e não da sessão (a leitura de uma linha travada por outra sessão continua respondendo "record is locked" depois deles). `SET LOCK MODE TO WAIT` vale normalmente.

## Catálogo estendido e linhas por busca (Tarefa 29: RN-CAT-001 a 010, RN-SQL-016)

Tudo pela sessão, como as consultas de catálogo de antes: esperam a vez, valores como parâmetros, a recusa do banco no 422 `SQL_EXECUTION_FAILED` com a mensagem dele. Toda chave nova vem sempre no JSON, nula quando não se aplica; tabela, visão ou esquema que não existe responde lista vazia (ou `{ definition: null }`). Os textos que cada banco devolve estão afirmados, um a um, em `Infrastructure/Databases/{Postgres,Db2,Informix}CatalogTests` (com `CatalogContractTests` em comum): é o que a tela mostra. O que foi provado, por banco:

- **Linhas por busca** (`pageSize`, RN-SQL-016). Chega ao `ExecuteQueryCommand` como `JsonElement?`, para texto e número com casas virarem 422 `QUERY_INVALID` no campo `PageSize` pelo validator (lido como `int`, o MVC responderia 400 em outro formato); nulo vale como ausente (200). A conexão guarda o tamanho do cursor (`_pageSize`) e o "carregar mais" o usa; no caminho da RN-SQL-013 ele é o número de linhas da resposta, e o `TotalRows` continua o do comando. Os testes que não são sobre o tamanho executam pelo padrão por `DatabaseConnectionExtensions.ExecuteAsync` (TestingCore).
- **As três consultas de chave estrangeira têm as mesmas colunas** (`ForeignKeysSql`, `ReferencedBySql`, `DiagramForeignKeysSql`: nome, esquema e tabela que têm a chave, coluna, esquema, tabela e coluna referenciados, as duas regras) e cada banco as monta por um só `ForeignKeyColumnsSql(filtro)`. A base junta as colunas: por nome nas chaves de uma tabela, por nome mais esquema e tabela de origem no `referenced-by` (duas tabelas podem ter chaves de mesmo nome apontando para a mesma), por nome mais tabela no diagrama.
- **Padrão e geração** (RN-CAT-001). PostgreSQL: `pg_get_expr(adbin, adrelid, true)`, como o `psql` (`'abc'::text`, `CURRENT_TIMESTAMP`, `nextval('...'::regclass)` do `serial`, que não é coluna gerada); identidade por `attidentity` (do 10), calculada por `attgenerated` (`s`, do 12; `v` do 18), com a expressão no padrão. Db2: o `DEFAULT` como ele guarda (`'abc'`, `42`, `CURRENT TIMESTAMP`, `USER`); `GENERATED` `A`/`D`; a calculada traz o `TEXT` sem o `AS (` e o `)` de fora; a de data da última alteração da linha é "sempre" sem padrão. Informix: `sysdefaults`. **O padrão de número, data, hora e intervalo fica guardado como uma codificação do Informix, um espaço e o valor legível** (`AAAAKg 42`, `wQMyAAAA 3.50`, `xxQaAwQ 2026-03-04`): sai só o legível, a data entre aspas, a hora e o intervalo com o qualificador da coluna (`DATETIME (2026-03-04) YEAR TO DAY`); texto e `BOOLEAN` ficam como foram escritos, entre aspas, com a aspa de dentro dobrada; `C`/`U`/`T`/`S`/`N`/`R`/`D` viram `CURRENT <qualificador>`, `USER`, `TODAY`, `DBSERVERNAME`, `NULL`, `CURRENT_ROLE` e `DEFAULT_ROLE`. O `SERIAL`, o `SERIAL8` e o `BIGSERIAL` são "por padrão"; identidade e coluna calculada o Informix não tem.
- **Regras das chaves** (RN-CAT-002). PostgreSQL tem as cinco (`confdeltype`/`confupdtype`). Db2: ao excluir `A`, `C`, `N`, `R` (sem `SET DEFAULT`), ao atualizar só `A` e `R`; duas chaves de uma tabela para a mesma tabela com regras de exclusão diferentes são recusadas pelo próprio Db2 (SQL20255N). Informix: só `ON DELETE CASCADE`; o resto é `R` ("restrict"), também ao atualizar.
- **Método do índice** (RN-CAT-003). PostgreSQL: `pg_am.amname`. Db2: `INDEXTYPE` na palavra da documentação (`REG` regular, `CLUS` clustering, `BLOK` block, `DIM` dimension block, `CPMA` page map, `RCT` range-clustered key sequence, `TEXT`, os quatro de XML); código desconhecido sai como veio. Informix: `sysams.am_name` pelo `amid` de `sysindices`, e `btree (cluster)` no índice `CLUSTER`; `rtree` e `bts` pedem DataBlade ou espaço que a imagem não tem (`CREATE INDEX ... USING rtree` em `INTEGER` responde RTR20).
- **Conferência** (RN-CAT-005). PostgreSQL: `contype = 'c'` (do 18 o `NOT NULL` também tem linha, `n`), a condição por `pg_get_expr(conbin, conrelid, true)`, sem a palavra `CHECK`. Db2: `SYSCAT.CHECKS` com `TYPE = 'C'` (a coluna calculada cria uma `S`, que fica de fora), o `TEXT` como ele guarda. Informix: `syschecks` `type = 'T'`, reescrita por ele (`(preco > 0 )`), em pedaços.
- **Definição da visão** (RN-CAT-006). PostgreSQL: `pg_get_viewdef(oid, true)`, a consulta reescrita (sem o `CREATE VIEW`), também da materializada. Db2: o `TEXT` de `SYSCAT.VIEWS`, o comando exatamente como foi escrito. Informix: o `CREATE VIEW` que ele reescreve (palavras em minúsculas, dono entre aspas, apelido `x0`, sem as quebras de linha de fora dos textos) em pedaços `CHAR(256)` de `sysviews`, contados em bytes; **num banco UTF-8 o caractere que não cabe no fim de um pedaço vai inteiro para o seguinte e deixa um byte nulo** (provado no `prism_utf8` que o `InformixSingleton` cria): o `JoinChunks` do Informix tira o nulo do fim de cada pedaço e os espaços do fim do texto. Quebra de linha dentro de um texto da visão só com `EXECUTE PROCEDURE IFX_ALLOW_NEWLINE('t')` na sessão. O nome de dono com aspas sai na reescrita sem as aspas dobradas (`"Dono "M" 'x'"`): é o texto do banco.
- **Diagrama** (RN-CAT-008): duas consultas para o esquema inteiro (colunas e chaves). Medido com 300 tabelas e 400 chaves (contêineres na mesma máquina): PostgreSQL 18 em 48 ms, Db2 11.5.8 em 70 ms, Informix 14.10 em 1,3 s; de 175 a 180 KB de JSON. No Informix as colunas das chaves saem primeiro como números, numa tabela derivada, e os nomes entram depois pelo índice de `syscolumns`: casar pela expressão da posição, direto, levava três vezes mais.
- **Estimativa e comentário** (RN-CAT-009). PostgreSQL: `reltuples` (-1 é nunca analisada, do 14; no 12 e 13 é 0, e quem separa é a estatística da tabela, nunca coletada) e `obj_description`. Db2: `CARD` (-1 sem `RUNSTATS`) e `REMARKS`. Informix: `nrows`, que vale 0 até a primeira estatística, nulo quando `ustlowts` é nula; criar um índice grava a estatística da tabela como ela está (a `pedido` da carga, indexada vazia, mostra 0 com mil linhas até um `UPDATE STATISTICS`): é a estimativa do banco, velha ou não. O Informix não tem comentário de tabela.
- **Propriedades** (RN-CAT-010): uma lista de consultas por banco (`PropertiesSql`), rodadas em ordem; o valor nulo e a consulta que o banco recusa a esta conta ficam de fora, e a recusa só é a resposta com a conexão caída. PostgreSQL: `encoding`, `collation`, `ctype`, `sizeBytes` (só com o privilégio `CONNECT`, que o `pg_database_size` pede), `owner`, `tablespace`, `connectionLimit`. Db2: `codePage`, `codeSet`, `territory`, `collation`, de `SYSIBMADM.DBCFG` na partição da sessão (`PUBLIC` lê no 11.5 da imagem). Informix: `loggingMode` (`noLogging`, `unbufferedLogging`, `bufferedLogging`, `ansi`), `locale`, `owner`, `dbspace`, do `sysmaster`. As contagens de `…/schemas` usam as mesmas letras das listas de objetos.
- **Nomes de objeto no Informix**: num banco que não é ANSI o nome de tabela, de rotina e de restrição é único no banco inteiro, e não por dono (-310, -625 e "routine already exists"): os testes sorteiam os nomes que repetiriam.
- **Conta sem permissão de ler o catálogo**: no PostgreSQL, num banco só do teste com `REVOKE SELECT ON pg_catalog.pg_constraint FROM PUBLIC` (42501); no Db2, a conta comum do contêiner (`Db2Singleton.GetReaderSettingsAsync`) com `SYSCAT.CHECKS` tirado de `PUBLIC` durante o teste (SQL0551N). No Informix não dá para montar: o catálogo não aceita `REVOKE` (-511).
- **Bancos do servidor** (RN-ARVORE-006, `DatabasesSql`, rota `GET .../databases`): pela sessão, esperando a vez como o resto do catálogo. PostgreSQL: os de `pg_database` com `datallowconn`, sem `datistemplate` e com `has_database_privilege(oid, 'CONNECT')` (o superusuário tem em todos). Informix: `sysmaster:sysdatabases`, com `TRIM` (o nome é `CHAR`) e o da sessão por `DBINFO('dbname')`. Db2: só o banco da sessão, como o servidor o chama (`CURRENT SERVER`, em maiúsculas), porque ele conecta num banco por vez e não tem SQL que liste os outros da instância. A ordem de nome é a do banco, e a base (`CurrentFirst`, testada) põe o da sessão primeiro. Outro banco abre pelo `POST` de sessão com `database`: o handler troca só o banco nas credenciais da conexão gravada, e o nome segue pelo construtor da string de conexão de cada driver (no Db2 e no Informix o `;` continua recusado pelo `SettingsRefusal`). O `OpenDatabaseSessionValidator` recusa o nome vazio, com mais de 128 caracteres ou com caractere de controle (`DATABASE_NAME_INVALID`); sem o campo, vale o banco da conexão.

- **Índice de nomes** (RN-BUSCA-002, rota `GET .../object-names`): as tabelas e as visões de todos os esquemas do banco da sessão numa consulta de catálogo só, para a busca do navegador filtrar no app sem ir ao banco a cada tecla. Pela sessão, esperando a vez (`waitsForTurn: true`) como o resto do catálogo, sem parâmetro nem corpo (então sem validator; vale o `{id:guid}`), com a recusa do banco no 422 `SQL_EXECUTION_FAILED` e a sessão que não existe no 404. A resposta são os records `ObjectNamesInfo` e `SchemaObjectNamesInfo` da Infrastructure, como estão (handler de uma linha, `.MapError(DatabaseSessionErrors.From)`): só os esquemas que têm ao menos uma tabela ou visão, os comuns antes dos de sistema, cada grupo na ordem do banco, e os nomes exatamente como o catálogo os guarda (a chave da linha na tela e o `SELECT * FROM "esquema"."nome"` dependem disso: a base não apara nem normaliza nada). **Não é a lista de objetos**: não traz estimativa de linhas nem comentário (RN-CAT-009), nem rotina, coluna, índice ou chave. **Só o banco da sessão**: o PostgreSQL e o Informix não leem outro banco na mesma conexão, então o outro banco do servidor tem a sessão dele (RN-ARVORE-006) e o índice dele vem por ela; o Db2 só tem o banco da conexão.
- **Índice de nomes: o contrato com as listas e o limite.** Os tipos de objeto e o critério de sistema são os mesmos da lista de objetos e do `SchemasSql` (`TableKinds`/`ViewKinds` no PostgreSQL, `TableTypes`/`ViewTypes` no Db2 e no Informix; o `pg_`/`information_schema`, o `SYS%`/`NULLID`/`SQLJ` e o dono `informix`): a consulta do índice usa as mesmas constantes, e quem muda um tipo de objeto muda os dois lugares de uma vez. `CatalogContractTests.ObjectNames_AreWhatTheObjectListsShow` confere, nos três bancos, que em cada esquema as tabelas e as visões do índice são as de `objects?kind=tables|views`, nos mesmos nomes e na mesma ordem, e `ObjectNames_AreWhatTheObjectListsShow_InEverySchemaOfTheDatabase` confere o mesmo em TODOS os esquemas do banco (só os que têm tabela ou visão estão no índice, na ordem da lista dos esquemas); é isso que garante que a linha que a tela monta do índice é a que a árvore carregaria. **O limite** é `DatabaseSessionService.ObjectNamesLimit`, 50.000 nomes por banco (constante do serviço): a base lê `limit + 1` linhas (`ObjectNamesSql(int rows)`, e o número entra no texto como constante, em `LIMIT`, `FETCH FIRST n ROWS ONLY` ou `SELECT FIRST n`, nunca como parâmetro), a linha a mais liga `Truncated` e não entra na resposta, e o esquema que só tinha ela some. Como os de sistema vêm por último, o corte tira o catálogo primeiro; um esquema cortado no meio traz só os primeiros nomes, e `ObjectNames_WithAnyLimit_AreThePrefixOfTheWholeIndex` prova, nos três bancos e para limites de 1 até além do total, que a resposta cortada é o começo do índice inteiro (só o último esquema vem incompleto) e que o limite exato não corta.
- **Índice de nomes: a consulta de cada banco.** Todas devolvem, em linhas misturadas, esquema, se é de sistema, nome e tipo (`table` ou `view`), em ordem de esquema (os de sistema por último) e de nome; a base agrupa por esquema na ordem de chegada (`GroupBy`) e separa as tabelas das visões, que ficam na ordem relativa em que o banco as lista. O `RTRIM`/`TRIM` do esquema e do tipo tira os espaços com que o Db2 e o Informix completam o texto mais curto (no tipo, o de um `CASE`). PostgreSQL: `pg_class` com `pg_namespace`, `ORDER BY is_system, nspname, relname` (o tipo `name` ordena byte a byte, pela colação `C`, como a lista); o esquema `pg_toast` não aparece porque a tabela de `TOAST` e o índice têm outro `relkind`; a tabela particionada e a partição entram como tabela, a visão materializada como visão, e a sequência, o tipo composto e a tabela temporária da sessão (no `pg_temp_N`, de sistema, por último) seguem a lista. Db2: `SYSCAT.TABLES`, `ORDER BY is_system, TABSCHEMA, TABNAME`; **as tabelas do catálogo (`SYSCAT`) são visões do Db2 e entram em `views`**, e os apelidos (`ALIAS`) ficam de fora, como na lista; a tabela de consulta materializada (tipo `S`) entra como visão. Informix: `systables`, o dono como esquema, `SELECT FIRST n … ORDER BY 2, 1, 5, 3`, por posição como o `SchemasSql`; a quinta coluna (`catalog_order`) só existe para pôr as tabelas que alguém criou, a partir de `tabid` 100, antes das do catálogo dentro do `informix`, como a lista faz; o nome de tabela é único no banco inteiro, e não por dono (e divide o espaço com o de sequência e o de sinônimo: `CREATE TABLE` com o nome de uma sequência de outro dono é recusado), e o sinônimo e a sequência não entram. Custo: uma varredura do catálogo por banco, uns 25 bytes de JSON por nome com nomes de uns 20 caracteres (cerca de 1,2 MB no limite), e o driver da IBM, síncrono, ocupa uma thread enquanto lê as até 50.001 linhas. Medido: 5.000 tabelas e 500 visões num esquema saem em 26 a 72 ms no PostgreSQL 18, 40 a 100 ms no Db2 e 49 a 56 ms no Informix (3 chamadas seguidas, 44 a 51 KB de JSON); 50.000 tabelas e 5.000 visões no PostgreSQL, o limite, saem cortadas em 123 a 143 ms, 439 KB de JSON com nomes `t12345`, contra 1,7 s da lista de tabelas do mesmo esquema.
- **Índice de nomes: o que foi provado e o que não.** As três consultas rodaram nos bancos de verdade, pelos contêineres da suíte de integração (PostgreSQL 18 e as imagens fixas do Db2 e do Informix): os testes de catálogo e de rotas dos três (`CatalogTests` e `DatabaseSessionsTests`) passam, e o `CatalogContractTests` é a prova de que o índice é o que as listas de objetos mostram, em todos os esquemas e com os mesmos nomes na mesma ordem. Mudar a ordem, os tipos de objeto ou o critério de sistema da consulta do PostgreSQL derruba esses testes (das mudanças tentadas, só `LIMIT {rows + 1}` passa, e é equivalente: a base descarta o que passa do limite de qualquer jeito). **O que não foi provado**: 50.000 nomes no Db2 e no Informix (a medida acima é de 5.000 tabelas; na conta linear o Informix leva meio segundo, e montar 50.000 tabelas no Db2 levaria uns 20 minutos, porque 5.000 levaram 102 s); nomes com acento no Informix (o teste dele usa só ASCII, espaço e aspas); e uma recusa real do banco nesta consulta (a recusa mapeada tem o teste de unidade).

## Rotas de sessão, catálogo e consulta (`Prism.Application/DatabaseSessions`)

A porta HTTP do registro de sessões: `UserDatabaseSessionsController` (`api/user/database-sessions`) mais `POST api/user/connections/test` no `UserConnectionsController`. A barreira do cofre já as cobre (começam por `api/user/`), e nenhuma leva `[AllowAnonymous]`.

- **Handlers de uma linha.** Cada um chama o `IDatabaseSessionService` e traduz com `.MapError(DatabaseSessionErrors.From)`, sem `try` nem transação. A exceção são os que executam um comando na conexão (`queries`, `edit-target`, `edits` e `edits/preview`): antes, perguntam ao cofre se a conexão da sessão é somente leitura agora (`SessionProtections.IsReadOnly`, em "Proteções e verificação periódica"). `DatabaseSessionErrors.From` é a única tradução do `DatabaseFailure` para a API (seção 6 da especificação); o `detail` de `ConnectionFailed` e `ExecutionFailed` é a mensagem do banco, sem alteração, e `sqlState` e `position` entram como extensões só quando o driver os informa. `outcome` (`canceled`, `unknown`, `partial`) entra só em `SQL_EXECUTION_FAILED`, e `executed: true` só em `TRANSACTION_CONTROL_NOT_SUPPORTED` (ver "O desfecho do cancelamento e o `executed`"). `VaultChanged` devolve o mesmo 401 `VAULT_LOCKED` do `VaultErrors`.
- **Os DTOs** são `DatabaseSessionDto`, `QueryResultDto` com `QueryColumnDto`, `QueryCountDto` e, da edição, `EditTargetDto`, `EditChangeDto` e `EditsAppliedDto` (ver "Edição de registros"). Esquemas, objetos, colunas, índices, chaves estrangeiras e o catálogo estendido saem como os records públicos da Infrastructure (`SchemaInfo`, `DatabaseObjectInfo`, `ColumnInfo`, `IndexInfo`, `ForeignKeyInfo`, `ReferencingForeignKeyInfo`, `CheckConstraintInfo`, `ViewDefinitionInfo`, `SchemaDiagramInfo`, `DatabasePropertyInfo`, `ObjectNamesInfo` com `SchemaObjectNamesInfo`), que já têm os campos que a tela valida: um DTO igual a eles só duplicaria o contrato. O `QueryResultDto` é a mesma forma para página e para linhas afetadas, com nulo no que não se aplica (`columns` nulo é o que a tela lê como "linhas afetadas").
- **Os nomes de esquema e de tabela da rota não passam por `Uri.UnescapeDataString` no valor de rota.** O Kestrel decodifica o caminho menos o `%2F`: uma barra no nome (`a%2Fb`) e o texto literal `%2F` dele (`a%252Fb`) chegam iguais ao controller, e decodificar o valor de novo desfaz um `%41` que fazia parte do nome. O `PathName` do controller lê o alvo cru (`IHttpRequestFeature.RawTarget`), conta os segmentos a partir do fim e decodifica uma vez; as ações nem declaram `schema` e `table`. O teste `Columns_OfSchemaAndTableWithSlashSpaceAndQuotes_Return200` cria nomes com `/`, `%2F` e `%41` literais para provar isso: um "conserto" para o valor de rota o quebra. **Esquema ou tabela chamados `.` ou `..` são inalcançáveis por estas rotas.** O Kestrel tira esses segmentos (crus ou `%2E`) do caminho antes de rotear, e o alvo cru fica como chegou: o helper leria posições diferentes das que o roteador casou (`.../tables/segredo/../pedido/columns` casa `loja`/`pedido`). Por isso o controller é o próprio `IActionFilter` e responde 404 sem corpo, igual à rota que não casa (a seção 6 não tem código de erro para isto), a qualquer caminho com um segmento `.` ou `..` decodificado. Os testes usam socket cru (`Api/Support/RawHttp`), porque o `HttpClient` normaliza a URL antes de enviar; pontos dentro de um nome (`..x`, `...`) seguem valendo.
- **Abrir sessão** lê `IVaultService.Generation` antes de `GetRecordByID` e passa o valor ao `OpenAsync`; o registro de sessões é quem confere (`VaultChanged`). **Testar conexão** (RN-CONN-013) usa os campos do corpo e, sem `password` e com `id`, a senha do cofre, desde que host e porta sejam os gravados (422 `CONNECTION_INVALID` sem conectar, regra em "Dados do usuário no cofre"; 404 `CONNECTION_NOT_FOUND` se o `id` não existe, como a seção 6 lista); lê a geração antes e a confere depois, como a abertura. O corpo do formulário traz também nome, pasta e ambiente, que o comando ignora. **A conexão sem usuário ou sem senha** (a que a importação trouxe sem eles, RN-TRANSF-015) não chega ao registro de sessões: abrir sessão (também de outro banco do servidor) responde 422 `CONNECTION_CREDENTIALS_MISSING` na forma do erro de campo, em `UserName` sem usuário e em `Password` com o usuário e sem a senha (`ConnectionErrors.CredentialsMissingToConnect`), antes da recusa do driver não instalado, que é do registro; e testar com o `id`, sem senha no pedido e sem senha gravada, responde o mesmo código em `Password` ("Esta conexão não tem senha gravada. Informe a senha do banco para testar."), antes da conferência do servidor (RN-TRANSF-016). **Excluir conexão** fecha as sessões dela (RN-CONN-014) só depois de a exclusão estar gravada.
- `kind` ausente na rota de objetos vira vazio e cai no validator (`OBJECT_KIND_INVALID`); `[FromQuery] string kind` obrigatório responderia 400 do MVC, em outro formato. SQL vazio ou só de espaços é `QUERY_INVALID`, e o texto que passa vai ao banco sem ser aparado (RN-SQL-003). Regra de validator sem `WithErrorCode` vira 500.

## Edição de registros (seção 22: RN-EDIT-001 a 012, rotas `queries/edit-target`, `queries/edits`, `queries/edits/preview`)

Vale para os Registros de uma tabela e para o resultado da aba de consulta, **também de junção** (pedido do dono, 2026-10-14: o `SELECT` com junção do Informix que lê `pallets_items.*`): a edição vale coluna por coluna, na tabela de onde a coluna veio. A transação manual (RN-TX) e o nível de isolamento (RN-ISOL) ficam para a próxima rodada, que só acrescenta às mesmas rotas. Linha nova e excluir linha numa junção, a mesma tabela duas vezes, subconsulta e `WITH` no `FROM`, `NATURAL JOIN`/`USING` com `*` no Db2 e no Informix, o `OUTER (...)` com parênteses do Informix e sinônimos ficam só leitura ("Fica para depois" da seção 22).

- **O resultado da sessão.** Cada execução que devolve linhas vira um `ResultState` do registro de sessões (`DatabaseSessionService`): o `resultID` (Guid v7, muda a cada execução), a leitura do texto (`ResultSource`) e as colunas que o banco devolveu. A página (`queries` e `queries/next`) leva `resultID` e `editable` (`ResultEditability`: `{ known: false }`, ou `{ known: true, reason }` quando o texto já diz que o resultado inteiro é só leitura). O comando que rodou e não devolveu linhas tira o resultado; a recusa pelo texto antes de executar (controle de transação, vários comandos) o deixa. O comando executado até o fim que devolveu linhas (`TotalRows`) é "o comando gravou e devolveu linhas". Além do atual, a sessão guarda os resultados que a tela pede pela lista `keep` (as abas do script), e as três rotas da edição os aceitam: ver "Os resultados que o script guarda", abaixo.
- **A leitura do texto** (`EditableSql`, pura, com `EditableSqlTests`): o nível de fora do comando, com comentário, texto e identificador entre aspas lidos como cada banco os lê (os métodos de leitura do `SqlText` passaram a `internal` para isso). Recusa com o motivo da regra: não é `SELECT`, `WITH`, união, `DISTINCT` (e o `UNIQUE` do Informix), agrupamento, `FOR UPDATE`, `INTO`, subconsulta no `FROM` (também a de uma junção), sem `FROM`, e o que ela não reconhece ("o Prism não conseguiu saber de onde vêm as colunas": `ONLY`, `LATERAL`, função no `FROM`, três partes, `banco:tabela`, a junção entre parênteses, o `OUTER (...)` do Informix, a lista de nomes de coluna depois do apelido, a junção sem `ON`/`USING`). **O `FROM`** (`ResultSource.Tables`, cada um `FromTable`: o `EditTableName`, com os nomes já na regra de maiúsculas do banco e `Written`, o nome entre aspas para o `to_regclass`, e o apelido) é uma lista de `[esquema.]tabela [[AS] apelido]` ligadas por vírgula, `[INNER | LEFT | RIGHT | FULL [OUTER]] JOIN ... ON` ou `USING (...)`, `CROSS JOIN`, `NATURAL ... JOIN` e, só no Informix, `, OUTER tabela`. O `ON` vai até a próxima junção ou vírgula do nível de fora; `left(...)`/`right(...)` e o nome qualificado (`p.left`) não são junção. No Db2 e no Informix o `*` sobre `NATURAL`/`USING` deixa o resultado inteiro só leitura (a coluna da junção sai uma vez só); no PostgreSQL não, porque quem diz a origem é o banco. Cada item da lista do `SELECT`: `*`, `t.*`, `[t.]coluna [[AS] nome]`, ou calculado (número e palavra de valor, `NULL`, `CURRENT_DATE`, são calculados).
- **De onde vem cada coluna** (`EditTargetResolver`). No PostgreSQL o banco diz: `PostgresConnection.ColumnOrigins` lê `TableOID` e `ColumnAttributeNumber` de `GetColumnSchema()` **sem `CommandBehavior.KeyInfo`** (com ele o Npgsql abriria outra conexão para buscar o resto), e a origem vai em `QueryColumn.Origin`, que não chega à tela. Conferido contra o banco numa junção de três tabelas, na externa e na auto-junção (`PostgresEditTests`, pelo contrato): cada coluna traz a tabela dela, e a calculada vem com zero. **As tabelas do PostgreSQL saem desses identificadores** (`EditTables.Relations`, `EditRelationByIdQuery`), e a do `FROM` é a que tem o nome dela (e o esquema, quando o comando o escreveu): o caminho de busca que valeu foi o da sessão da aba, e não o da conexão do catálogo; a tabela do `FROM` de que nenhuma coluna vem é procurada pelo nome (`to_regclass`, no caminho de busca da conexão do catálogo). No Db2 e no Informix é a lista do `SELECT`, expandida pelo catálogo: `*` são as colunas de cada tabela na ordem do catálogo, tabela por tabela, na ordem do `FROM`; `t.*` e `t.coluna` pelo apelido, ou, sem apelido, pelo nome da tabela com ou sem o esquema; a coluna sem tabela é da única tabela que a tem (em duas, ou com uma tabela que o catálogo não achou, "a coluna sem tabela pode ser de mais de uma tabela do comando"; em nenhuma, calculada: `TODAY`, `USER`). O resultado tem de bater com ela (o número de colunas e o nome de cada uma); se não bate, ou um `*` passa por uma tabela que o catálogo não achou numa junção, o resultado inteiro é "o Prism não conseguiu saber de onde vêm as colunas".
- **O catálogo da edição** (`IDatabaseConnection.DescribeEditTablesAsync(EditTables)`): todas as tabelas do `FROM` numa chamada só (um `RunAsync`), e para cada uma três consultas (`EditRelationQuery`, por banco: o esquema, o nome, o tipo `table`/`view`/`materializedView`/`foreign`/`other`, o OID no PostgreSQL e, no Informix, o banco sem log pelo `sysmaster`; o `ColumnsSql` de sempre; e `EditKeysSql`, as chaves que servem: a primária, as restrições únicas e os índices únicos sem condição e só de colunas); a tabela escrita duas vezes do mesmo jeito é consultada uma vez. A tabela sem esquema é a do esquema atual (Db2, `CURRENT SCHEMA`), a do dono que o banco resolve, o usuário primeiro (Informix), ou a do caminho de busca (PostgreSQL, `to_regclass`, quando nenhuma coluna diz o identificador dela). O `edit-target` nunca consulta na sessão do resultado (o cursor dela continua aberto): vai na sessão da árvore (`catalogSessionID`: mesma conexão, mesmo banco, mesmo cofre, e diferente da do resultado), esperando a vez, ou numa conexão à parte com as credenciais da sessão e `LockTimeoutSql` (5 s), interrompida pelo "cancelar" e pelo fechamento da sessão como a contagem. O alvo fica guardado com o resultado.
- **O que se edita** (`EditTargetResolver`): cada tabela do `FROM` que é tabela, aparece uma vez só no `FROM` (pelo nome do catálogo: a mesma tabela duas vezes, ou duas de mesmo nome em esquemas diferentes, ficam "<tabela> aparece mais de uma vez no comando"; no PostgreSQL as duas ocorrências têm o mesmo identificador, e as colunas ficam com a primeira) e tem uma chave inteira no resultado como colunas DELA (a primária antes; só colunas não nulas); a coluna que vem de uma tabela que se edita e não é calculada, gerada sempre (`ColumnGeneration.Always`), binária, de tipo que o Prism não converte nem, numa junção (mais de uma tabela no `FROM`), coluna da chave escolhida ("coluna da chave numa junção"). `rowOperations` só no resultado de uma tabela só que se edita; `oneAtATime` quando alguma tabela diz. O `generated` de cada coluna é o do catálogo e, no PostgreSQL, `byDefault` também na coluna cujo padrão é `nextval(...)` (o `serial` e o `bigserial`, `GenerationOf`; seção 33): o "Duplicar linha" da tela não copia a coluna gerada "sempre" nem "por padrão", e o banco gera o valor da linha nova (RN-EDIT-016). Só no alvo da edição: as rotas do catálogo continuam a dizer essa coluna padrão, com `generated` nulo (RN-CAT-001). A coluna continua editável, e o `Same` a compara como as outras (o padrão tirado entre o `edit-target` e o Salvar é a tabela que mudou). A coluna de uma tabela que não se edita leva o motivo da tabela; numa tabela só que não se edita, também a calculada. `Same` compara o alvo de antes com o de dentro da transação, tabela por tabela e coluna por coluna.
- **A conversão por tipo** (`EditValues`, pura, com `EditValuesTests`): no PostgreSQL o texto vai num parâmetro **`NpgsqlDbType.Unknown`** (o banco o lê pelo tipo da coluna, como um literal na sessão), e todo tipo que não é binário se edita. No Db2 e no Informix o Prism converte, com a cultura invariável, do formato do `CellFormatter`: inteiros (com a faixa), decimal (`decimal` do C# até 28 dígitos; acima, o texto conferido vai como está), ponto flutuante, data (`DbType.Date`), hora (`DbType.Time`), data e hora (até 7 casas no `DateTime`; no Db2, de 8 a 12 casas, o texto `aaaa-mm-dd-hh.mm.ss.ffffffffffff`), lógico (`bool` no Db2; `t`/`f` no Informix, que pela DRDA entrega o lógico como 0 ou 1) e texto. No Informix, o texto de mais de 16.350 caracteres, que o driver da IBM manda como `CLOB` quando o parâmetro não tem tipo, vai como `LONG VARCHAR` enquanto cabe nos 32.767 bytes dele em UTF-8 (`InformixConnection.BindEditParameter`, que a carga da importação usa também): o Informix não converte `CLOB` nem `TEXT` em `LVARCHAR` ("No cast from text to lvarchar"), e o `LONG VARCHAR` entra no `LVARCHAR`, no `TEXT` e no `CLOB`; o maior segue como `CLOB`, que só o `TEXT` e o `CLOB` guardam. No Db2 o mesmo texto entra no `VARCHAR` como o driver o manda, e nada muda. Intervalo, objetos grandes, coleções, XML e o `DATETIME` do Informix que não começa por `YEAR` (ou não é `HOUR TO SECOND`) ficam só leitura. Os tipos provados contra os três bancos estão em `*EditTests.TypeSamples`, e a leitura de volta é o mesmo texto escrito.
- **Os comandos** (`EditPlanner`, pura, com teste): exclusões, alterações e linhas novas, cada grupo na ordem do pedido; a alteração e a exclusão pela chave da tabela dela (`change.table`), com os valores que a grade leu: numa junção, as alterações de uma linha da grade em duas tabelas chegam como duas, e viram dois `UPDATE`. A linha repetida da grade (a mesma chave) é uma alteração só: quem junta é a tela. Os nomes entre aspas duplas, a aspa dobrada; os valores em parâmetros (`$n` no PostgreSQL, `?` no Db2 e no Informix). O "Ver SQL" é o mesmo comando com os literais (`EditValues.Literal`), e `?` com o valor em `values` quando há caractere de controle. A recusa antes do banco é `EditInvalid`, com `Change` (a posição no pedido) e `Column`: a coluna que não se edita, a de outra tabela ("A coluna não é da tabela da alteração."), a chave com valor nulo (a junção externa sem linha), a linha nova e a exclusão sem `rowOperations`.
- **O Salvar** (`AdoDatabaseConnection.ApplyEditsAsync(EditTables, ...)`): dentro de um `RunAsync` (o cursor anterior fecha; o "cancelar" alcança o comando em andamento). Com transação, ela é **a do driver** (`BeginTransactionAsync`, nos três; no Db2 é ela que tira a conexão do auto-commit, e no Informix com log ela vale pela DRDA) e fica em `_editTransaction`, à parte do `_inTransaction` da leitura paginada: o `FinishCursorAsync` das consultas de catálogo de dentro do Salvar não confirma nada. Todo comando entra nela (`command.Transaction`): os `UPDATE` de todas as tabelas de um Salvar são uma transação só. O catálogo de todas as tabelas é consultado dentro dela e entregue ao plano; cada comando tem de afetar exatamente uma linha (`EditRowMismatch`, com `RowsAffected`); a recusa do plano ou da contagem desfaz pelo mesmo fim do cursor abandonado (`TransactionEnd` desfaz a transação do driver; se o `ROLLBACK` não passa com a conexão viva, ela fecha). A transação sai do campo antes do `COMMIT`. No Informix sem log (`OneAtATime`) não há transação: cada comando é confirmado sozinho, o Salvar para no primeiro que falha, e a recusa leva `Applied`. O alvo de dentro diferente do de antes diz a primeira tabela que mudou (`TableChanged`).
- **As rotas** (`UserDatabaseSessionsController`, handlers de uma linha, `EditChangeRules` no validator: `resultID` e ao menos uma alteração, com `kind` de `update`, `delete`, `insert` ou, da seção 38, `updateAll`, senão 422 `EDIT_INVALID` no campo): `edit-target` responde `EditTargetDto` (sem o tipo de catálogo da coluna); `edits`, `{ applied }`; `edits/preview`, o `EditPreview`. Recusas (`DatabaseSessionErrors`): 409 `RESULT_CHANGED` (o resultado não é o atual nem um guardado, ou a tabela mudou desde o `edit-target`, ou o esquema atual leva a outra, ou, no Db2 e no Informix, a tabela sem esquema de um guardado depois de um comando que pode trocar o esquema), 422 `RESULT_NOT_EDITABLE` com `reason`, `EDIT_INVALID` com `change` e `column`, `EDIT_ROW_MISMATCH` com `change` e `rowsAffected`, `SQL_EXECUTION_FAILED` com `change` (a mensagem do banco, como veio), e `applied` no banco sem log. O `transaction` da resposta da seção 22 é da transação manual e entra com ela.
- **O alvo para o "Gerar SQL"** (seção 37, RN-GRADE-020). O `edit-target` aceita `purpose` (`GetEditTargetCommand.Purpose`, `string?`): ausente, nulo ou `edit` é o de sempre; `sql` é o pedido do "Gerar SQL" e do "Copiar como" do SQL e do DbUnit; outro valor é 422 `EDIT_INVALID` no campo `Purpose` (`EditChangeRules.MustBeAPurpose`, com a frase "O pedido (purpose) deve ser edit ou sql."). Numa conexão comum os dois pedidos são o MESMO alvo, o guardado com o resultado. Numa conexão somente leitura o `edit` continua recusado com `CONNECTION_READ_ONLY` antes de ir ao banco, e o `sql` vai a `IDatabaseSessionService.GetReadOnlyEditTargetAsync`: o alvo resolvido como o da edição (as mesmas recusas: `RESULT_NOT_EDITABLE` com o `reason`, `RESULT_CHANGED`), passado por `EditTargetResolver.ReadOnly` (todas as tabelas e colunas com `editable` falso e o motivo `ReadOnlySql.ResultReason`, "a conexão é somente leitura", e `rowOperations` falso; a `Key` fica como estava) e **não guardado** (`TargetOfAsync` com `keep: false`): o "Salvar" segue recusado ali, e o `edit-target` da edição, quando a conexão deixa de ser somente leitura, consulta o catálogo de novo. O alvo que a edição já guardou serve a ele, sem consulta. Cada tabela de `tables` ganhou `kind` (`EditTableKind`: `table`, `view`, `materializedView`, `foreign`, `elsewhere`, e `other` para o que o catálogo não acha, ou de tipo que ele não conhece) e `keyColumns`: os nomes, na tabela, das colunas da chave que a edição usa (a que `KeyOf` achou), ou, sem ela, as da primeira candidata (`CandidateKeys`: a primária antes, só de colunas não nulas), também a que não está inteira no resultado, a de coluna binária que a edição pula e a da tabela que aparece duas vezes no `FROM`; vazia sem chave nenhuma e fora de uma tabela. É por ela, e não pela `Key` (que vem vazia quando falta uma coluna ou quando a chave tem coluna que a edição não converte), que a tela acha a chave do SQL. **As visões** já vinham com as colunas ligadas a elas (`table` 0, o `baseColumn` da visão, só leitura com "<visão> é uma visão"): no PostgreSQL pelo `TableOID` e o número da coluna da descrição das linhas, que são os da visão (também na coluna com apelido e na que a visão calcula); no Db2 e no Informix pela lista do `SELECT`. O `Same` do "Salvar" não compara o `kind` nem o `keyColumns`: o que a edição usa já está na `Key`, no `editable` e nas colunas.
- **Testes**: unidade em `Databases/EditableSqlTests` (as formas de junção, o `, OUTER` do Informix, o comando do dono, e os de fora), `EditValuesTests`, `EditTargetResolverTests` (a junção no PostgreSQL pelo identificador, no Db2 e no Informix pela lista, a tabela repetida, a coluna sem tabela, o sinônimo numa junção, o `nextval` do PostgreSQL "por padrão"; e, da seção 37, o `kind` e o `keyColumns` de cada caso, as colunas da visão e o `ReadOnly`), `EditPlannerTests` (um `UPDATE` por tabela), `DatabaseSessions/EditHandlersTests` (com `DatabaseSessionErrorsTests`; o `purpose` aceito e recusado, o `sql` na conexão somente leitura e na comum) e `Databases/DatabaseSessionServiceReadOnlyTargetTests` (o alvo do "Gerar SQL" que não se guarda, o guardado que serve a ele, o resultado lido na conexão somente leitura, que responde as tabelas e, desmarcada ela, a edição, e a união dela, que continua `RESULT_NOT_EDITABLE`); integração no contrato `Infrastructure/Databases/DatabaseEditContractTests`, pelo registro de sessões, com `PostgresEditTests` (também o cursor que continua aberto, a sessão da árvore, e o `serial`, o `bigserial` e a identidade "por padrão" no alvo, com o catálogo que segue dizendo padrão), `Db2EditTests` e `InformixEditTests` (também o banco sem log, a junção `, OUTER` e o `LVARCHAR` de 20.000 caracteres): o contrato tem as tabelas `pallets`, `items` e `pallets_items` do pedido do dono e prova a junção de três que lê `pallets_items.*`, as duas tabelas editadas na mesma linha (dois `UPDATE` no "Ver SQL" e no Salvar, e a linha repetida relida com o valor novo), a junção externa sem linha e a tabela que aparece duas vezes. Da seção 37, no contrato: o `kind` e o `keyColumns` das tabelas de sempre (`EditTarget_TellsTheKindAndTheKeyColumnsOfEachTable`), as colunas da visão com apelido (`EditTarget_OfAView_LinksItsColumnsByTheColumnsOfTheView`) e as condições que o "Gerar SQL" escreve rodando nos três servidores (`GeneratedSql_TheConditionsOfEachItem_FindTheRightRowsOnTheServer`, na tabela `composta`: o `OR` de `AND`s, o `IN` de uma coluna, o `IS NULL` sem chave e, só no PostgreSQL, a lista de linhas no `IN`, `AcceptsRowListInIn`). As rotas em HTTP em `Api/DatabaseSessionEditsTests`, e o `purpose: sql` na conexão somente leitura em `Api/ReadOnlyDatabaseSessionsTests.ReadOnlyConnection_AnswersTheTargetOfTheGeneratedSql_WithoutKeepingItForTheSave`. Cada teste do contrato fecha no fim as sessões que abriu (`CloseSessionsAsync`), e o fim da classe descarta o registro mesmo quando o `DROP` falha: o Informix Developer Edition aceita 25 conexões no servidor inteiro, e as sessões do contrato abertas até o fim da classe, com as que outra classe deixa, passavam dele.

## Os resultados que o script guarda (seção 33: RN-SQL-024, campo `keep` de `queries`)

Cada aba de resultado que o "Executar script" (Alt+X) mantém se edita como a do último comando (RN-SQL-023). A API guardava um resultado só por sessão (o atual, com o cursor), e o comando seguinte o substituía; agora ela guarda também o que a edição precisa dos resultados que a tela pede, pelo `resultID`.

- **O pedido** (`ExecuteQueryCommand.Keep`, `JsonElement?` como o `PageSize`): a lista dos `resultID` que a aba continua mostrando depois deste comando, até 20 (`QueryPaging.MaxKeptResults`, o teto da RN-SQL-020). O `ExecuteQueryValidator` recusa com 422 `QUERY_INVALID` no campo `Keep` a lista de mais de 20, a entrada que não é um identificador em texto (nula, número, texto qualquer) e o `keep` que não é lista; ausente, nulo ou vazio passa. `KeptResults()` tira os repetidos. O handler chama a sobrecarga de `ExecuteAsync` com `keep`; as de antes passam a lista vazia (são as dos testes).
- **O que a sessão guarda** (`Session.Kept`, um dicionário trocado inteiro, com a vez tomada, e lido pelo `edit-target` e pelo "Ver SQL" sem a vez): o próprio `ResultState`, que já era só o que a edição precisa (a leitura do texto, as colunas com a origem do PostgreSQL e o alvo, quando já perguntado), sem as linhas, que nunca estiveram nele. Os valores completos das células cortadas (`Cells`) saem quando ele deixa de ser o atual (`ReplaceResult`), e o cursor é da conexão, do atual. Morre com a sessão (`Session.Close` o esvazia).
- **Quando a lista vale** (`Keep`, chamado no `ExecuteAsync` antes de o atual ser trocado): no comando que foi ao banco, a mesma condição que tira o resultado atual (sucesso, `ExecutionFailed`, `Executed`). Ficam, entre o atual e os já guardados, os da lista; os outros saem; o identificador que a sessão não conhece é ignorado. A recusa antes do banco (o filtro, o somente leitura, o controle de transação sem `executed`, a sessão ocupada) não muda nada.
- **As rotas da edição** (`EditableResult`): `edit-target`, `edits/preview` e `edits` acham o atual ou um guardado; o resto é `ResultChanged` com "O resultado não está mais guardado na sessão: outro comando foi executado nela depois dele. Execute o comando de novo para editar." O "Salvar" de um guardado é um `RunAsync` como o do atual: toma a vez (`SESSION_BUSY`), fecha o cursor do atual (`DisposeCursorAsync` da base) e não troca nada (o atual continua o atual, com os valores completos; os guardados continuam guardados). Quem diz à tela que o cursor do último fechou é a própria tela (RN-SQL-023).
- **A tabela sem esquema no Db2 e no Informix.** O driver da IBM não diz o esquema atual sem uma consulta, e perguntá-lo a cada comando seria a consulta a mais da RN-EDIT-010. A sessão conta (`Session.SchemaChanges`) os comandos que foram ao banco e podem trocar a resolução de um nome sem esquema (`EditableSql.MayChangeTheCurrentSchema`: começam, depois dos comentários, dos `;` e dos parênteses, por `SET`, `CALL` ou `EXECUTE` e, no Informix, `DATABASE`; no Db2, em qualquer das duas leituras do comentário de bloco), e cada `ResultState` guarda o número de quando foi lido. O guardado com uma tabela do `FROM` sem esquema e um número menor responde `ResultChanged` com o detalhe próprio ("Um comando executado depois deste resultado (como um SET ou um CALL) pode ter trocado o esquema atual da sessão, e <tabela>, escrita sem esquema, pode ser outra tabela agora..."), sem consultar nem executar nada. O atual nunca tem comando depois dele. No PostgreSQL não conta: a origem é a tabela pelo OID, e o resto é a conferência de sempre (a tabela que sumiu deixa as colunas só leitura; o alvo já perguntado é conferido dentro da transação do "Salvar").
- **O nome sem esquema no PostgreSQL** (a RN-SQL-024: o guardado edita a tabela que leu, e o `SET search_path` depois dele que leva o nome a outra tabela deixa as colunas só leitura). O catálogo acha a tabela do `FROM` pelo OID que a resposta do comando dá, e o nome escrito sem esquema não diz nada fora da sessão do resultado: o `edit-target` vai à sessão da árvore ou a uma conexão à parte (RN-EDIT-010, nunca à do resultado, que pode ter o cursor aberto), com outro caminho de busca. Quem confere é o "Salvar", que roda na própria sessão: dentro da transação, `DescribeCoreAsync(inTheSession: true)` pergunta a que tabela o nome leva AGORA (`to_regclass`, pelo `EditRelationQuery`), e a tabela achada pelo OID a que ele não leva mais (outra, ou nenhuma) vem como `EditCatalogTable.Elsewhere`: o resolvedor a deixa só leitura ("<tabela>, escrita sem esquema, leva agora a outra tabela na sessão"), o alvo de agora não é o de antes, e o "Salvar" responde 409 `RESULT_CHANGED` com "A tabela <nome> mudou desde a consulta…", sem gravar nada. A tabela com o esquema escrito não é conferida. **Limite**: a primeira pergunta do alvo pelo `edit-target` não vê o caminho de busca da sessão do script, então as colunas aparecem editáveis e a recusa vem no "Salvar"; a regra diz que já a primeira pergunta as deixa só leitura, o que pediria o catálogo na sessão do resultado (contra a RN-EDIT-010). Só a conferência de dentro da transação do "Salvar" vê o caminho de busca da sessão; o alvo que o "Salvar" sem `edit-target` antes pergunta na própria sessão (`DescribeEditTablesAsync`) também acha a tabela pelo OID, e a recusa vem da conferência, como no alvo já perguntado.
- **Testes**: unidade em `DatabaseSessionValidatorsTests` (o `keep` aceito e recusado), `ExecuteQueryHandlerTests` (a lista vai ao registro sem repetir; o matcher `NoKeep` é a lista vazia), `EditableSqlTests` (`MayChangeTheCurrentSchema` nos três dialetos e nas duas leituras do Db2) e `Databases/DatabaseSessionServiceKeptResultsTests` (parte do `DatabaseSessionServiceTests`, com o `EngineClient` de cada banco e a conexão de mentira que ganhou o catálogo da edição e o "Salvar": o guardado que se edita e o "Salvar" que fecha o cursor do atual, a lista que esquece, a que vale no comando que falha e no desfeito com `executed`, e não na recusa, os valores completos que não ficam, a guarda da tabela sem esquema), `AdoDatabaseConnectionEditTablesTests` (parte do `AdoDatabaseConnectionTests`: o nome sem esquema conferido só no "Salvar", na própria sessão) e `EditTargetResolverTests` (o `Elsewhere` só leitura); integração em `Api/DatabaseSessionEditsTests.Edits_OfAKeptResult_FollowTheRoutesOfSection33` (HTTP, PostgreSQL: o guardado editado, o "carregar mais" do atual que fecha, o 422 do `keep` e o 409 com o texto novo), `Save_OfAKeptResult_IsRefused_WhenTheUnqualifiedNameNowLeadsToAnotherTable` (o `SET search_path` depois do guardado: 409 no "Salvar", nada gravado nas duas tabelas) e no contrato `DatabaseEditContractTests.Edits_OfAKeptResult_AreSavedAfterAnotherCommand` (os três bancos).

## A coluna inteira (seção 38: RN-EDIT-018 a 023, rota `queries/edits/count` e a alteração `updateAll`)

A edição da coluna inteira é UMA alteração (`EEditKind.UpdateAll`, `{ kind: "updateAll", table, set: [{ column, value }], rows }`) que vale para todas as linhas que o comando do resultado devolve no momento do "Salvar". A forma do SQL é da API, pelo comando e pelo banco (`WholeColumnSql`, pura, com `WholeColumnSqlTests`); a tela só manda a alteração.

- **O comando de cada resultado** (`ResultState.Sql`): o texto como a API o executou (`sent`, com o filtro do resultado já junto, RN-GRADE-011), só na memória, também nos guardados do script (RN-SQL-024), nunca no disco nem no log. O `<Q>` é ele limpo (`WholeColumnSql.Cleaned`): sem os `;` das pontas e sem o que o leitor do comando (`EditableSql.Lex`) acha depois do último pedaço de código (comentário, espaço; também antes do primeiro). Ele entra sempre seguido de uma quebra de linha, para um `--` no fim não engolir o resto. A tela não manda o comando de volta.
- **As três formas** (RN-EDIT-020). **Direta**: o `SELECT` de uma tabela só, sem apelido e sem limite de linhas no nível de fora, em que o texto depois do nome da tabela é, por inteiro, `[WHERE <condição>] [ORDER BY <lista>]` (com uma lista de palavras que, no nível de fora da condição ou da ordem, levam à outra forma: `WITH UR`, `FOR ...`, `OPTIMIZE`, `OFFSET`, `TABLESAMPLE`, `ONLY`, `INTO` e as das outras cláusulas); o comando refeito com as partes é conferido, pedaço por pedaço (a palavra sem diferença de maiúsculas), contra o `<Q>`, e no Db2 as duas leituras do comentário de bloco têm de ver os mesmos pedaços. `SELECT COUNT(*) FROM "s"."t" WHERE <condição>\n` e `UPDATE "s"."t" SET "c" = ? WHERE <condição>\n`, a condição como a pessoa a escreveu, e sem `WHERE` quando o leitor provou que não há um no nível de fora. **Pela chave**, nos outros: `SELECT COUNT(*) FROM (\n<Q>\n) AS "q"` e o `UPDATE` pela chave da tabela, cada coluna dela pelo nome que ela tem NO RESULTADO e SEMPRE com `"q".` (uma coluna: `WHERE "id" IN (SELECT "q"."codigo" FROM (...) AS "q")`; várias: `UPDATE "s"."t" AS "u" ... WHERE EXISTS (SELECT 1 FROM (...) AS "q" WHERE "q"."a" = "u"."a" AND ...)`, porque o Informix recusa o `IN` de várias colunas). **Sem o `"q".` a coluna que o `<Q>` não devolve é procurada na tabela do `UPDATE`, sem erro, e o `IN` casa com todas as linhas**: `Probe_TheUnqualifiedKeyInTheDerivedTable_MatchesEveryRow_AndTheQualifiedOneIsRefused` refaz isso nos três bancos (3 linhas alteradas, e não 2), e o "conserto" de tirar o `"q".` apaga a proteção. **Por lotes** (só no Informix, com `LIMIT`, `OFFSET` ou `FETCH` no FIM, no nível de fora, que a tabela derivada dele recusa com -201): a contagem lê as chaves do próprio `<Q>` (`ReadKeysAsync`, os textos como a grade os escreve, o cortado inteiro), até 1.000.000 (a linha seguinte é a recusa `EDIT_ALL_ROWS_NOT_SUPPORTED`), e o "Salvar" as lê de novo dentro da transação e altera em lotes de até 1.000 (`WholeColumnPlan.Batches`: `IN (?, ...)` com uma coluna, `OR` de pares com várias, as chaves convertidas como as da edição por linha). O `LIMIT` logo depois do `SELECT` do Informix (`SELECT LIMIT 5 * ...`) é como o `FIRST` e o `SKIP`: a tabela derivada o aceita (sonda S-COL-1), e ele vai pela chave. Os nomes entre aspas duplas, a tabela com o esquema do catálogo (no Informix, o dono), os valores em parâmetros convertidos como os da edição por linha (`EditPlanner.Writer`, `$n` no PostgreSQL, `?` nos outros), várias colunas num `SET` só.
- **As recusas antes do banco** (`WholeColumnSql.Plan`, na ordem da RN-EDIT-018): `EDIT_INVALID` com `change` (e `column`) para a tabela que não existe ou não se edita, o `set` vazio ou com a coluna repetida, a coluna fora do resultado, de outra tabela ou que não se edita, o valor que não converte, a segunda `updateAll` (`Find`) e, no "Salvar", o `rows` que falta ou não é um inteiro de 0 em diante (o `rows` chega como `JsonElement?`; o que não é inteiro vira -1 no `ToChanges`); `EDIT_ALL_ROWS_NOT_SUPPORTED` (`EDatabaseFailure.EditAllRowsNotSupported`, 422, com `change`, `reason` e, quando é de uma coluna, `column`) para o `rowOperations` falso (a junção), a coluna da chave, a chave com o nome repetido no resultado, o comando que não é leitura (o `read` da página e o `ReadOnlySql` de uma leitura só sobre o `<Q>`), o limite de linhas sem `ORDER BY` no mesmo nível (no de fora e em cada parêntese: `LIMIT`, `OFFSET`, `FETCH FIRST`/`NEXT` e, no Informix, `SKIP`, `FIRST`, `LIMIT` e `MIDDLE` da cabeça com um número depois; a palavra qualificada, `p.limit`, não conta), o `TABLESAMPLE` e, na leitura das chaves, mais de 1.000.000. As frases do `reason` são as da regra, como a tela as mostra.
- **A contagem** (`POST .../queries/edits/count`, `CountWholeColumnCommand`, resposta `{ rows }`): `changes` só com a `updateAll` (`OnlyOne`: outra alteração é `EDIT_INVALID` com o `change` dela; nenhuma, sem `change`). Na sessão do resultado, como o "Salvar": toma a vez (`SESSION_BUSY`), fecha o cursor aberto, e o `queries/cancel` a interrompe (`outcome`). Dentro do comando (`IDatabaseConnection.CountWholeColumnAsync`), a conferência do catálogo na própria sessão (`DescribeCoreAsync(inTheSession: true)`, a tabela que mudou e o nome sem esquema que leva a outra são o `RESULT_CHANGED` do `TableChanged`), depois a contagem: no PostgreSQL, na transação só de leitura (`BEGIN READ ONLY`, confirmada no fim); no Db2 e no Informix, sem transação. Na conexão somente leitura, o handler recusa antes (`CONNECTION_READ_ONLY`).
- **O "Ver SQL"** (`queries/edits/preview`): a contagem e o `UPDATE` da coluna inteira vêm antes dos comandos por linha, com os valores como literais. `EditStatement.Note` (`note` no JSON, ausente quando nula, `JsonIgnoreCondition.WhenWritingNull`): a contagem leva "A contagem confere, antes do UPDATE, que o comando ainda devolve as linhas confirmadas."; no caminho por lotes, o primeiro comando é o `<Q>` (que lê as chaves), com a mesma nota, e o segundo é o `UPDATE` do primeiro lote com `?` no lugar das chaves (`IN (?, ?, …)`), com "As chaves vão em lotes de até 1.000."; os `values` dele são só os do `SET` que não têm literal.
- **O "Salvar"** (`AdoDatabaseConnection.ApplyEditsAsync(tables, oneAtATime, wholeColumn, plan)`, com `EditPlan(WholeColumn, Commands)`): o plano é o mesmo do de antes, mais a coluna inteira, que vai PRIMEIRO, depois da conferência do catálogo: a contagem (ou a leitura das chaves) tem de dar o `rows` (senão 409 `RESULT_CHANGED` "O resultado mudou desde a contagem: o comando devolve agora N linhas, e não as M confirmadas. ...", e nada é executado); o `UPDATE` (ou a soma dos lotes, cada um com as linhas das chaves dele, parando no que difere) tem de alterar exatamente o `rows` (senão `RESULT_CHANGED` "... o comando alterou N linhas, ..." com a dica do gatilho, e tudo é desfeito). Os comandos da coluna inteira vão pelo envio do banco (`RunCountedAsync`, `ExecuteReaderAsync` e `RecordsAffected`), em que o driver da IBM repete o pedido de cancelamento. No driver da IBM, o comando interrompido dentro da transação do driver (a do "Salvar" e a da carga) pode chegar sem o erro da interrupção: no Informix não traz o -213; no Db2 o 57014 some quando o `Cancel` chega em dobro (o do registro do `CancellationToken` no `ExecuteReaderAsync` do ADO.NET e o do `Cancel` da base), 3 de 40 na sonda da trava, e nunca com um `Cancel` só nem em auto-commit (a consulta, a contagem). A exceção vem sem nenhum erro ("ERROR - no error information available"), e `IbmDatabaseConnection.CameWithoutErrorInformation` (gancho da base, que o `IsInterruption` dos dois bancos lê) a conta como interrupção (com o pedido de cancelamento, `outcome: canceled`; sem ele, o `WithTheCancelOutcome` a deixa um erro comum, sem desfecho). Na sonda do Db2, depois dela o banco já tinha encerrado o comando (a espera sumiu do `SYSIBMADM.MON_LOCKWAITS` com a trava ainda presa pela outra sessão), o que a transação tinha antes dele continuava nela, e o `ROLLBACK` do "Salvar" passava: nada da coluna inteira fica, e a sessão segue servindo. A coluna inteira conta como uma alteração em `applied`. **No PostgreSQL** a transação do "Salvar" com a coluna inteira é Repeatable read (`WholeColumnIsolation`, gancho da base; nulo no Db2 e no Informix, que ficam no nível do banco): a linha que outra sessão mudou depois do retrato é a recusa 40001, como veio. O cancelamento que chega depois do último comando não desfaz nada (`_executed` sobe antes do `COMMIT`, como no `CommitLoadAsync`). **Sem log** (`OneAtATime`): a contagem que difere não grava nada; o `UPDATE` que altera outro número fica gravado, e a resposta é 422 `EDIT_ROW_MISMATCH` com `change`, `rowsAffected` e `applied` 1; qualquer falha do `UPDATE` da coluna inteira (ou de um lote), também o cancelamento, é `SQL_EXECUTION_FAILED` com `outcome: unknown` e `applied` 0 (`writingTheWholeColumn`); a falha de uma alteração por linha depois dela leva `applied` contando a coluna inteira. O prazo de espera de trava da sessão da aba não muda (a espera é a do banco, e a saída é o "Cancelar"). O log do registro de sessões diz os IDs e o número de linhas da coluna inteira, nunca o comando, os nomes nem os valores.
- **O teto do corpo**: 32 MiB (`UserDatabaseSessionsController.MaxEditRequestBytes`, `[RequestSizeLimit]`) nas três rotas da edição (`edits`, `edits/preview`, `edits/count`), acima dos 30 MB do Kestrel; acima dele a requisição é recusada antes do handler, com o 500 do defeito conhecido de toda rota que lê corpo.
- **O `transaction` da resposta** da seção 6 (`{ rows, transaction }`, `{ applied, transaction }`) é da transação manual e entra com ela, como no "Salvar" de antes. O Commit manual não existe no código: a contagem e o "Salvar" no ponto de salvamento da aba, e o cancelamento que desfaz só ele (a parte da RN-EDIT-021 e 023 que fala dele, e as sondas S-DB2-7 e S-IFX-5), entram com ele.
- **O que a sonda S-COL-1 provou** (testes de integração, 2026-10-19, PostgreSQL 18, Db2 12.1, Informix 14.10 com log e sem log): o `EXISTS` com `"u"` e a tabela com o esquema ou o dono, nos três; o `UPDATE` que altera a coluna que a condição usa, nas formas direta e pela chave, altera as linhas que a condição achava antes dele; os nomes repetidos em colunas que não são da chave (`SELECT id, status, status`) passam na tabela derivada dos três, na contagem e no `UPDATE`; o `LIMIT … OFFSET` do Db2 dentro da tabela derivada do `UPDATE` vale; o `LIMIT` da cabeça do Informix dentro dela vale, e o do fim, o `OFFSET` e o `FETCH` não (-201). A trava de outra sessão faz o "Salvar" esperar nos três (no Informix, depois de `SET LOCK MODE TO WAIT`; o padrão dele recusa na hora), e o "Cancelar" o interrompe com `outcome: canceled`, sem gravar; com a outra sessão confirmando a mudança durante a espera, o PostgreSQL responde 40001 e o Db2 e o Informix, `RESULT_CHANGED` (o `UPDATE`, ou a contagem do Informix, que esperou, não acham as linhas).
- **Testes**: unidade em `Databases/WholeColumnSqlTests` (o `<Q>` limpo nos três dialetos, a forma direta e o que leva à forma pela chave, a condição como foi escrita, o `"q".` na chave pelo nome do resultado, o `EXISTS` com `"u"`, os lotes de 1.000 e o `OR` de pares, as recusas e as frases), `AdoDatabaseConnectionWholeColumnTests` (parte do `AdoDatabaseConnectionTests`, sobre o driver de mentira: a ordem dos comandos, o Repeatable read pedido, a contagem que difere, o `UPDATE` que difere, o sem log com `EDIT_ROW_MISMATCH` e com `outcome: unknown`, os lotes, o teto de 1.000.000 com um leitor sem Moq, a contagem na transação só de leitura), `DatabaseSessionServiceWholeColumnTests` (o comando guardado com o filtro, a contagem de um guardado, as recusas antes da conexão, o "Ver SQL" com a coluna inteira primeiro), `EditHandlersTests` (o `rows` lido do JSON, a rota da contagem, o somente leitura) e `DatabaseSessionErrorsTests`; integração no contrato `DatabaseEditContractWholeColumnTests` (parte do `DatabaseEditContractTests`, nos três bancos), em `InformixEditTests` (o caminho por lotes, o `LIMIT` da cabeça pela chave, a sonda da tabela derivada, o banco sem log com chave de duas colunas) e `Db2EditTests` (o `LIMIT … OFFSET`), e em HTTP em `Api/DatabaseSessionEditsTests` (a rota da contagem, o `note`, as recusas e o teto de 32 MiB). Os testes de trava seguram as linhas por uma conexão à parte com a transação da carga (`BeginLoadTransactionAsync` e `EmptyTableAsync`), sem SQL de transação.

## Valor completo das células cortadas (RN-SQL-017, rota `results/{resultID}/cells`)

Defeito do dono (2026-10-13): o `CLOB` do Informix (um JSON longo) copiado com Ctrl+C ou "Copiar valor" vinha cortado, porque a cópia usava o texto da grade. A grade continua recebendo o corte da RN-SQL-011; copiar e exportar pedem o valor completo à API.

- **De onde vem.** `ReadPageAsync` (a base) lê a célula inteira, como sempre leu, e para cada cortada guarda `CellFormatter.Full(valor)` em `QueryPage.FullValues`, na mesma ordem de `TruncatedCells`: o texto inteiro, ou os bytes do binário. No PostgreSQL o `ReadCell` passou a converter o `bytea` inteiro (`\x...` vira os bytes todos; antes só os 33 primeiros). Os drivers entregam o valor inteiro ao leitor: no PostgreSQL o `text` de 50.000 e o `bytea` de 300.000 bytes; no Informix o `CLOB` e o `TEXT` de 50.000 e o `LVARCHAR` de 30.000 (`InformixClientTests.Execute_LongClobTextAndLvarchar_CarryTheWholeValue`: o driver não corta nada). O Db2 não tem teste disso.
- **Onde fica** (`Services/ResultCells.cs`, com `ResultCellsTests`): um por `ResultState`, pela `CellPosition` (a linha no resultado inteiro, que o `Add` de cada página continua, e a coluna). Só na memória do processo, nunca em disco nem no log. O teto é `QueryPaging.MaxFullValueBytes` (256 MB): a sessão só tem um resultado de cada vez, então é o teto da sessão. **Conta o que fica na memória** (`FullCellValue.Bytes`): 2 bytes por caractere do texto (o UTF-16 do .NET) e 1 por byte do binário, que fica como veio e só vira hexadecimal (`0x` e maiúsculas, como a grade) na resposta. A célula que não cabe e TODAS as seguintes ficam sem valor completo (mesmo uma pequena que coubesse: "as seguintes" da regra), e a página diz quais em `cellsWithoutFullValue` (`[linha, coluna]` dentro da página, como `truncatedCells`). O registro tira `FullValues` da página antes de responder.
- **Quando larga** (`ReplaceResult` e `Session.Close`, que chamam `ResultCells.Clear`): resultado novo, comando que rodou sem linhas, `ExecutionFailed`, controle de transação que rodou (`executed`) e sessão fechada (inclusive pelo cofre e pela ociosidade da conexão). O resultado que passa a guardado pela lista `keep` (RN-SQL-024) larga os dele do mesmo jeito: só o atual tem valores completos, e a rota responde 404 `RESULT_NOT_FOUND` para um guardado (a tela copia o valor cortado). A recusa pelo texto antes de executar deixa o resultado e os valores, como o `CurrentResult` da edição; o cursor fechado por ociosidade também (as páginas entregues continuam copiáveis). Durante o comando seguinte os valores do anterior ainda servem: ele só é trocado quando o comando novo termina.
- **O `resultID`** já vinha em toda página com linhas (`queries` e `queries/next`): editável ou não, a do comando que grava e devolve linhas (RN-SQL-013) e a dos Registros, que usam a mesma rota. Não precisou estender.
- **A rota** (`GetResultCells`: controller, handler de uma linha e validator): `POST api/user/database-sessions/{id}/results/{resultID}/cells` `{ cells: [{ row, column }] }` responde `{ values: [{ row, column, value }] }` na ordem pedida, `value` nulo na célula sem valor completo (também a que não foi cortada). Validator: de 1 a 10.000 células (`QueryPaging.MaxCellsPerRequest`), linha e coluna não negativas, senão 422 `CELLS_INVALID` no campo. O registro recusa a linha além das entregues e a coluna além das do resultado (422 `CELLS_INVALID`), o resultado que não é o atual (404 `RESULT_NOT_FOUND`) e a sessão que não existe (404 `DATABASE_SESSION_NOT_FOUND`). **Não toma a vez da sessão**: lê só da memória, sob a trava do `ResultCells` (o "carregar mais" acrescenta com a vez tomada), então responde enquanto outro comando roda. O log tem só as contagens ("N células pedidas, M sem valor completo"; `LogHygieneTests` confere). `FullCellValue` e `CellValueDto` não imprimem o valor.
- **Testes**: unidade em `ResultCellsTests`, `CellFormatterTests` (`Full`), `AdoDatabaseConnectionTests` (a página leva os valores, também no "carregar mais"), `DatabaseSessionServiceTests` (`GetCells`: a linha no resultado inteiro, outro comando, sessão fechada, linha não entregue), `DatabaseSessionErrorsTests` e `GetResultCellsHandlerTests`; integração em `PostgresClientTests` e `InformixClientTests`, e as rotas em HTTP em `Api/DatabaseSessionCellsTests` (texto de 50.000 com acento, aspas e emoji e binário de 300.000 bytes, byte por byte, na segunda página do "carregar mais"). O `InformixSingleton` cria o espaço de objetos grandes `sbspace`, que a configuração da imagem nomeia e ela não cria (sem ele o `CLOB` é recusado com -9814), e tem `RunScriptAsync`: roda um script no `dbaccess` do contêiner com os arquivos que ele lê, porque o `TEXT` só entra por parâmetro ou `LOAD` e o `CLOB` acima dos 32 KB de um literal só pelo `FILETOCLOB`.

## Filtro do resultado (RN-GRADE-011, campo `filter` de `queries`)

O resultado da aba de consulta ganha o campo de filtro dos Registros. O texto do editor não muda: a tela executa de novo o mesmo comando com `filter` (condição, ordem ou as duas, como na RN-TABELA-010), e a API junta o filtro ao comando.

- **A leitura** (`Clients/SqlFilter.cs`, pura, com `SqlFilterTests`). O leitor é o da edição, `EditableSql.Lex`, que passou a `internal` e dá a posição de cada pedaço (`Token.Start` e `End`): as aspas, os comentários e o `$marca$` de cada banco, o nível de fora. Nada de regex. O filtro se divide no `ORDER BY` de fora: a condição é o que vem antes dele, e a ordem é o que vem depois, cada uma do primeiro ao último pedaço de código.
- **Junto (`merged`).** Vale para um `SELECT` só, com `FROM`, cujas cláusulas de fora a junção conhece, na ordem do banco: `WHERE`, `WINDOW`, `ORDER BY` e o fim. O fim são os limites (`LIMIT`, `OFFSET`, `FETCH`), as travas e o `FOR READ ONLY` (`FOR` seguido de `READ`, `FETCH`, `UPDATE`, `SHARE`, `NO` ou `KEY`: o `FOR SYSTEM_TIME` do Db2 é do `FROM`), o `WITH UR|CS|RS|RR` (o `WITH ORDINALITY` é do `FROM`) e o `OPTIMIZE FOR`.
  - A condição entra como `WHERE (<o que havia>) AND (<condição>)`, ou `WHERE (<condição>)` logo depois do último pedaço do `FROM`.
  - A ordem troca o `ORDER BY` do comando, ou entra antes do fim.
  - O `SKIP`, o `FIRST` e o `LIMIT` da cabeça do Informix ficam onde estão.
  - O que se acrescenta entra depois do último pedaço de código da cláusula, e os comentários e o `;` ficam onde estavam: um `-- comentário` no fim não engole o filtro.
  - `DISTINCT`, `FOR UPDATE`, junções e subconsulta no `FROM` também se juntam. A edição é lida do comando montado (`EditableSql.Read`), e fica como seria sem o filtro.
- **Por fora (`wrapped`).** Vai assim o que tem união (`UNION`, `INTERSECT`, `EXCEPT`, `MINUS`), `GROUP BY`, `HAVING`, `INTO`, `WITH` na frente, o que não tem `FROM`, o que começa por parêntese, o que não é `SELECT`, e o `SELECT` de cláusulas fora de ordem. O resultado é `SELECT * FROM (\n<comando>\n) prism_filtro\nWHERE <condição>\nORDER BY <ordem>`.
  - O comando vai do primeiro ao último pedaço de código, sem os `;` e os comentários das pontas.
  - Conferido à mão nos três bancos (Db2 11.5.8 e a imagem de teste do Informix): a tabela derivada aceita `ORDER BY` e os limites dentro (no Db2 `FETCH FIRST`, `LIMIT` e `OFFSET`; no Informix `SKIP`, `FIRST` e `LIMIT` na cabeça), e também `GROUP BY`, as uniões, o `WITH` e o `VALUES`.
  - O Db2 recusa dentro dela `FOR READ ONLY` e `OPTIMIZE FOR` (SQL0104N), e o Informix recusa `FOR READ ONLY` (-201). Por isso o fim do comando inteiro sai do parêntese e vai por último, depois da ordem, onde vale para o comando todo, como valia.
  - O resultado é só leitura, com o motivo do próprio comando ("agrupamento", "união de consultas"...). O comando que a leitura aceitaria e a junção não conhece usa `EditableSql.FilteredOutside`.
- **As recusas.** `SqlFilter.Refusal` recusa o filtro com `;`, com aspas sem fechar (simples, duplas, `$marca$` do PostgreSQL, `E'...'` com a barra), com comentário sem fechar (a `{` do Informix também), que termina em comentário (também o `-- ` com a quebra de linha), com parênteses sem par ou com mais de um `ORDER BY` de fora.
  - "Aberto" se descobre pelo leitor, com uma linha a mais no fim (`\n1`): o que ficou aberto a engole.
  - Os parênteses sem par não estão na lista da especificação. Entraram porque `1=1) OR (1=1` daria um comando válido com outro sentido, sem o `WHERE` de antes.
  - O comando com mais de um envio e com filtro é `MultipleStatementsNotSupported` ("Com filtro, execute um comando só."): não se sabe a qual comando o filtro iria.
- **Pela rota** a recusa é do validator. O `ExecuteQueryValidator` é o único que depende de um serviço: ele chama `IDatabaseSessionService.FilterRefusal(sessionID, filter)`, que lê com o banco da sessão sem tomar a vez dela. A resposta é 422 `FILTER_INVALID` no campo `Filter` (`errors.Filter` com o motivo, `errorCodes.Filter`), pelo mesmo caminho do `QUERY_INVALID`. Sem a sessão, a recusa é nula, e a execução responde 404.
  - O registro de sessões também recusa (`EDatabaseFailure.FilterInvalid`, 422 `FILTER_INVALID` com o motivo no `detail`) para quem o chama direto.
  - Em nenhum dos dois caminhos algo vai ao banco, e o resultado anterior continua.
- **O registro de sessões** (`ExecuteAsync(sessionID, sql, filter, pageSize, ct)`; o de quatro argumentos é o sem filtro). O handler escolhe pelo `filter` vazio ou só de espaços, que vale como a falta dele.
  - O comando montado é o que roda, o que o "contar total" conta (`LastRowQuery`) e o que a edição lê.
  - A falha do banco com filtro vem sem `position`, que seria a do comando montado, como na contagem.
  - `ResultState.FilterApplied` vai na página de `queries` e de `queries/next` (`QueryPage.FilterApplied`, e no DTO `filterApplied`: `"merged"`, `"wrapped"` ou nulo). O log continua só com a operação, o tempo e as linhas: nem o filtro nem o comando montado.
- **Testes**: unidade em `SqlFilterTests` (junto em cada banco, com e sem `WHERE`, com `ORDER BY` e limites, com comentário no fim; por fora, com o fim do comando; as recusas e as aspas e os comentários de cada banco), `DatabaseSessionServiceTests` (o comando que chega à conexão, a página, a recusa sem executar, a posição), `ExecuteQueryHandlerTests`, `DatabaseSessionValidatorsTests`, `DatabaseSessionErrorsTests` e `DatabaseSessionMappingsTests`.
  - Integração nos três bancos, em `DatabaseEditContractTests`: junto, com as linhas certas, a contagem e um "Salvar"; junto com limite de linhas; por fora de um agrupamento com `ORDER BY` e limite dentro (e `FOR READ ONLY` no Db2 e no Informix); por fora de uma união. Os ganchos do contrato são `WithFirstRows` e `ReadOnlyClause`.
  - HTTP em `Api/DatabaseSessionsTests` (o 200 de cada forma, o `filterApplied` nulo, o 422 no campo com o resultado anterior intacto, o envio de dois comandos, a falha sem posição) e no roteiro do `IbmDatabaseSessionsTests` (com a `{` aberta só no Informix). `LogHygieneTests` marca o filtro e a coluna dele.

## Os parâmetros das consultas (seção 41: RN-VAR-017, 032, 033 e 036, campo `params` de `queries`)

A tela troca o `@nome` do script pelos marcadores do banco (`$1`, `$2`... no PostgreSQL; `?` no Db2 e no Informix) e manda os valores à parte. A API nunca monta o valor no texto do comando: ele vai como parâmetro do driver, e o texto do SQL, os `params` e a mensagem do banco ficam como estavam (RN-LOG-001).

- **O pedido** (`ExecuteQueryCommand.Params`, `JsonElement?` como `keep`): uma lista de `{ type, value }`, na ordem dos marcadores, até 10.000 entradas e 4 MiB de valores (`QueryParameterRules`, pura, com `QueryParameterRulesTests`). O `value` é sempre um texto, ou nulo; o `type` é um destes e dá a forma do texto:
  - `text`: qualquer texto de até 1.000.000 de caracteres, sem `U+0000` e sem metade de um par UTF-16 (o Npgsql lança e o Db2 troca por U+FFFD em silêncio: a API recusa antes). O vazio vale como vazio (no Informix o banco o guarda como nulo).
  - `number`: `12`, `-3.5` ou `1e10`, até 100 caracteres, sem `+` na frente, sem zeros à esquerda, sem `NaN` nem `Infinity`. O inteiro que cabe em `long` vai como `BIGINT`; o decimal exato (com ponto e sem expoente) vai como decimal; o resto vai como `double`.
  - `boolean`: `true` ou `false`. `date`: `aaaa-mm-dd` existente. `timestamp`: `aaaa-mm-dd hh:mm:ss`, com até 6 casas e, só no PostgreSQL, o fuso (`Z`, `+03` ou `-03:30`).
  - Nulo é um valor de cada tipo. A lista pode faltar, ser nula ou vazia: é o comando sem parâmetros, como antes.
- **A forma errada é `422 QUERY_INVALID` no campo**: `params` (a lista), `params[i].type` ou `params[i].value`, pelo mesmo caminho do `QUERY_INVALID` de `keep` (`errors` e `errorCodes`). O que só o banco decide é conferido pelo registro antes de ir a ele, no mesmo campo: o decimal com mais de 31 dígitos no Db2 e no Informix ("O número tem 35 dígitos, e o Db2 guarda até 31."), o expoente que o `DOUBLE` não guarda e o instante com fuso. No PostgreSQL o valor vai como texto e o servidor diz o que não cabe, como veio.
- **A contagem dos marcadores é a da tela** (`ParameterMarkers`, o mesmo leitor do `EditableSql`; a fixture `src/test-fixtures/variables/markers.json` confere os dois lados). Não contam os comentários, os textos entre aspas, o `E'...'` (com a barra), o `U&'...'`, os identificadores entre aspas duplas e o corpo de `$marca$...$marca$`; no PostgreSQL o `?` é o operador do `jsonb` e `k$1` é um nome. No PostgreSQL os números têm de ser exatamente `$1` a `$N`, sem buracos, e `$1` pode aparecer mais de uma vez; no Db2 e no Informix o número de `?` tem de ser o número de valores. Quando não bate: `422 QUERY_PARAMETERS_MISMATCH` com as extensões `markers` e `values` (as duas contagens) e nada vai ao banco.
- **O que o driver faz com cada tipo** (o quadro da RN-VAR-017, como a sonda S-VAR-1 provou nos contêineres: PostgreSQL 18.6, Db2 12.1.5 e Informix 14.10):
  - PostgreSQL: o Npgsql com `EnableSqlRewriting` desligado, `$n` posicionais e cada valor como texto `NpgsqlDbType.Unknown`; com `AllResultTypesAreUnknown` o servidor decide o tipo pelo contexto. Dois marcadores sem tipo numa conta (`$1 + $2`) o servidor recusa ("operator is not unique"); o contorno é `CAST($1 AS integer)`. `COPY (SELECT ... $1)` não aceita parâmetro. O limite do driver é 65.535 parâmetros.
  - Db2 e Informix (`IbmDatabaseConnection.BindQueryParameter`): `?` com o valor já no tipo do .NET e o `DB2Type` do tipo (`BigInt`, `Double`, `Date`, `Timestamp`, `VarChar`; a ordem é `DbType`, depois `Value`, depois `DB2Type`). Decimal: `DB2Decimal.Parse`, até 31 dígitos nos dois bancos (o Informix pelo DRDA também). Booleano no Db2: `bool` com `DbType.Boolean` (o `DB2Type.Boolean` lança). Booleano no Informix: o texto `t` ou `f` (o `bool` dá -674 contra a coluna `BOOLEAN`). O inteiro -2^63 no Informix vai como decimal (o `INT8` não o tem). Texto acima de 32.672 bytes no Db2 vai como `Clob`; no Informix, até 16.350 caracteres `VarChar`, até 32.767 bytes `LongVarChar` e acima disso `Clob`. O limite do driver é 32.767 marcadores.
  - `SELECT ?` sozinho é recusado pelo Db2 (-418) e pelo Informix (-201), com ou sem tipo; `? + 1`, `? || ?` e `CAST(? AS INTEGER)` vão. A mensagem é a do banco.
  - **O custo** (S-VAR-3): 10.000 marcadores num `IN` levam cerca de 6 s nos dois bancos da IBM (o tempo do `ExecuteReader` do driver, que cresce com o quadrado do número de marcadores; 1.000 levam 0,2 s) e 0,1 s no PostgreSQL. Nenhum banco recusa o teto de 10.000.
- **O comando guardado leva os parâmetros** (RN-VAR-033). `ResultState.Sql` e `RowQuery` guardam o texto e os `params` (`IReadOnlyList<QueryParameter>`) só na memória da sessão, e tudo o que executa de novo os leva, na mesma ordem: a contagem (`queries/count`, RN-SQL-006), o F5 da tela (a mesma rota com o mesmo comando), os guardados do script (RN-SQL-024), o filtro, o `edit-target` (que lê o comando com os marcadores), a coluna inteira, a exportação e a cópia. `QueryParameter.ToString()` e os registros que os levam escrevem só o nome do tipo, para um objeto nunca vazar o valor numa mensagem.
  - **O filtro** (RN-GRADE-011/012/014): o filtro não pode ter marcador, nem `$1` nem `?` (`FILTER_INVALID` no campo `Filter`, "O filtro não pode ter marcador de parâmetro ($1 ou ?)."). O comando com `params` e filtro se junta como antes, com os marcadores do comando onde estavam. Quando a ordem do filtro troca um `ORDER BY` que tem marcador, o comando vai por fora (`wrapped`), porque trocar a cláusula perderia o marcador e a conta de valores deixaria de bater (`SqlFilter.Merge` devolve nulo).
  - **A coluna inteira** (RN-EDIT-020, `WholeColumnSql`): os valores do `SET` entram depois dos do `<Q>` e a numeração é refeita. No PostgreSQL, na forma direta só a condição do `<Q>` fica no `UPDATE`, e seus marcadores são renumerados a partir de `$k+1` (k = os do `SET`), sem buracos, na ordem em que aparecem; a contagem começa em `$1`. Na forma pela chave o `<Q>` leva os valores dos `params` e o `SET` vem depois. No Db2 e no Informix os `?` se ordenam pela posição no texto (`ParameterMarker.Index`). No lote do Informix a leitura das chaves leva os `params` do `<Q>` e os lotes levam só o `SET` e as chaves. O "Ver SQL" mostra os valores como literais.
  - **A exportação e a cópia** (RN-EXPORT-002 e 016): `source.params` na origem `query` (a mesma lista, a mesma forma e as mesmas recusas, em `source.params[i].value`, com `EXPORT_OPTIONS_INVALID` ou `IMPORT_OPTIONS_INVALID`; os marcadores que não batem são `QUERY_PARAMETERS_MISMATCH`). O corpo das rotas de `transfers` tem o teto de 16 MiB (`UserTransfersController.MaxExportRequestBytes`), porque 4 MiB de valores podem ser escritos em até seis vezes isso no JSON (caracteres de controle como `\u0001`); o `POST queries` cabe nos 30 MB do Kestrel. A leitura do trabalho usa os mesmos `params`.
- **A memória e o log** (RN-VAR-036, RN-LOG-001). Os valores só existem na memória da sessão (no `ResultState`, no `RowQuery` e no trabalho de exportação) e somem com o resultado, com a sessão ou com o trabalho. Nada vai ao disco, ao cofre ou ao log; o log da execução diz só quantos parâmetros o comando levou ("levou 2 parâmetros"). A mensagem do banco continua indo à tela e não ao log. `LogHygieneTests` marca um valor de texto e um número e procura os dois em `logs/`, com a recusa por forma, por divergência e pelo banco.
- **Testes**: unidade em `ParameterMarkersTests` (a fixture e a contagem de cada banco), `QueryParameterRulesTests` (cada tipo, os limites e as recusas), `QueryParameterBindingTests` (a conversão e o `DB2Type` de cada banco), `AdoDatabaseConnectionParametersTests` (um `DbConnection` de mentira que confere cada parâmetro ligado), `SqlFilterParametersTests`, `WholeColumnSqlParametersTests` (a renumeração), `DatabaseSessionServiceParametersTests`, `EditableSqlParametersTests`, `ExecuteQueryParametersTests` e `StartExportParametersTests`. Integração nos três bancos em `Api/QueryParametersTests` (a base abstrata com uma classe por banco, e duas no Informix: `prism`, com log, e `prism_sem_log`, sem, pelo `InformixSingleton.GetUnloggedSettingsAsync`; os ganchos `M(n)`, `CreateTableSql`, `FromDual`... e os sinalizadores do que só um banco faz): cada tipo no `WHERE`, `IN`, `LIKE`, `BETWEEN`, `INSERT` e `UPDATE`, o texto com aspas e barras (e a injeção como valor), o decimal acima do limite, o -2^63, o texto de 40.000 caracteres, o filtro junto e por fora, a contagem, o `edit-target`, a coluna inteira nas três formas, a exportação e a cópia.

## Proteções e verificação periódica (seção 32: RN-PROT-001 a 006, RN-VERIF-001 a 003)

O somente leitura é da API; a confirmação antes de executar e o indicador da verificação são da tela, e a API só guarda a escolha e diz as que valem.

- **A regra única** (`Common/Protections/ProtectionRules`, como o `EnvironmentRules`): a lista da confirmação (`none`, `irreversible`, `all`; `MustBeAConfirmation` leva a mensagem, e o código é de quem valida: `CONNECTION_INVALID` ou `FOLDER_NAME_INVALID`), a forma gravada ("Não" e o desmarcado se gravam nulos), a herança (`Of`: vale a mais forte entre a própria e as das pastas acima, subindo pelo `ParentID` com o registro das visitadas, como o `IsSelfOrDescendant`; a origem é a pasta mais próxima que impõe o valor que vale, e nula quando ele é o próprio) e quando a mudança pede a senha (`NeedsPassword(antes, depois)`, sobre os dois documentos: o somente leitura próprio de uma pasta ou de uma conexão que já existia mudou, ou uma conexão que já existia deixou de ser somente leitura por herança; criar, duplicar, excluir e mover para dentro não pedem).
- **A senha do somente leitura** (RN-PROT-003). `IVaultService.SaveWithPasswordAsync(change, needsPassword, password)` é a gravação que pode pedir a senha, numa operação só do semáforo: aplica a função, pergunta a `needsPassword` com o documento de antes e o de depois e, se pede, confere pelo `CheckPassword` (a mesma derivação e a mesma contagem de cinco erros da revelação e da troca de senha) antes de gravar. Devolve `EPasswordCheck`: `NotNeeded` (não pedia, e a senha que veio não foi conferida), `Matched`, `Missing` (pedia e não veio: nada é derivado nem contado) e `Wrong` (contado); os dois últimos não gravam. A função que devolve o mesmo documento (a recusa da regra) é `NotNeeded`, sem pergunta nem gravação. `VaultSaves.SaveOrRefuseWithPassword` é o `SaveOrRefuse` dela: a recusa da regra vem antes de tudo, depois o cofre fechado (também pelo quinto erro) e o disco, depois 422 `USER_PASSWORD_REQUIRED` ou `INVALID_PASSWORD` no campo `UserPassword` (`ProtectionErrors`, o mesmo título "Senha incorreta." da revelação). O `ConnectionRepository.Update` e o `FolderRepository.Update` gravam por ela; quem decide se a senha é pedida é o documento mais recente, e não o que o handler leu. O `UpdateConnectionCommand` e o `UpdateFolderCommand` levam `UserPassword` e sobrescrevem o `ToString()`.
- **A verificação gravada** (RN-VERIF-001): `verificationEnabled` (nulo é verdadeiro), `verificationInterval` (5 a 3.600, nulo é 30; texto e número com casas são o 400 do MVC) e `verificationQuery` (aparada, em branco é nula; nesta ordem, até 1.000 caracteres, sem caractere de controle nem de direção do texto fora a tabulação, a quebra de linha e o retorno de carro, `TextRules.HasControlOrDirectionBesidesLineBreaks`, emenda de 2026-10-17, e uma leitura só no banco da conexão, `ConnectionRules.VerificationQueryRefusal` sobre o `ReadOnlySql.VerificationRefusal`, com o motivo na mensagem do campo). Os três validators (criar, alterar e testar) e a importação (RN-TRANSF-014) aplicam a mesma regra; a conexão não guarda a consulta da pasta, que não tem.
- **O que é leitura** (`Databases/Clients/ReadOnlySql`, pública como o `VaultFileName.IsAllowed`, porque os validators da Application a usam). Lê o texto pelo leitor da edição e do filtro (`EditableSql.Lex`, que ganhou a leitura do driver do comentário de bloco do Db2, `asTheDriver`), divide nos `;` e exige que cada comando seja leitura: começa, depois dos parênteses, por `SELECT`, `WITH` ou `VALUES` (no PostgreSQL também `TABLE`, `SHOW` e `EXPLAIN` sem `ANALYZE`, que só planeja) e não tem, como palavra, `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `INTO`, a trava de linha (`FOR`/`KEY`/`KEEP` antes de `UPDATE`, `SHARE`, `EXCLUSIVE`) nem `NEXTVAL` ou `NEXT VALUE`; no Db2 nem `TABLE (` nem `EXPLAIN`. No Db2 basta uma das duas leituras do comentário ver o que não é leitura. É uma lista do que passa: na dúvida, não é leitura (uma coluna `update` sem aspas é recusada). O texto sem comando nenhum passa (quem responde é o banco). `Refusal` diz o motivo ("um DELETE não é leitura"), e `Message` monta a frase da recusa. Ela é mais estrita que o `SqlText.IsSingleRead` da paginação do Db2 e do Informix: todo comando que ela aceita também pagina.
- **A recusa** (RN-PROT-002). `IConnectionQueries.IsReadOnly(connectionID)` diz se a conexão é somente leitura agora (a dela ou a de uma pasta acima, no documento aberto; nulo quando ela não existe), e `IDatabaseSessionService.ConnectionOf(sessionID)` diz de que conexão a sessão é. `SessionProtections.IsReadOnly` junta as duas: sessão que não existe é "não" (a operação responde `DATABASE_SESSION_NOT_FOUND` por conta própria), cofre fechado é o 401, e a conexão excluída com a sessão ainda fechando responde 404 `DATABASE_SESSION_NOT_FOUND`. O `ExecuteQueryHandler` passa o resultado ao `ExecuteAsync(..., filter, pageSize, readOnly, ...)` do registro (as duas sobrecargas antigas são as de uma conexão comum, e ficam para os testes); os três da edição respondem 422 `CONNECTION_READ_ONLY` (`SessionProtections.EditsRefusal`) sem chamar o registro. No registro, com `readOnly`, o comando montado (com o filtro) passa pelo `ReadOnlySql` antes de tudo: o que não é leitura é `EDatabaseFailure.ConnectionReadOnly` (422 `CONNECTION_READ_ONLY`, sem `executed`), sem ir à conexão, sem tirar o resultado e sem mexer no prazo do cursor aberto, que continua contando da última página (o cursor ocioso, acima: a recusa não chega a ele); o que é leitura vai ao `IDatabaseConnection.ExecuteReadOnlyAsync`, e a página leva `editable: { known: true, reason: "a conexão é somente leitura" }` (`ReadOnlySql.ResultReason`). Esse motivo vai à parte no `ResultState` (`readOnlyReason`), e o `Source` do resultado continua o que o texto diz (`EditableSql.Read`): o alvo do "Gerar SQL" nela (`purpose: sql`, RN-GRADE-020) e o da edição, quando a conexão deixa de ser somente leitura, saem dele; um `ResultSource.ReadOnly` ali deixaria os dois em `RESULT_NOT_EDITABLE` (o `DatabaseSessionServiceReadOnlyTargetTests` lê pelo `ExecuteAsync` com `readOnly`). Quem recusa a edição é a rota, pela proteção de agora. A proteção é lida a cada comando: mudá-la vale para o comando seguinte das sessões abertas, e nenhuma fecha.
- **A leitura somente leitura na conexão** (`AdoDatabaseConnection.ExecuteReadOnlyAsync`): as mesmas recusas pelo texto do `ExecuteAsync`, e sempre a tentativa paginada (no PostgreSQL, a transação só de leitura); a recusa do banco por gravar (25006) é a resposta, e o comando nunca roda de novo em modo completo (no `ExecuteAsync` comum ele rodaria). O cursor guarda que é somente leitura (`_cursorReadOnly`): a recusa por gravar no "carregar mais" volta como veio, sem a frase de executar de novo e sem marcar `_writesAfterTheFirstPage`.
- **O modo da sessão** (RN-PROT-006, gancho `SessionModeSql`, que só o PostgreSQL tem: `SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY` ou `READ WRITE`). `ApplySessionModeAsync` roda dentro do comando, antes de qualquer transação (dentro de uma, o `SET` seria desfeito com ela), no `ExecuteCommandAsync` e no `ApplyEditsAsync`, e só vai ao banco quando o modo muda (`_readOnlyMode`): no primeiro comando de uma conexão somente leitura, e no primeiro comando ou "Salvar" depois de ela deixar de ser. A sessão em que o Prism nunca pôs o modo não recebe nada. O `set_config('default_transaction_read_only', ...)` que a pessoa rodar num `SELECT` muda o modo sem o Prism saber, e não abre a porta: a leitura somente leitura roda sempre na transação só de leitura.
- **Db2 e Informix** não têm conexão só de leitura no driver (o `Net.IBM.Data.Db2` não tem o dado na string de conexão nem na conexão, e o modo de acesso da CLI é só uma dica), nem transação só de leitura usável numa sessão em auto-commit: quem guarda é o texto, e o banco recusa a rotina que grava chamada por um `SELECT` (SQL0740N no Db2, -675 no Informix).
- **A verificação** (RN-VERIF-002, `POST api/user/connections/{id}/verification` → `VerifyConnectionHandler` → `IDatabaseSessionService.VerifyAsync(connectionID, consulta, geração)`). O handler lê a `Generation` do cofre antes da conexão e manda a consulta gravada (nula é a do banco); não olha `verificationEnabled`. O registro só olha as sessões da conexão daquela geração: nenhuma é `NotConnected` (e nenhuma é aberta); a sem resultado (a da árvore) vem antes da de uma aba; a vez é tomada sem esperar (`Wait(0)`), e o cursor é conferido na conexão depois de tomá-la (`IDatabaseConnection.HasOpenCursor`: a marca `CursorOpen` da sessão é a do temporizador, e quem sabe se o cursor está aberto é a conexão); com todas ocupadas, `Busy`. A consulta roda pelo `IDatabaseConnection.VerifyAsync` (o `PingAsync` é o mesmo sem consulta própria): com o ajuste do banco num texto da pessoa (`ConfigureUserCommand`, que no Db2 e no Informix tira os `;` soltos), o prazo do driver e, no PostgreSQL, a própria numa transação só de leitura. A falha é `Failed`, com a mensagem e o SQLSTATE como vieram (a resposta é 200, e não erro), e a sessão cuja conexão caiu sai do registro (`RemoveIfClosedAsync`). Nada da sessão muda (resultado, última leitura, temporizador). O log tem a conexão, a sessão, o tempo e a classe da falha (`Information`), e o sucesso, o `busy` e o `notConnected` só em `Debug`.
- **A verificação não deixa a sessão ocupada para a pessoa.** Com a vez tomada, a sessão fica marcada (`Session.Verifying`): o `RunAsync` que não espera a vez (executar, carregar mais, "Salvar") espera o fim da verificação em vez de responder `SESSION_BUSY`. O "cancelar" não interrompe a verificação, e o comando que esperava desiste na hora, sem esperar o fim dela e sem ir ao banco (`ExecutionFailed` com `ECancelOutcome.Canceled`, "O comando foi cancelado antes de ir ao banco: nada foi executado."): a espera leva a fonte de cancelamento da sessão (`CountCancellation`, a das contagens, que o `Cancel` troca depois de cancelar e o fechamento da sessão cancela de vez), junto com a da requisição. O fechamento da sessão durante a espera responde `SessionNotFound` na hora, e a requisição abandonada, a recusa de quem desiste da vez ("A operação foi cancelada antes de chegar a vez dela na sessão."). O contador `Session.CancelRequests`, comparado antes e depois da espera, pega o "cancelar" que chega junto com a vez, quando a fonte já não interrompe nada. Sem a fonte, o "cancelar" só valeria quando a verificação acabasse: até o prazo do driver (30 s) com a rede parada.
- **O teste de conexão** (RN-CONN-013) aceita `verificationQuery` (`TestConnectionCommand`), validada como na gravação antes de conectar, e o `TestAsync(settings, consulta)` a executa pelo mesmo `VerifyAsync` (falha `ConnectionFailed`, 422 `DATABASE_CONNECTION_FAILED`). O `TestAsync(settings)` sem consulta continua para os testes.
- **Testes**: unidade em `Databases/ReadOnlySqlTests` (os três dialetos), `Common/ProtectionRulesTests`, `Vault/VaultServiceSaveWithPasswordTests` (parte do `VaultServiceTests`), `Vault/VaultProtectionsTests`, `Databases/DatabaseSessionServiceVerificationTests` (parte do `DatabaseSessionServiceTests`, com conexões de mentira por sessão: `QueueClient`; a recusa do somente leitura com o cursor aberto é conferida com o relógio que dispara os temporizadores na hora e com o que não dispara nada, o aviso perdido), `Databases/AdoDatabaseConnectionReadOnlyTests` (parte do `AdoDatabaseConnectionTests`, com o banco de mentira `SessionModeEngineConnection`), e os validators, repositories e handlers de pastas, conexões e sessões (`VerifyConnectionHandlerTests`). Integração em `Api/ProtectionsTests` (sem banco: os campos, a herança, a senha, as recusas, a verificação sem sessão e o teste recusado antes de conectar, com o `ConnectionCounter`) e `Api/ReadOnlyDatabaseSessionsTests` (`[Category("Databases")]`, com o Docker: a recusa antes do banco, o 25006 da função que grava, a regra nova na sessão aberta, a verificação ok, failed e busy), e, no `Infrastructure/Databases/DatabaseSessionServiceTests`, o cursor que fecha aos cinco minutos da leitura com a recusa do somente leitura no meio e o "cancelar" do comando que espera uma verificação de `pg_sleep(5)`.

## Drivers sob demanda (`Prism.Infrastructure/Drivers`, `Prism.Application/Drivers`)

A terceira integração, no formato das outras (`Models/`, `Clients/`, `Services/`), mais o `DriverRegistration.AddDrivers`, que o `AddInfrastructure` chama. É a seção 16 da especificação (RN-DRIVER-001 a 009): o Prism leva só o driver do PostgreSQL, e o da IBM é baixado pelo usuário, do nuget.org. **A API baixa código da rede**, e tudo aqui parte de uma regra: o catálogo é a única fonte do que se baixa, de onde vem e para onde vai cada arquivo. Nenhum valor recebido numa requisição vira endereço, nome de pasta ou nome de arquivo; o `id` da rota é só uma chave de busca no catálogo.

- **O catálogo** é o arquivo `Drivers/drivers.catalog.json`, embutido no assembly (`EmbeddedResource`, RN-DRIVER-002), lido e conferido na partida pelo `DriverCatalog` (`AddDrivers`): com ele ausente ou errado a API não sobe. Por driver: identificador (minúsculas, dígitos e hífen, porque vira nome de pasta), nome, fabricante, bancos, tipo (`bundled`, `downloadable`, `comingSoon`) e, para o que se baixa, um pacote por plataforma (`win-x64`, `linux-x64`, `osx-arm64`): nome no nuget.org, SHA-512 do `.nupkg` em base64 (o mesmo valor do arquivo `.nupkg.sha512` do cache do NuGet; **não** é o `contentHash` do lock file), tamanho, licença (nome e endereço `https://`), e o mapa do que sai do pacote (`files` e `trees`, de entrada para destino), o assembly gerenciado e a biblioteca nativa principal. Plataforma sem pacote é `unavailable`, com a `unavailableNote`. A leitura recusa campo desconhecido, campo obrigatório ausente, caminho que não é relativo e simples (`DriverPaths.IsSafe`), endereço de licença que não é `https://` e banco atendido por dois drivers (a RN-DRIVER-006 precisa dizer qual driver falta). **Mudou a versão de um `PackageReference` do driver, muda a do catálogo**: `DriverCatalogTests` compara a versão do catálogo com a do assembly que a Infrastructure referencia (`IBM.Data.Db2` e `Npgsql`), e `DriverInstallerTests` instala o pacote de verdade, do cache do NuGet, contra o catálogo de verdade, nas três plataformas.
- **Um client só, `DriverPackageClient`**, para a rede e para o disco, com o único `try` no `Send`. A interface só recebe o identificador do driver: o endereço (`https://api.nuget.org/v3-flatcontainer/<pacote>/<versão>/<pacote>.<versão>.nupkg`, em minúsculas), o hash e os destinos saem do catálogo dele. O `HttpClient` é do próprio client (por isso ele é `Singleton`): sem seguir redirecionamento (um 3xx é falha, sem segunda requisição), sem cookies, sem descompressão, com a validação de certificado padrão, 15 s para conectar, 30 s até os cabeçalhos e 30 minutos para o download inteiro. O tamanho do catálogo é o teto: `Content-Length` diferente é recusado sem ler o corpo, e a leitura para no byte seguinte ao esperado. O SHA-512 é somado enquanto o arquivo é gravado e conferido **antes** de o zip ser aberto, e o arquivo fica aberto sem compartilhamento do primeiro byte ao fim da extração (o que foi conferido é o que é extraído), e some ao fechar (`DeleteOnClose`).
- **A extração** (`DriverPackageExtractor`) confere o nome de **toda** entrada do pacote, também das que não saem dele: caminho absoluto, `..`, `.`, segmento vazio, barra invertida, dois-pontos, caractere de controle ou link simbólico (o modo do Unix nos atributos da entrada) recusam o pacote inteiro, antes do primeiro arquivo. Só sai o que o catálogo mapeia; dois nomes para o mesmo destino (sem diferenciar maiúsculas) são recusa; o teto (512 MiB) conta os bytes gravados, e não o que a entrada declara. O executável de teste da IBM (`tools/TestConn.*`) não é mapeado e não sai. Nada do pacote é executado.
- **A pasta no disco** (`DriverStore`): `<PRISM_DATA_DIR>/drivers/<id>/<versão>/`, com o `install.json` dentro (o aceite: licença, versão, data; o hash do pacote; e o SHA-512 do assembly gerenciado e da biblioteca nativa como foram extraídos). **A pasta da versão só existe com esse nome depois de completa**: a instalação extrai numa pasta `.tmp-*` ao lado, grava o registro e só então renomeia. O que uma queda deixa é sempre um `.tmp-*`. A remoção é um arquivo `<versão>.remove` ao lado da pasta, porque um assembly carregado não se apaga.
- **A conferência da partida** (`DriverStore.Probe`, pelo `CheckInstallation` do client, uma vez por execução, no construtor do `DriverService`, que o `UseApi` pede na subida da API, antes de ela atender): apaga os `.tmp-*`, executa a remoção marcada (o marcador só sai depois da pasta), e só dá o driver como instalado se a pasta é a da versão do catálogo, o registro é desse pacote e os dois hashes batem. Não bateu: o driver vale como não instalado, o motivo vai para o log (`Warning`), a API segue, e uma instalação nova toma o lugar da pasta. Pasta de outra versão fica onde está (atualizar driver é "fica para depois" na especificação).
- **O `DriverService` é `Singleton`** e guarda o que cada driver está fazendo nesta execução: a instalação em andamento (uma por driver, com a própria fonte de cancelamento), os bytes recebidos, a falha (até a próxima tentativa) e a remoção pedida. O que a partida aprovou é o que esta execução usa; `restartRequired` é "instalado nesta execução" ou "removido nesta execução". A ordem das recusas de instalar: não existe → indisponível (plataforma sem pacote, `comingSoon`) → já instalado (embutido, instalado, ou removido à espera do reinício) → em andamento → sem o aceite. **O estado vira `installing` antes de a requisição responder**; o download roda em outra thread. **Cancelar só volta quando a instalação parou**: se ela passou do ponto sem volta (a troca de nome) antes de ver o cancelamento, a resposta é `NotInstalling` e o driver ficou instalado. O descarte do contêiner interrompe o que estiver baixando.
- **O que a tela recebe e a seção 16 não escreve**: instalar um driver removido antes do reinício é 409 `DRIVER_ALREADY_INSTALLED` (a pasta ainda está no disco, e carregada); remover o embutido é 409 `DRIVER_NOT_INSTALLED`; instalar um `comingSoon` é 422 `DRIVER_UNAVAILABLE`; o disco que recusa o marcador de remoção é 500 `INTERNAL_SERVER_ERROR` (não há código de driver para isso). Falha de disco numa instalação é `DRIVER_DOWNLOAD_FAILED`; tamanho ou hash diferente, zip ilegível e nome de entrada estranho são `DRIVER_INTEGRITY_FAILED`. O detalhe é sempre uma frase do Prism: a mensagem da exceção (que traz caminho ou host) nunca vai para a tela nem para o log, que recebe o driver, a versão, a operação e a classe do erro (RN-LOG-001).
- **Application**: quatro handlers (`GetDrivers`, `InstallDriver`, `CancelDriverInstall`, `RemoveDriver`), de uma linha menos o de remover, `DriverErrors.From` (a única tradução do `EDriverFailure`) e o `DriverDto`, que é onde o estado e os códigos de falha viram texto (`comingSoon`, `DRIVER_DOWNLOAD_FAILED`): a Infrastructure fala em enums. O `POST …/install` responde 202 sem corpo, e o corpo dele é opcional (a falta do aceite é o 422 da regra, e não um 400 do MVC).
- **A costura de teste é uma só**: o registro `DriverSettings` (pasta, endereço de origem, plataforma) e o `DriverCatalog` são internos, e `UseDriverSource` (`Prism.TestingCore/Extensions`) os troca no host de teste. Não há variável de ambiente, opção nem parâmetro público para mudar o endereço (RN-DRIVER-008). A plataforma dos testes é `plataforma-de-teste`, para o mesmo teste valer em qualquer sistema.
- **A carga do driver instalado** (RN-DRIVER-005). O que a conferência da partida aprova fica registrado no `DriverPackageClient`, e é só por isso que os dois ganchos dele respondem: `AssemblyLoadContext.Default.Resolving` entrega o assembly gerenciado (pelo nome dele no catálogo, e só se o arquivo ainda existe), e `ResolvingUnmanagedDll`, a biblioteca nativa (só ao assembly de um driver aprovado, e só pelo nome da biblioteca do catálogo). São os mecanismos de resolução do próprio .NET: sem reflexão para chamar o driver, sem API interna, e o código dos clients não sabe de onde o assembly veio. **A carga é preguiçosa**: acontece quando o primeiro tipo do driver é usado (a primeira conexão), não na partida; o arquivo conferido na partida é o que é carregado. Uma exceção lançada dentro de um gancho sairia no ponto da carga, fora de qualquer `Send`: por isso os ganchos só devolvem "não sei". O descarte do client tira os ganchos (num processo de teste há um client por contêiner de injeção). O que foi instalado depois da partida não é carregado nesta execução, nem a quente.
- **Sem o driver, o client é outro** (RN-DRIVER-006). No `AddInfrastructure`, o client do Db2 e o do Informix são fábricas: se `IDriverService.RefusalFor(banco)` é nulo (a partida aprovou o driver), entra o `Db2Client` ou o `InformixClient`; senão entra o `MissingDriverDatabaseClient`, que não conecta e devolve a recusa: `EDatabaseFailure.DriverNotInstalled` (422 `DRIVER_NOT_INSTALLED`, com o nome do driver no detalhe e a extensão `driverID`, que vem de `DatabaseFailure.DriverID`), ou `ConnectionFailed` com a nota do catálogo quando a plataforma não tem pacote. Abrir sessão e testar conexão passam os dois pelo `ConnectAsync` do registro de sessões, então a troca do client cobre as duas rotas e o registro não muda. **Nenhum caminho toca num tipo de `IBM.Data.Db2` sem o driver aprovado**: o assembly não está ao lado da API, e tocá-lo seria uma falha de carga (500). `DriverNotInstalledTests` roda isso no processo dos testes de unidade, que não tem o assembly. A decisão é de quem a partida aprovou (`Active`), não do que está no disco agora: o driver instalado nesta execução ainda responde `DRIVER_NOT_INSTALLED` (com "só passa a valer quando o Prism reiniciar"), e o removido nesta execução continua conectando até o reinício. O texto "O Prism para <plataforma> ainda não conecta..." do `ConnectAsync` só é alcançado onde a API é compilada sem os clients (`osx-x64`).
- **`DRIVER_IN_USE`** (RN-DRIVER-007) é decidido no `RemoveDriverHandler`: só para o driver instalado, ele pergunta ao registro de sessões (`IDatabaseSessionService.HasOpenSession`, com os bancos do driver) antes de marcar a remoção. Fica no handler, e não no `DriverService`, porque o registro de sessões depende dos clients, que dependem do gerenciador de drivers: o contrário fecharia um ciclo de injeção. Remover o embutido responde `DRIVER_NOT_INSTALLED` mesmo com sessão do PostgreSQL aberta. Instalar de novo um driver removido antes do reinício responde 409 `DRIVER_ALREADY_INSTALLED` (decisão do dono: a remoção não é desfeita; a lista o mostra `available` com `restartRequired`).

## Dados do usuário no cofre (modelo: `Prism.Application/Folders`)

As pastas são a primeira fatia de `api/user/...` e o modelo das próximas (conexões, Tarefa 5). O formato é o do guia zanveri, com o cofre no lugar do banco:

- Controller em `Prism.Api/Controllers/User<Recurso>Controller.cs`, rota `api/user/<recurso>`; a barreira do cofre já o cobre, sem `[Authorize]`. `POST` responde 201 com o `Location`: nas pastas aponta para a lista (não há rota de um item só), nas conexões para o item, que tem rota.
- `Queries` (interface pública, retorna `bool`/DTO) e `Repositories` (interface `internal`, trafega o domínio) falam com o `IVaultService`; o `Domain` não conhece o cofre (`Folder.Restore` e o `ToRecord` do repository fazem a ida e a volta).
- **A regra tem de valer dentro da função do `SaveAsync`.** O handler confere antes (a `Queries`) para responder depressa e com o erro certo, mas só o serviço do cofre, com o semáforo tomado e o documento mais recente, impede duas requisições de passarem juntas pela conferência. Por isso o repository repete cada regra de unicidade, de existência do pai e de ciclo dentro da função, a partir das mesmas perguntas sobre o documento (`VaultFolders`, usadas também pela `Queries`). A função não tem como falhar: o `VaultSaves.SaveOrRefuse` (Application/Common/Vault, que os repositories chamam no lugar do `SaveAsync`) anota a recusa numa variável, devolve o documento como entrou e traduz depois do `await`. A mesma instância devolvida é "nada a gravar": o `VaultService.Save` não cifra nem escreve, e o `.bak` guarda a versão anterior de verdade (uma recusa, como apagar duas vezes, não o iguala ao arquivo atual). A recusa vale mesmo que uma gravação falhe, e uma função que não rodou (cofre fechado) não recusou nada.
- Repository de uma fatia do cofre devolve `Result<_, ApiErrorDto>`/`UnitResult<ApiErrorDto>`: sem restrições de banco, a recusa da regra é o que a chave única e a chave estrangeira seriam.
- **Consulta que não leu o cofre não decide nada; quem decide é a função passada ao `SaveAsync`.** A `Queries` devolve `bool`, que não carrega a falha de `Read()`: com o cofre fechado no meio da requisição ela responde como um documento vazio, e esse "não" é o mesmo de "não existe". Por isso o handler só recusa por um "sim" da consulta (duplicidade, filhos, descendente) e **nunca responde 404 por um `false`** (nem por `ExistsByID`): a existência da pasta e da pasta pai é dita pelo repository, dentro da gravação, onde o cofre fechado vira 401 `VAULT_LOCKED`. Os repositories (`GetByID`) e o handler de leitura (`Read()` direto, como o `GetFolders`) traduzem a falha com `VaultErrors.From`; uma lista vazia nunca é a resposta do cofre fechado.
- **Conexões (`Prism.Application/Connections`) seguem o mesmo modelo, com duas diferenças.** (1) A `IConnectionQueries` tem o `GetRecordByID`, que devolve `Result<VaultConnectionRecord?, EVaultError>`: a falha `Locked` carrega o cofre fechado (o handler responde 401), e o sucesso com `null` é "não existe" (404), então esta consulta pode decidir um 404 e as de `bool` não. Quem altera, revela, testa, verifica e abre a sessão a usam. E o `IsReadOnly`, do mesmo jeito (`bool?`, nulo é "não existe"), que as rotas de sessão perguntam a cada comando (seção 32). (2) Não há conferência prévia de pasta, de nome nem de existência: tudo isso é decidido só dentro da função do `ConnectionRepository` (reaproveitando `VaultFolders.ExistsByID` para a pasta), porque uma recusa dentro da gravação não regrava mais o arquivo e uma conferência antes não teria o que acelerar.
- **O ambiente da pasta** (RN-PASTA-005: `environmentName` e `environmentColor`, opcionais, no `GET`, `POST` e `PATCH api/user/folders`). As regras são as do ambiente da conexão e moram num lugar só, `Common/Environments/EnvironmentRules` (até 30 caracteres depois do `NormalizeName`, cor `#RRGGBB` aparada e com as letras como vieram, em branco é nulo; as extensões `MustBeAnEnvironmentName` e `MustBeAnEnvironmentColor` levam a mensagem, e o código é de quem valida): os validators e os domínios da conexão e da pasta as aplicam, e o `ConnectionRules` não as tem mais. A recusa da pasta é 422 `FOLDER_NAME_INVALID`, no campo (`EnvironmentName` ou `EnvironmentColor`), o código que a seção 6 já lista. **O `PATCH` grava a pasta por inteiro**, como o da conexão: o ambiente ausente a deixa sem ambiente, e quem só move ou renomeia manda o que ela já tem (a tela faz isso no `folderInputOf`). O "nada mudou" do `UpdateFolderHandler` compara também o ambiente normalizado: o mesmo ambiente com espaços sobrando não regrava o cofre, e trocar só o ambiente grava sem conferir nome nem ciclo (a chave da pasta é a mesma). A herança (a conexão sem ambiente próprio mostra o da pasta mais próxima acima) é só da tela: a API devolve o ambiente próprio de cada uma.
- **A cor da pasta** (RN-PASTA-007: `color`, opcional, no `GET`, `POST` e `PATCH api/user/folders`) é a do ícone dela na árvore, à parte do ambiente: `Folder.Color`, `ChangeColor`, e a regra e a normalização da cor do ambiente (`MustBeAnEnvironmentColor` e `EnvironmentRules.NormalizeColor`), com a recusa em 422 `FOLDER_NAME_INVALID` no campo `Color`. O `PATCH` grava a pasta por inteiro também aqui (sem `color`, a pasta fica sem cor), e o "nada mudou" do `UpdateFolderHandler` compara a cor normalizada. Não passa a subpasta nem a conexão: nenhuma herança.
- **As proteções da pasta e da conexão** (seção 32: `confirmCommands` e `readOnly` nas duas, `protections` na resposta; as regras e a senha em "Proteções e verificação periódica"). O domínio guarda as próprias, já normalizadas (`Folder.ChangeProtections`; na conexão, o record `ConnectionSafeguards`, que junta as proteções e a verificação para o domínio não ter mais cinco parâmetros em cada construção, com o `ToString()` sobrescrito por causa da consulta); as que valem não são do domínio, e saem do documento que a leitura ou a gravação acabou de ver: os repositories devolvem `EffectiveProtections` no `Insert`, no `Update` e no `Duplicate` (e o `GetByID` da pasta devolve a pasta com elas), e o `GetConnectionHandler` lê o cofre direto (`Read()`, como o `GetConnections`), e não mais pela `IConnectionQueries`, porque precisa das pastas acima. O `ConnectionMappingsTests` e o `FolderMappingsTests` fixam as propriedades sem origem automática: `HasPassword` e `Protections` no domínio, e do registro também o que ele guarda nulo no padrão (`ReadOnly`, e na conexão `VerificationEnabled` e `VerificationInterval`). O "nada mudou" do `UpdateFolderHandler` compara também as proteções (o "none" é o nulo), e responde com as que valem da leitura.
- A senha do banco vive no domínio (`Connection.Password`) e no registro do cofre, e em nenhum DTO além do `ConnectionPasswordDto` de revelar (RN-CONN-001). `PATCH` com `password` nulo ou ausente mantém a gravada (RN-CONN-004), enviada tem de ser não vazia; na criação é obrigatória. O comando que carrega senha (`CreateConnectionCommand`, `UpdateConnectionCommand`, `RevealConnectionPasswordCommand`, `ConnectionPasswordDto`) sobrescreve o `ToString()`. O `ID` do comando de revelar vem da rota (`[JsonIgnore]` e `command with { ID = id }`). Revelar faz uma primeira leitura (`GetRecordByID`) só para o 404 de um ID inexistente não gastar uma das cinco tentativas, e **nunca responde com ela**: a senha do banco sai do documento que o `IVaultService.ReadIfPasswordMatchesAsync` entrega junto com a conferência da senha do usuário, e se a conexão não está nesse documento a resposta é 404 `CONNECTION_NOT_FOUND`. Quem conta os erros seguidos e fecha o cofre no quinto é o `VaultService`, pelo `CheckPassword` (privado), o único jeito de conferir a senha do usuário: `ReadIfPasswordMatchesAsync`, `ChangePasswordAsync` e `SaveWithPasswordAsync` o usam, e a contagem é uma só (não há `VerifyPasswordAsync`). `PATCH` sem senha mantém a do documento mais recente: o repository recebe `string? password` à parte e resolve `password ?? existente.Password` dentro da função, porque a senha do domínio é a que o handler leu antes (fora do semáforo) e outra requisição pode ter gravado outra.
- **Duplicar conexão** (RN-CONN-016: `POST api/user/connections/{id}/duplicate`, sem corpo → `DuplicateConnectionHandler` → `ConnectionRepository.Duplicate`). Uma gravação só, sem leitura antes: dentro da função do `SaveAsync` o repository acha a conexão de origem no documento mais recente (404 `CONNECTION_NOT_FOUND` se ela não está lá), escolhe o nome pelo `ConnectionRules.CopyName` ("<nome> (cópia)", depois "(cópia 2)", "(cópia 3)"…, o primeiro livre na pasta pela mesma comparação da RN-CONN-011, com o original cortado para caber nos 80 de `NameMaxLength`, sem partir um caractere e sem espaço antes do sufixo) e acrescenta `Connection.Duplicate` (ID novo, as duas datas de agora, todo o resto igual, a senha inclusive). A senha vai de registro para registro e não passa pela tela nem pela resposta. 201 com a cópia no formato do `GET api/user/connections/{id}` e o `Location` dela. É o único handler da Application que loga: `Information` com os dois IDs (`{ConnectionID}` e `{CopyID}`), pelo `Serilog.ILogger`, nunca nome, host, usuário ou senha.
- **A senha gravada só vai ao servidor para o qual foi gravada** (RN-CONN-004 e 013): `ConnectionRules.SameServer` é a comparação: host EXATO (`Ordinal`) depois de aparado, que é a única normalização que a gravação aplica; porta como número. O servidor que prende a senha é só host e porta: mudar apenas o banco (`engine`), com os dois iguais, mantém a senha gravada. Mudar só as maiúsculas do host conta como mudança e pede a senha: host que começa por `/` é diretório de socket Unix, e `/tmp/pgsock-x` e `/tmp/PGSOCK-X` são diretórios diferentes; e o `OrdinalIgnoreCase` iguala `ς` e `σ`, `µ` e `μ`, que são endereços diferentes (a senha iria a um nome parecido que o atacante resolve). No `PATCH` sem `password`, host ou porta diferentes dos gravados são 422 `CONNECTION_INVALID`, e a recusa mora dentro da função do `SaveAsync` (`ConnectionRepository.Update`), contra o documento mais recente e depois das checagens de existência, pasta e nome: a leitura do handler pode ser de antes de outra alteração. No teste de conexão (com `id` e sem `password`) o handler recusa antes de conectar. Nos dois casos o 422 sai na forma do filtro de validação (`errors` e `errorCodes` com `Password`), para a tela mostrar a mensagem no campo da senha. Os testes provam que a API não conectou com um servidor de mentira (`Api/Support/ConnectionCounter`, que aceita e conta conexões; o mesmo pedido com a senha digitada tem de fazer o contador subir, ou a prova não vale).
- **Regra geral: leitura do cofre fora do semáforo não decide nem responde sobre um dado que dependa de uma conferência ou de uma escrita.** `Read()` e as queries leem sem o semáforo, e o cofre aberto pode ser trocado por outro usuário (`POST api/public/users` deriva a chave por segundos com o anterior ainda aberto) ou fechado no meio da requisição. (1) Quem confere a senha e depois usa um dado do cofre faz as duas coisas pela mesma operação do serviço (`ReadIfPasswordMatchesAsync`), e usa o dado do documento que ela entregou, nunca o de uma leitura anterior. (2) Quem escreve a partir do que leu resolve o que depende do estado atual (existência, unicidade, senha mantida) dentro da função do `SaveAsync`. (3) Quem lê um dado e age com ele fora do semáforo (a Tarefa 10 abre sessões com credenciais lidas do cofre) lê `IVaultService.Generation` ANTES do dado e compara com a de depois; se mudou, abandona. A geração sobe quando o cofre aberto muda (abrir, fechar, trocar de usuário, o quinto erro de senha) e não numa gravação nem numa leitura.
- Registro: `AddRepositories()` e `AddQueries()` no `AddApplication`, um `AddTransient` por interface, em ordem alfabética. O `TimeProvider` (`TryAddSingleton(TimeProvider.System)`) também mora lá.
- Lista inteira, sem paginação, ordenada pelo nome (ordinal, sem diferenciar maiúsculas) e depois pelo ID.

## Scripts salvos (`Prism.Application/Scripts`, seção 23: RN-SCRIPT-001 a 004)

Os scripts são do usuário e moram no documento do cofre (`VaultScriptRecord`: id, nome, SQL, `ConnectionID`, `Database`, datas, o `Icon` e a `Color` da seção 28, e o `FolderID` da seção 33), cifrados como o resto; o modelo é o das conexões, com o cofre no lugar do banco.

- **Rotas** (`UserScriptsController`, `api/user/scripts`; a barreira do cofre as cobre): `GET` a lista em ordem de nome (ordinal, sem diferenciar maiúsculas, e o ID desempata), **sem o SQL** (`ScriptSummaryDto`: `id`, `name`, `connectionID`, `database`, `folderID`, `icon`, `color`, `updatedAt`); `GET {id}` o item com o SQL (`ScriptDto`), 404 `SCRIPT_NOT_FOUND`; `POST` 201 com o `Location` do item e o resumo (sem o SQL: ele pode ter 1 MB, e a tela acabou de mandá-lo); `PATCH` 200 com o resumo; `DELETE {id}` 204. 409 `SCRIPT_ALREADY_EXISTS` no nome repetido, 422 `SCRIPT_NAME_INVALID` (campo `Name`) e `SCRIPT_TOO_LARGE` (campo `Sql`).
- **As regras** (`ScriptRules`, usadas pelos dois validators): o nome tem de 1 a 200 unidades UTF-16 depois do `NormalizeName` (que é o que se grava) e nenhum `char.IsControl` no texto que veio (a tabulação e a quebra de linha são recusadas, e não trocadas por espaço); o SQL tem até 1 MiB (1.048.576) em bytes de UTF-8, a mesma conta da tela, e vai como veio (só o nome é normalizado). O nome único é sem diferenciar maiúsculas (`OrdinalIgnoreCase`) e é decidido só dentro da função do `SaveAsync` (`ScriptRepository`), sem conferência antes. A conexão não é conferida: o script continua do usuário depois de a conexão sair (a tela abre a aba sem conexão).
- **O `PATCH` é parcial**: o que vem ausente ou nulo fica. Renomear manda `name`; gravar a aba por cima manda `sql` e o lugar. **O lugar é um par**: com `connectionID`, conexão e banco são gravados juntos (`database` nulo ou vazio é o banco da conexão); sem ele, os dois ficam, e um `database` sozinho não muda nada (não há banco sem conexão). O mesmo no `POST`. **O script genérico** (RN-SCRIPT-005) é o que não tem conexão: o `POST` sem `connectionID` já o cria, e no `PATCH` quem tira o lugar é `generic: true` (o `UpdateScriptCommand.Generic`, um `bool`), porque a conexão ausente quer dizer "fica". `Script.Change` recebe o `generic` e apaga a conexão e o banco; com ele, `connectionID` ou `database` enviados são 422 `SCRIPT_PLACE_INVALID` no campo (`UpdateScriptValidator`), e o domínio, se chegasse lá, ficaria com o genérico. O registro do cofre já tinha `ConnectionID` opcional: o formato não mudou. Como é parcial, a alteração não pode partir de uma leitura de antes (um renomear e um gravar por cima ao mesmo tempo perderiam um dos dois): o handler não lê nada, e entrega ao repository a alteração do domínio (`IScriptRepository.Update(id, Func<Script, bool>)`), que a roda sobre o registro do documento mais recente, dentro da gravação, e devolve o script depois dela. `Script.Change` diz se algo mudou; nada mudou não carimba a data nem regrava o cofre (a mesma instância).
- **O ícone e a cor** (RN-SCRIPT-006, o "Editar script…" da tela): `icon` e `color` no `PATCH`, no mesmo "ausente ou nulo fica". O ícone é um da lista fechada `ScriptRules.Icons` (`document`, o padrão, `code`, `database`, `table`, `chart`, `clock`, `lightning`, `bug`, `wrench`, `star`, `flag`), **a mesma da tela** (`scriptIcons`, em `saved-scripts.ts`; o teste da tela, `saved-scripts.test.ts`, lê o `ScriptRules.cs` e confere a lista e a ordem, e o daqui confere a lista que a regra tem): ícone novo entra nas duas. `ScriptRules.NormalizeIcon` grava o padrão e o vazio como nulo, para "o padrão" ter uma forma só e o "nada mudou" valer. A cor é a regra da cor do ambiente (`MustBeAnEnvironmentColor`, `EnvironmentRules.NormalizeColor`), e a vazia tira a cor. A recusa dos dois é 422 `SCRIPT_ICON_INVALID`, no campo (`Icon` ou `Color`). O `POST` não os recebe: o script novo nasce com o padrão e sem cor.
- **A pasta do script** (RN-SCRIPT-007, 009 e 010, seção 33): `folderID` no `POST` (o campo "Pasta" do diálogo do nome; ausente ou nulo é a raiz) e no `PATCH`, que continua parcial: `folderID` move o script para a pasta, e o nulo é "fica"; quem leva para a raiz é `root: true` (o `UpdateScriptCommand.Root`, um `bool`, como o `Generic`), e `root` com um `folderID` é 422 `SCRIPT_PLACE_INVALID` no campo `FolderID` (`UpdateScriptValidator`). A mudança de pasta é o `Script.MoveTo(folderID, root, quando)`, à parte do `Change` (o handler roda os dois e grava se um mudou), e não muda mais nada. A pasta que não existe é 404 `SCRIPT_FOLDER_NOT_FOUND`, decidido dentro da gravação (`VaultScriptFolders.ExistsByID`), com o detalhe de cada lugar (`ScriptFolderErrors.ChosenNotFound` no `POST`, "A pasta escolhida não existe mais."; `DestinationNotFound` no `PATCH`, "A pasta de destino não existe mais."); no `PATCH` ela só é conferida quando muda, e mover não confere o nome, que continua único entre todos os scripts (RN-SCRIPT-004).
- **RN-LOG-001**: os commands, o `ScriptDto` e o `VaultScriptRecord` sobrescrevem o `ToString()`; nenhuma linha de log tem o SQL nem o nome. O `ScriptsLogTests` roda a API como processo, passa por todos os caminhos (criar, ler, recusar, gravar por cima, a falha de disco, excluir, e os das pastas de scripts) e confere `logs/`.
- **Testes**: unidade em `Prism.UnitTesting/Scripts` (`ScriptTests`, o domínio, o `MoveTo` inclusive; `ScriptValidatorsTests`; `ScriptRepositoryTests`, a função do `SaveAsync` contra o documento que outra requisição já mudou, e a pasta que outra janela excluiu; `ScriptHandlersTests`) e, no cofre, `VaultServiceTests` (o script não vai em claro para o disco, nem em base64; o cofre nasce no formato atual) e `VaultFormatOneSampleTests`; integração em `Api/ScriptsTests` (as rotas, as recusas, a pasta no `POST` e o mover pelo `PATCH`, o cofre fechado, o arquivo do cofre sem o SQL depois de sair e entrar, e o cofre do formato 1 migrado pela rota de entrada) e `Api/ScriptsLogTests`.

## Pastas de scripts (`Prism.Application/ScriptFolders`, seção 33: RN-SCRIPT-007 a 011)

As pastas da seção Scripts do navegador, à parte das pastas de conexões (`api/user/folders`): não têm ambiente, cor nem proteções, e nada herda delas. Moram no documento do cofre (`VaultDocument.ScriptFolders`, o formato 4 em "O cofre"). O modelo é o dos scripts: nenhuma conferência antes, no handler; tudo dentro da gravação.

- **Rotas** (`UserScriptFoldersController`, `api/user/script-folders`; a barreira do cofre as cobre): `GET` a lista de todos os níveis (`ScriptFolderDto`: `id`, `parentID`, `name`, `createdAt`, `updatedAt`), em ordem de nome (ordinal, sem diferenciar maiúsculas, e o ID desempata; a ordem do português é da tela); `POST { name, parentID? }` 201 com a pasta e o `Location` da lista (não há rota de um item só, como nas pastas de conexões); `PATCH { id, name, parentID? }` 200 com a pasta, gravando-a POR INTEIRO como o das pastas de conexões (sem `parentID` ela vai para a raiz; quem só renomeia manda a pasta pai que ela tem); `DELETE {id}` 204.
- **As regras** (`ScriptFolderRules`, nos dois validators, e `VaultScriptFolders`, as perguntas sobre o documento que a função do `SaveAsync` faz): o nome tem de 1 a 60 unidades UTF-16 depois do `NormalizeName` e nenhum `char.IsControl` no texto que veio (422 `SCRIPT_FOLDER_NAME_INVALID` no campo `Name`); único entre as irmãs sem diferenciar maiúsculas e sem contar a própria pasta (409 `SCRIPT_FOLDER_ALREADY_EXISTS`; uma pasta e um script podem ter o mesmo nome); mover para dentro dela mesma ou de uma descendente é 409 `SCRIPT_FOLDER_CYCLE` (`IsSelfOrDescendant`, com a subida limitada pelas já visitadas); a pasta e a pasta pai que não existem são 404 `SCRIPT_FOLDER_NOT_FOUND`; só a pasta sem subpastas e sem scripts se exclui (409 `SCRIPT_FOLDER_NOT_EMPTY`, com `folders` e `scripts` no corpo, pelo `Contents`). Tudo isso vale contra o documento mais recente: duas janelas não criam duas irmãs de mesmo nome, nem uma exclui a pasta em que a outra acabou de pôr um script (o `ScriptRepository` confere a pasta do script na mesma gravação).
- **O detalhe é a frase da tela** (`ScriptFolderErrors`): as recusas de regra vão ao aviso de erro com o `title` e o `detail` da API (RN-SCRIPT-009), então o detalhe diz o que a especificação escreve: "A pasta pai não existe mais." (o `POST`), "A pasta de destino não existe mais." (o `PATCH`), "Já existe uma pasta chamada <nome> em <caminho da pasta pai>." (`PathOf`, "Fechamento / Mensal"; na raiz, "na raiz da seção Scripts"), "Uma pasta não pode ir para dentro dela mesma nem de uma subpasta dela." e "A pasta <nome> tem 2 subpastas e 3 scripts. Só uma pasta vazia pode ser excluída: …" (o singular, e só a parte que existe, pelo `Contents`).
- **O domínio** (`ScriptFolder`): `Create` normaliza o nome; `Change(nome, pasta pai, quando)` devolve se algo mudou (mudar só as maiúsculas é mudança; o mesmo nome e a mesma pasta pai não carimbam a data e o repository devolve o mesmo documento, que o cofre não regrava). O `IScriptFolderRepository.Update(id, Func<ScriptFolder, bool>)` roda a alteração sobre o registro mais recente, como o dos scripts.
- **O log** (RN-LOG-001): os handlers registram os IDs e as contagens (`Information`: a lista lida com N pastas; a pasta criada, gravada e excluída pelo ID; a recusa da pasta que não está vazia com o ID e as duas contagens), nunca o nome; os commands, o DTO e o `VaultScriptFolderRecord` sobrescrevem o `ToString()`.
- **Testes**: unidade em `Prism.UnitTesting/ScriptFolders` (`ScriptFolderTests`, `ScriptFolderValidatorsTests`, `ScriptFolderRepositoryTests`, a função do `SaveAsync` contra o documento que outra janela já mudou, `ScriptFolderHandlersTests`, com o log, e `ScriptFolderErrorsTests`) e, no cofre, `VaultFormatThreeSampleTests`; integração em `Api/ScriptFoldersTests` (as rotas, as recusas com o detalhe, o `PATCH` que não muda nada e não regrava, a pasta com um script, o cofre fechado, o arquivo do cofre sem o nome em claro e o cofre do formato 3 migrado pela rota de entrada) e `Api/ScriptsLogTests`. O `TestingCore` tem o `ScriptFolderFakers` e, no `VaultFakers`, o `CreateScriptFolder`.

## Abas que voltam na próxima entrada (`Prism.Application/Workspaces`, seção 24: RN-ABAS-006)

As abas abertas de todas as janelas moram no documento do cofre (`VaultDocument.Workspace`), cifradas como os scripts. Uma área de trabalho por usuário: a tela (o processo principal do Electron, que junta as janelas) manda a lista inteira a cada vez, e a gravada troca a anterior.

- **Rotas** (`UserWorkspaceController`, `api/user/workspace`; a barreira do cofre as cobre): `GET` 200 `{ tabs, activeIndex }` (`WorkspaceDto`; nada gravado é a lista vazia e o índice nulo), `PUT` com o mesmo corpo (`SaveWorkspaceCommand`) 204. Cada aba (`WorkspaceTabDto`) tem `kind` e os campos dos dois tipos, os do outro nulos (ou falsos): `query` com `sql`, `connectionID` (nula na aba sem conexão), `database`, `scriptID`, `dirty`, `sqlTooLarge` (o texto passava de 1 MB, não foi gravado, e a aba vem vazia) e `resultPlace` (seção 39, RN-ABAS-016: `panel`, `tab` ou `window`; ausente ou nulo no `PUT` é `panel`, e o `GET` o traz sempre na aba de consulta, também na gravada antes da 0.5.0, que volta como `panel`); `table` com `connectionID`, `database`, `schema`, `table` e `view` (`data`, `structure`, `diagram`), e `resultPlace` nulo.
- **As regras** (`WorkspaceRules`, no `SaveWorkspaceValidator`): 422 `WORKSPACE_INVALID` para a aba que não tem a forma do tipo dela (tipo desconhecido; a consulta sem `sql` ou com campo de tabela; `sqlTooLarge` com texto; a tabela sem conexão, sem esquema, sem nome, com vista desconhecida ou com texto, script ou marca; o `resultPlace` fora dos três valores, que se comparam com a caixa, e qualquer `resultPlace` não nulo na aba de tabela, também o `panel`), o banco fora da regra da abertura de sessão (1 a 128 caracteres, sem caractere de controle), esquema ou tabela acima de 1024 caracteres, a aba nula e o índice da ativa fora da lista (o nulo vale sempre); 422 `WORKSPACE_TOO_LARGE` no campo `Tabs[i].Sql` para o texto acima de 1 MiB em bytes de UTF-8 (`ScriptRules.FitsTheLimit`, a mesma conta dos scripts). A recusa derruba a gravação inteira, e quem grava não é a pessoa: por isso as regras recusam só o que a tela nunca manda (o esquema pode ser vazio, e o nome de tabela incomum passa). O tipo JSON errado (um `connectionID` que não é Guid) é o 400 do MVC, como nas outras rotas.
- **O domínio** (`Workspace`, `WorkspaceTab.CreateQuery` e `CreateTable`) normaliza como o script: o banco só com a conexão (o vazio é o da própria conexão) e a marca de mudança não salva só com o script. A conexão e o script não são conferidos: a tela reabre a aba sem a conexão excluída e sem o script excluído.
- **O lugar do resultado não subiu o formato do cofre** (seção 39 e RN-VERSAO-005). `VaultWorkspaceTabRecord.ResultPlace` está no FIM do registro, com padrão nulo, como o ambiente da pasta: o cofre gravado antes o lê nulo (o mapeamento do `GET` dá `panel`) e a gravação seguinte o escreve. **O rebaixamento foi conferido** contra a 0.4.0 lançada (`c8106cd`, compilada fora da árvore): com a mesma pasta de dados, a API desta versão criou o usuário e gravou três abas (`tab`, uma de tabela e `window`); a 0.4.0 entrou no cofre (200, formato 4), devolveu as três abas sem o campo, gravou de novo (204) e aceitou o `PUT` com o campo (204, o MVC ignora o membro que não conhece); de volta a esta versão, as abas voltaram como `panel`. Quem deixa isso acontecer é a leitura do documento com as opções padrão do `JsonSerializer` (`VaultService`, desde o formato 1): o membro desconhecido é ignorado, na aba, na área de trabalho e no documento. **Não ponha `UnmappedMemberHandling.Disallow` nem `[JsonUnmappedMemberHandling]` nos registros do cofre**: a versão anterior deixaria de abrir o cofre da seguinte. O `VaultWorkspaceResultPlaceTests` prova as duas pontas com cofres montados à mão (o da 0.4.0, sem o campo, e um com membros que nenhuma versão tem).
- **O repository** (`WorkspaceRepository.Replace`) grava pela função do `SaveAsync`, sem regra de concorrência (a última gravação fica); a mesma área de trabalho de novo (os registros são records só de valores, e a igualdade gerada compara campo a campo) devolve o documento que recebeu, e o cofre não é regravado: a tela grava a cada mudança e antes de o cofre fechar, e muitas vezes nada mudou.
- **O log** (seção 24 e RN-LOG-001): os dois handlers registram só a contagem (`Information`, "Área de trabalho lida com {TabCount} abas." e "Área de trabalho gravada com {TabCount} abas."), pelo `Serilog.ILogger`; os commands, os DTOs, o domínio e os registros do cofre sobrescrevem o `ToString()`. O `WorkspaceLogTests` roda a API como processo, passa por gravar, ler, as duas recusas (com as marcas dentro) e a falha de disco, e confere `logs/`.
- **Testes**: unidade em `Prism.UnitTesting/Workspaces` (`WorkspaceTests`, `WorkspaceValidatorTests`, `WorkspaceRepositoryTests`, `WorkspaceHandlersTests`) e, no cofre, `VaultServiceTests` (as abas não vão em claro para o disco; o cofre nasce sem abas), `VaultFormatTwoSampleTests` e `VaultWorkspaceResultPlaceTests`; integração em `Api/WorkspaceTests` (as rotas, as recusas, a mesma área de trabalho que não regrava, o cofre fechado, o arquivo sem o SQL nem os nomes em claro depois de sair e entrar, e o cofre do formato 2 migrado pela rota de entrada) e `Api/WorkspaceLogTests`. O `TestingCore` tem o `WorkspaceFakers` (os DTOs) e, no `VaultFakers`, `CreateQueryTab`, `CreateTableTab` e `CreateWorkspace` (os registros).

## Exportar e importar conexões (seção 34: RN-TRANSF-001 a 016)

Quem monta e quem lê o arquivo é a API; a tela recebe o arquivo cifrado e o grava, e na importação manda o texto dele de volta. Nada da importação fica na API entre um pedido e outro: cada pedido (a prévia, cada atualização dela, a importação) lê e deriva de novo.

- **O arquivo** (`Prism.Infrastructure/ConnectionFiles`, RN-TRANSF-007 a 010): `IConnectionFileService` (público, `Singleton`) sobre o `ConnectionFileClient` (o único `try`, no `Send`) e o `VaultCrypto` do cofre, sem a chave do cofre no meio: a chave sai da senha de exportação por Argon2id (os parâmetros das `ConnectionFileOptions`, 64 MiB, 3 e 4, gravados no cabeçalho; sal novo de 16 bytes a cada exportação) e cifra o conteúdo direto com AES-256-GCM. O texto é um JSON (`ConnectionFile`: `kind` `prism-connections`, `version` 1, `kdf` e `payload`, nos nomes do cabeçalho do cofre). O dado autenticado é `prism-connections|<versão>|<algoritmo>|<memória>|<passadas>|<paralelismo>|<sal>` (`ConnectionFileFormat`): um arquivo de exportação nunca abre como cofre, nem o contrário. `SealAsync(conteúdo, senha)` serializa em camelCase, cifra e zera o JSON em claro e a chave, na saída de um `using` (`Wipe`, sem `try`/`finally`), também quando a serialização ou a cifra lançam; `OpenAsync(texto, senha, leitura)` lê o cabeçalho SEM derivar (`Invalid`: não é JSON, `kind` errado, `version` que não é um inteiro escrito como tal, de 1 até o conhecido; `Newer`: inteiro maior, lido antes do resto do cabeçalho, também com o resto numa forma desconhecida; `Invalid` de novo: o cabeçalho fora da forma ou dos limites do `VaultHeaderLimits`, ou um base64 que não decodifica), deriva com os parâmetros do próprio arquivo, abre (`WrongPassphrase`, a MESMA recusa para a senha errada e para o arquivo alterado, em qualquer byte do conteúdo, da tag, do nonce ou valor do cabeçalho que passe pelos limites) e entrega o conteúdo como `JsonElement` à função de leitura, sobre o buffer em claro, que é zerado na saída do `using` (também quando a leitura lança); a chave também, do mesmo jeito. O JSON que não lê é `Invalid`, e o log recebe só o tipo da exceção (a mensagem de um `JsonException` traz um pedaço do texto). **A fila das derivações** (RN-TRANSF-008) é um `SemaphoreSlim` do serviço: uma derivação do arquivo por vez em toda a API, fora da trava do cofre; quem desiste esperando a vez (a requisição abortada) não deriva. **A derivação entra pelo construtor** (`VaultCrypto.DeriveKey` em produção), como a do `VaultService`: os testes usam uma barata e contam as chamadas.
- **As regras dos campos, num lugar só** (RN-CONN-010 e RN-PASTA-001, seção 34): `Common/Texts/TextRules` (o caractere de controle, U+0000 a U+001F e U+007F a U+009F, e o de direção do texto, U+200E, U+200F, U+202A a U+202E e U+2066 a U+2069; o corte sem partir um caractere; e a extensão `MustPass`, que aplica no validator uma função que devolve o motivo ou nulo, com a frase dela), `Folders/Models/FolderRules.NameRefusal`, `ConnectionRules.NameRefusal`, `HostRefusal` (até 255), `PortRefusal`, `DatabaseRefusal` (até 128), `UserNameRefusal(…, required)` (até 128), `PasswordRefusal` (até 1.024, contada como veio), `VerificationQueryRefusal` (o caractere de controle e o de direção do texto também, menos a tabulação e as quebras de linha, `HasControlOrDirectionBesidesLineBreaks`) e `EnvironmentRules.NameRefusal` e `ColorRefusal`. Os validators de criar e de alterar pasta e conexão e o do teste as aplicam, e a importação as chama direto, com a mesma frase.
- **A conexão sem usuário e senha** (RN-TRANSF-015): fica no cofre com os dois vazios (o formato não muda; `hasPassword` já era falso para a senha vazia). Só a importação a cria: o `CreateConnectionValidator` e o `TestConnectionValidator` exigem o usuário. O `UpdateConnectionValidator` deixa o usuário vazio passar, e quem decide é o `ConnectionRepository.Update`, dentro da gravação, contra o documento mais recente: vazio só na conexão gravada já sem usuário (o "Renomear" e o "Mover" mandam o que ela tem), e 422 `CONNECTION_INVALID` em `UserName` ("Informe o usuário do banco.", `ConnectionErrors.UserNameRequired`) na que tem um. A senha ausente mantém a gravada, que é a vazia. As recusas ao conectar e ao testar estão em "Rotas de sessão, catálogo e consulta".
- **A senha de exportação** (`ConnectionTransfers/Models/PassphraseRules`, RN-TRANSF-004 e 009): na forma NFC antes de contar e de usar; de 12 a 128 unidades UTF-16, sem espaço nas pontas pela lista da especificação (`IsSpace`: U+0009 a U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000 a U+200A, U+2028, U+2029, U+202F, U+205F e U+3000; não o `Trim()`, que tiraria outros, e o U+FEFF fica) e sem `char.IsControl`, com as cinco frases na ordem (422 `EXPORT_PASSPHRASE_INVALID` em `Passphrase`). Na importação ela perde os espaços das pontas pela mesma lista e passa à NFC (`ForImport`), e só é recusada vazia ou acima de 128 (`IMPORT_PASSPHRASE_INVALID`). Nunca é gravada nem vai a log.
- **Exportar** (`POST api/user/connections/export`, `UserConnectionTransfersController`, corpo até 1 MiB → `ExportConnectionsHandler`; RN-TRANSF-003 a 008). O validator recusa, nesta ordem, nada marcado (`EXPORT_EMPTY`), a escolha fora de `none`/`user`/`userAndPassword` (ausente ou nula é `none`), a conexão nula e o mesmo ID duas vezes (`EXPORT_INVALID`), as listas acima de 2.000 (`EXPORT_LIMITS_EXCEEDED`) e a senha de exportação. O handler lê a `Generation`, lê o cofre UMA vez e confere nele (`ExportPlanner.Plan`): a pasta ou a conexão que sumiu é 404 `FOLDER_NOT_FOUND` ou `CONNECTION_NOT_FOUND`; as pastas que vão são as marcadas e as do caminho de cada item até a raiz, cada uma uma vez, na ordem da árvore; 2.000 conexões, 2.000 pastas e 32 níveis contados da raiz do navegador (`EXPORT_LIMITS_EXCEEDED`). Tudo isso antes da senha do Prism, que só é pedida quando uma conexão vai com `userAndPassword` E tem usuário e senha gravados (a sem senha leva só o usuário, e a sem usuário nada, sem erro): sem ela, 422 `USER_PASSWORD_REQUIRED` em `UserPassword`, sem conferir; com ela, o `ReadIfPasswordMatchesAsync` de sempre (a mesma contagem de cinco erros da revelação, da troca de senha e do somente leitura: errada é `INVALID_PASSWORD` em `UserPassword`, e o quinto erro é 401 `VAULT_LOCKED`); a senha de exportação igual à do Prism que veio e conferiu (as duas em NFC) é `EXPORT_PASSPHRASE_INVALID` em `Passphrase`; e o plano é refeito no documento que a conferência devolveu, de onde o arquivo sai. A senha do Prism que vem sem ser pedida não é conferida. `ExportPlanner.Build` monta o conteúdo (`TransferFileContent`: as chaves `f1`, `c1`…, o banco pelo nome, o usuário e a senha só quando vão, com `JsonIgnore` quando nulos, a verificação como vale e o `effective` de cada item, de `ProtectionRules.Of` e `EnvironmentRules.ShownBy`); a cifra roda na fila; a geração que mudou durante a derivação descarta o arquivo (401 `VAULT_LOCKED`), conferida antes do tamanho, para o cofre que fechou nunca responder outra coisa; e o arquivo acima de 5 MiB é `EXPORT_LIMITS_EXCEEDED`. Nada é gravado no cofre. Resposta 200 `{ content, folders, connections, withUser, withPassword }`.
- **A leitura do arquivo** (`ImportFiles.OpenAsync`, a mesma na prévia e na importação; RN-TRANSF-010): o validator confere antes, sem derivar, o texto até 5 MiB em UTF-8 (`IMPORT_LIMITS_EXCEEDED` em `Content`) e a senha (`IMPORT_PASSPHRASE_INVALID` em `Passphrase`); o serviço lê o cabeçalho e abre (`TransferErrors.From`: `IMPORT_FILE_INVALID` em `Content`, 409 `IMPORT_FILE_NEWER`, `IMPORT_PASSPHRASE_WRONG` em `Passphrase`); `ImportedFile.Read` lê o conteúdo campo a campo, sobre o buffer em claro (só a falta ou o tipo errado das listas, de um item, da `key` e do pai recusam o arquivo; as contagens, 2.000 e 2.000, vêm antes de guardar os itens); e `ImportAnalysis.Analyze` confere a estrutura (as chaves de 1 a 64 e únicas, comparação exata, ANTES de qualquer dicionário; as referências; os ciclos; os 32 níveis, `IMPORT_LIMITS_EXCEEDED`) e depois cada item com as regras da criação (`FileValue` guarda o campo como veio: o tipo errado ou a falta de um obrigatório tira só o item, com a frase da regra, e a pasta que não passa leva junto o que está dentro dela, "A pasta X não pode ser importada."). De cada item que passa sai o que valia nele na origem (`ImportOrigin`): o mais forte entre o `effective` do arquivo e o que as pastas do arquivo dão, e o ambiente próprio, o do `effective` ou o da pasta mais próxima acima que tem um. A senha errada não toca o cofre e não conta erro nenhum.
- **A prévia** (`POST api/user/connections/import/preview`, corpo até 6 MiB → `PreviewConnectionsImportHandler`; RN-TRANSF-011): lê a `Generation`, abre o arquivo, lê o cofre e confere a geração (mudou durante a derivação: 401 `VAULT_LOCKED`, porque a prévia diz o que há no cofre aberto; o lugar que não existe mais é 404 `FOLDER_NOT_FOUND`) e roda a mesma conta da importação (`ImportPlacement.Place`) com tudo o que pode ser importado marcado e "Importar com outro nome", sem gravar. Responde `ImportPreviewDto` (`folders` e `connections` com `existing`, `conflict`, `copyName`, `strengthened`, `invalid`, `effective`; o banco pelo número, nulo quando este Prism não o conhece; `userName` vazio quando não veio, `hasPassword`, e nunca a senha). O texto do item importável vem como seria gravado; o do não importável, como veio, cortado em 200.
- **Importar** (`POST api/user/connections/import`, corpo até 6 MiB → `ImportConnectionsHandler` e `ConnectionImportRepository`; RN-TRANSF-012 a 014): o validator recusa, antes de derivar, nenhuma chave (`IMPORT_EMPTY`), a chave nula ou repetida, mais de 4.000 e o `onConflict` fora de `rename`/`skip` (`IMPORT_INVALID`); a chave que o arquivo não tem só se sabe depois de abri-lo (`IMPORT_INVALID` em `Items`), e a de um item não importável é ignorada. A gravação é UMA (`SaveOrRefuse`), e tudo o que outra janela pode ter mudado é decidido dentro dela, contra o documento mais recente: a geração lida antes de abrir o arquivo (mudou: 401 `VAULT_LOCKED`, nada gravado), o lugar (404), e o `ImportPlacement.Place`: as pastas do caminho de cada item marcado vão sozinhas, cada pasta antes do que está dentro dela; a de mesmo nome no mesmo lugar (sem diferenciar maiúsculas, o nome normalizado, como a RN-PASTA-002, também entre duas irmãs do próprio arquivo) é a que existe, que não muda; a conexão de nome tomado (pelo que existe e pelo que a importação já pôs) vai com o `ConnectionRules.CopyName` ou fica de fora; o domínio cria cada item (`Folder.Create`, `Connection.Create`: IDs novos, a normalização e as datas da criação); e nada fica mais fraco que na origem: o somente leitura e a confirmação da origem são gravados no item (na conexão e na pasta criada) quando ali valeriam menos (`ProtectionRules.Of` sobre as pastas que já existiam e as criadas), e o ambiente da origem na conexão sem ambiente próprio que ali herdaria outro (pelo nome, sem diferenciar maiúsculas) ou nenhum. Sem a caixa "Manter as consultas de verificação do arquivo" (`keepVerificationQueries`, falsa quando ausente), a consulta própria vira a do banco. Criar assim não pede a senha do Prism. Nada criado devolve o mesmo documento (o cofre não é regravado). Resposta 200 `{ folderIDs, connectionIDs, mergedFolders, renamed, skipped }`.
- **RN-LOG-001**: os handlers registram só as contagens e os IDs (`Information`), e a recusa só com o código; os commands, as respostas, a prévia e todo record que carrega o arquivo, uma senha, um host ou um usuário (`TransferFileContent`, `ImportedConnection`, `FileValue`, `ConnectionCandidate`…) escrevem só o nome do tipo no `ToString()`.
- **O formato 1 é contrato** (RN-VERSAO-002): `tests/Prism.UnitTesting/ConnectionTransfers/Samples/connections-format-1.prismconexoes` foi gerado pelo código (o `ExportPlanner` e o `ConnectionFileService`, com o Argon2id pequeno, 8 MiB e uma passada, que o cabeçalho registra), com dados inventados e hosts `.invalid`, e a senha de exportação fictícia que o `ConnectionFileFormatOneSampleTests` guarda; não se regera. Um campo novo e opcional vai dentro do conteúdo cifrado e não sobe o número; o número sobe quando um Prism mais antigo leria o arquivo errado.
- **Testes**: unidade em `Prism.UnitTesting/ConnectionFiles/ConnectionFileServiceTests` (a cifra, o cabeçalho, cada recusa e quantas derivações custou, a fila, o cancelamento na fila, o zeramento da chave, também quando a serialização ou a leitura lançam) e em `Prism.UnitTesting/ConnectionTransfers` (`TransferFixtures`, com a derivação barata e o conteúdo montado à mão; `PassphraseRulesTests`, `ExportPlannerTests`, `ExportConnectionsValidatorTests`, `ExportConnectionsHandlerTests`, `ImportAnalysisTests`, `ImportPlacementTests`, `ImportHandlersTests`, `TransferErrorsTests` e o exemplo do formato 1), mais `Common/TextRulesTests` e os validators, repositories e handlers de pastas, conexões e sessões. Integração (sem banco) em `Api/ConnectionTransfersTests` (as rotas de ponta a ponta, as recusas no campo, os cinco erros, a senha de exportação errada que não fecha o cofre, a conexão sem usuário e senha recusada antes do driver, o corpo acima do teto) e `Api/ConnectionTransfersLogTests` (a API como processo, e o `logs/` sem nada do arquivo, das senhas e dos dados das conexões). O `ApiHost` reduz também as `ConnectionFileOptions`.

## Importar do DBeaver (seção 40: RN-DBEAVER-006 a 018; rotas `api/user/connections/dbeaver`)

O processo principal copia os arquivos do DBeaver para `transfers/<sourceId>.dbeaver/` (um `manifest.json` e uma subpasta `1` a `50` por projeto) e a tela só recebe o `sourceId`. Quem lê, decifra e traduz é a API; nada é decifrado na tela nem no processo principal, nada sai do computador, e nenhuma senha vai à resposta (a prévia diz só `hasPassword`). Cada pedido (contagem, prévia, importação) lê a cópia e decifra de novo; a API não guarda nada entre um e outro.

- **A cópia e a cifra** (`Prism.Infrastructure/DbeaverSources`, a quinta integração, com o único `try` no `Send` do `DbeaverSourceClient`): o client lê o manifesto (versão 1, `where`, projetos; pasta que não é `1` a `50` ou repetida é ignorada) e, de cada projeto, SÓ os cinco nomes de arquivo conhecidos (`data-sources[-sufixo].json`, `credentials-config[-sufixo].json`, `project-settings.json`; sufixo de 1 a 64 caracteres), até 41 por projeto e 5 MiB cada, sem seguir atalho; o que passa do limite ou não abre vem com `Content` nulo. `ReadJson` lê um JSON até 64 níveis e sem comentários (o `JsonException` vira "nenhum valor", nunca a mensagem). `DbeaverCrypto` é o AES-128 em CBC com PKCS #7 do DBeaver Community: a chave é a constante pública `PublicKeyHex` (a do `LOCAL_KEY_CACHE` do `BaseProjectImpl`, que o `openssl` do dono também usa; seção 8, item 9, do guia da raiz), o IV são os 16 primeiros bytes e o arquivo com menos de 32 bytes ou fora do múltiplo de 16 não se decifra. O buffer em claro e a cópia da chave são zerados (`Wipe`), também quando a leitura falha, e o `credentials-config` em memória é zerado depois de lido. `IDbeaverSourceService` (público, `Singleton`) assina o `Locked` do cofre e apaga as cópias prontas; `TransferFileClient.Prepare` apaga, na partida, as pastas `*.dbeaver` e `*.dbeaver.part` com o que têm dentro (não só os arquivos). O `IDatabaseSessionService.HasSession` diz se a conexão está conectada em qualquer janela (`existing.connected`).
- **A leitura** (`Prism.Application/DbeaverImports/Models`): `DbeaverProjects.Read` faz o `project-settings` primeiro (`secureProject`: o projeto não é lido; só `useProjectPassword`: lê, sem abrir o `credentials-config`), depois cada `data-sources*.json` (o `data-sources.json` primeiro e os outros em ordem ordinal; o ID repetido fica de fora com "O ID desta conexão se repete no projeto."; o ID vazio, com mais de 128 caracteres ou com caractere de controle é recusado, já que vai para a origem; a conexão com `origin` nem aparece; o caminho de pastas com mais de 64 níveis ou 4.096 caracteres não é aberto em pais, nem o conjunto passa de 2.001 pastas: a conexão fica sem pasta e recusada, e o projeto fica `PathsOverLimit`, que a prévia e a importação respondem como `DBEAVER_LIMITS_EXCEEDED` e a contagem ignora) e o `credentials-config` do par pelo sufixo (ausente ou 0 byte é silêncio; o que não decifra marca `CredentialsUnreadable`). `DbeaverConnections.Map` traduz uma conexão para a forma do arquivo do Prism (`FileValue`): o banco pelo `provider` e pelo `driver` (PostgreSQL `postgresql` com `postgres-jdbc` ou `postgresql`, Db2 `db2` com `db2`, Informix `generic` com `informix`; os outros dão "O Prism ainda não tem este banco (X)."), o host, a porta e o banco pelos campos ou pela URL (`DbeaverJdbcUrl`; porta padrão 5432 e 50000, `postgres` como banco padrão do PostgreSQL, o resto recusa), o usuário e a senha (o `configuration` não vazio vence o `#connection`; a senha sem usuário não vem; `auth-model` que não é `native` não traz nada, e o `postgres_pgpass` traz o usuário), a variável `${…}` recusa, e o que fica de fora (`LeftOut`, na ordem da especificação). **A URL que não casa** mostra só `DbeaverJdbcUrl.Beginning` (até antes do primeiro `/`, `?`, `;` ou `,` depois do `//`; só o esquema com um `@` em QUALQUER lugar depois do `//` (a senha pode ter o caractere do corte), com um trecho que não é `host` nem `host:porta`, ou sem `//`; e só se o que vem antes do `//` tem a forma `jdbc:<subprotocolo>:`): é o ÚNICO pedaço da URL que chega à resposta e ao log. `DbeaverEnvironments` põe o tipo de conexão como ambiente (`dev`, `test` e `prod` pelo ID, com o nome em português; nome de 30 caracteres; cor da conexão antes da do tipo; branco é sem cor), `confirm-execute` como "Todos os comandos" e `read-only` ou `permission-restrictions` como somente leitura.
- **A montagem** (`DbeaverAssembly`): põe o que foi lido na forma do `ImportedFile` (as chaves `p<posição do projeto>`, `f<posição>_<i>` e `c<posição>_<i>`, estáveis para a mesma cópia e as mesmas escolhas e as mesmas de um projeto em "Todos os projetos" e escolhido sozinho, para a tela manter as marcas ao trocar o projeto; o projeto que não é o `General` vira uma pasta de nome cortado em 60; os limites de 2.000 conexões, 2.000 pastas e 32 níveis dão `DBEAVER_LIMITS_EXCEEDED`, e a contagem os ignora) e segue pela análise e pela colocação do "Importar conexões" (`ImportAnalysis`, com `SourceRefusal` e `checkDepth`, e `ImportPlacement`), que não mudaram. A **porta DRDA do Informix** (`drdaPorts`, adição à RN-DBEAVER-010) troca a `Port` da conexão no `FileValue`, por servidor do DBeaver (host, porta SQLI e `INFORMIXSERVER`, comparados como vêm); `dbeaverPort` é sempre a SQLI e `drdaPort` a aplicada.
- **A reimportação** (`DbeaverReimport`, `DbeaverPlacement`): "já existe" é a mesma origem (`Origin`, o projeto sem diferenciar maiúsculas e o ID do DBeaver; com mais de uma, a primeira na ordem da árvore); ela não é conflito de nome nem entra na colocação. `Plan` diz o que sobrescrever muda e é a mesma conta da prévia e da gravação: nome (fica o do Prism se o novo está tomado na pasta), banco, host, porta (no Informix, a do Prism fica, a menos que `drdaPort` tenha sido preenchida), banco de dados, usuário, senha (só a do DBeaver; a do Prism só continua para o mesmo servidor e usuário) e ambiente; ficam o ID, a pasta, a verificação, a criação e a origem; as proteções só aumentam (sem pedir a senha do Prism). `DbeaverPlacement.Apply` roda DENTRO da gravação, contra o documento mais recente: a chave de `overwrite` que já não existe vira conexão nova, a que existe e não está em `overwrite` não é importada nem tocada, e a conexão criada guarda a origem. Na mesma gravação o cofre ganha `Dbeaver.InvitedAt` (sem trocar a data de um convite anterior) e `LastImportAt`; sem nada criado nem atualizado devolve a mesma instância (o cofre não é regravado).
- **O cofre** (RN-DBEAVER-018, sem subir o formato 4): `VaultConnectionRecord.Origin` (`VaultConnectionOrigin`: `Source` `dbeaver`, `Project` até 255, `ID` até 128) e `VaultDocument.Dbeaver` (`VaultDbeaverRecord`: `InvitedAt` e `LastImportAt`, em UTC), os dois opcionais e no fim do record. O leitor é o `JsonSerializer` com as opções padrão, o mesmo da 0.4.0, que ignora o membro que não conhece: `VaultDbeaverFieldsTests` prova nos dois sentidos (o cofre da 0.4.0 abre aqui, e o gravado aqui abre nos records da 0.4.0). Editar, renomear e mover mantêm a origem (`ConnectionRepository.Update`); duplicar e exportar não a levam. `GET api/user/connections/dbeaver` devolve `{ invitedAt, lastImportAt }` e `PUT .../invite` grava o convite (204).
- **As rotas** (`UserDbeaverImportsController`, corpo até 1 MiB, atrás da barreira do cofre): `POST .../dbeaver/scan` `{ sourceId }`; `POST .../dbeaver/import/preview` `{ sourceId, project?, targetFolderID?, withPasswords?, drdaPorts? }`; `POST .../dbeaver/import` com mais `items`, `onConflict` e `overwrite`. `sourceId` fora do formato de 36 caracteres em minúsculas, `withPasswords` que não é booleano e `drdaPorts` mal formadas são 422 `IMPORT_INVALID` no campo; `DBEAVER_SOURCE_MISSING` (404), `DBEAVER_PROJECT_NOT_FOUND` (404), `DBEAVER_SOURCE_INVALID` e `DBEAVER_LIMITS_EXCEEDED` (422). A importação apaga a cópia quando termina com sucesso (também a que não criou nem atualizou nada) e quando o cofre falha (`VAULT_LOCKED`, `VAULT_UNAVAILABLE`); as outras recusas a deixam. **Campos além da lista da especificação**: `existing.host`, `existing.port`, `existing.database`, `existing.userName` e `existing.environmentName` (o que a conexão do Prism tem hoje, para a pergunta de sobrescrever dizer "host a → b"; nunca a senha), `authModel` (o modelo de autenticação, para "o login do DBeaver (<modelo>)") e `notes.unreadableProjects` (os projetos que ficaram de fora por inteiro, também em `unreadableFiles`).
- **RN-LOG-001**: os commands, as portas DRDA, os resultados, a cópia lida, as conexões traduzidas e o `DbeaverItem` escrevem só o nome do tipo no `ToString()`; os logs levam o `sourceId`, as contagens, os códigos do que ficou de fora e os IDs criados e atualizados, nunca nome, host, usuário, senha, ID do DBeaver, projeto ou caminho (`DbeaverImportsLogTests` roda a API como processo e procura tudo isso em `logs/`).
- **Testes**: unidade em `Prism.UnitTesting/DbeaverImports` (`DbeaverJdbcUrlTests`, `DbeaverEnvironmentsTests`, `DbeaverConnectionsTests`, `DbeaverSourceClientTests`, `DbeaverProjectsTests`, `DbeaverPreviewTests`, `DbeaverImportTests`, `DbeaverStateTests` e `VaultDbeaverFieldsTests`), com o DBeaver SINTÉTICO de `Prism.TestingCore/Fakers/Dbeaver` (`DbeaverWorkspace`, escrito à mão com hosts `.invalid` e senhas inventadas; o `credentials-config` é cifrado no próprio teste com um IV conhecido ou sorteado). O arquivo real do dono nunca entra no repositório. Integração, sem banco, em `Api/DbeaverImportsTests` e `Api/DbeaverImportsLogTests`.

## Exportação de dados em segundo plano (seção 35: RN-EXPORT-001, 002, 006 a 014, 016 a 018 e 024; rotas `api/user/transfers`)

A exportação de dados é a primeira transferência: um trabalho em segundo plano, numa conexão à parte com as credenciais do cofre, que escreve um arquivo temporário na pasta de dados; a tela consulta o trabalho e, no fim, o processo principal do Electron leva o arquivo ao destino (ou o texto à área de transferência). A API nunca recebe nem escreve o caminho do destino. A importação e a cópia (seção 36) entram no mesmo registro, com `kind` próprio; a exportação de **conexões** (seção 34) é outra coisa, numa rota só dela.

- **O `read` da página** (RN-EXPORT-001 e 002). A página de `queries` e de `queries/next` leva `read`: o comando como foi executado (com o filtro junto, RN-GRADE-011) é uma leitura só pela regra do somente leitura (`ReadOnlySql.ExportRefusal`, a mesma da RN-PROT-005, com um comando só) e não gravou (`TotalRows` nulo). É calculado uma vez, no `DatabaseSessionService`, e guardado no `ResultState`. A tela só oferece "Exportar…" com `read`; a API confere de novo no começo do trabalho (`ExportSql`).
- **O comando** (`Databases/Clients/ExportSql`, público, como o `ReadOnlySql`). A tabela pelo navegador vira `SELECT "a", "b" FROM "esquema"."tabela"`, só das colunas marcadas, na ordem, com a aspa de dentro dobrada, sem filtro nem ordem. Os Registros e o resultado mandam o `sql` como foi executado e o `filter` do resultado, que entra como no `queries` (`SqlFilter.Apply`); a recusa é, nessa ordem, `MULTIPLE_STATEMENTS_NOT_SUPPORTED` (`ReadOnlySql.HasSeveralStatements`, pelo dialeto do banco; no Db2 também pela leitura do driver), `FILTER_INVALID` e `EXPORT_SOURCE_NOT_READ` (detalhe "Exportar executa o comando de novo, e só se exporta uma leitura: {motivo}. Nada foi enviado ao banco.", e o motivo também na extensão `reason`). Tudo sem ir ao banco.
- **O começo** (`StartExportHandler`, na ordem da RN-EXPORT-016). Antes de tudo, o validator (`StartExportValidator` sobre `ExportRequestRules`): a forma do pedido e as faixas da seção 6, todas de uma vez, com `EXPORT_OPTIONS_INVALID` no campo, **pelo caminho em camelCase** (`source.sql`, `columns`, `format`, `options.minWidth`, `output.entryName`, `windowID`), como a seção 6 o escreve; as opções de cada formato são lidas à mão do `JsonElement` (`ExportOptionsReader`), com o padrão do Prism no que não vem, para o tipo errado ser a mesma recusa no campo (e não o 400 do MVC). Depois, no handler: a geração do cofre (lida **antes** das credenciais e levada ao registro) → a conexão (404 `CONNECTION_NOT_FOUND`, 401 `VAULT_LOCKED`) → `database` pela regra da abertura de sessão (`DATABASE_NAME_INVALID`, sem campo) → usuário e senha gravados (`CONNECTION_CREDENTIALS_MISSING` no campo `userName` ou `password`, com a frase do assistente) → o driver (`IDriverService.RefusalFor`, com a tradução do `DatabaseSessionErrors.From`: `DRIVER_NOT_INSTALLED` com `driverID`) → o comando (`ExportSql`) → no Informix, `rowsPerStatement` acima de 1 (`EXPORT_OPTIONS_INVALID` no campo `options.rowsPerStatement`) → o registro (409 `TRANSFER_LIMIT_REACHED`, 401 `VAULT_LOCKED` se o cofre mudou desde a leitura da geração). A conexão é lida de novo depois de o trabalho entrar: excluída nesse meio, o trabalho é cancelado e esquecido (dois `DeleteAsync`) e a resposta é 404. Os dez formatos da lista têm escritor. O validator recusa também, no campo `columns`, o que o assistente já não deixa passar da Extração: no SQL, duas colunas de mesmo nome ("O resultado tem duas colunas chamadas id: deixe uma de fora na Extração.", pela comparação ordinal, como o banco compara o nome entre aspas); no XLSX, mais de 16.384 colunas ("…deixe 1.216 de fora na Extração, ou escolha outro formato."). Só quando as colunas passaram pelas regras da seção 6.
- **As rotas** (`UserTransfersController`). `POST api/user/transfers/exports` (corpo até 8 MiB) 202 `{ id }`. `GET api/user/transfers` 200 com os trabalhos do cofre aberto, de todas as janelas, em ordem de início (não conta como consulta). `GET api/user/transfers/{id}` 200 com o trabalho (a consulta o mantém vivo) ou 404 `TRANSFER_NOT_FOUND`. `DELETE api/user/transfers/{id}` 204: o que roda é cancelado (motivo `person`) e a resposta vem quando ele parou, ou em 10 s (o prazo começa no pedido: o `CancelAsync` não é esperado, porque o `Cancel` da conexão meio aberta pode ficar preso na rede); o que terminou `done` apesar do cancelamento é esquecido na hora, porque a tela já o deu por cancelado; o que terminou (também o cancelado) é esquecido e o arquivo sai; 404 para o que não existe. O item (`TransferDto`) tem sempre todas as chaves (o que a importação e a cópia acrescentam está na seção delas): `id`, `kind` (`export`), `connectionID`, `targetConnectionID` (nulo), `windowID`, `state` (`running`, `done`, `failed`, `canceled`), `phase` (a última pela qual passou: `connecting`, `counting`, `reading`, `finishing`), `rows`, `committed` (nulo), `total` (nulo sem contagem ou com a contagem recusada), `bytes`, `size` (nulo), `uncertain` (falso: a exportação não grava no banco; seção 36), `summary` (`{ rows, bytes, sheets, cutValues, removedCharacters, skippedRows }` e as chaves da importação, zero ou falso, só no `done`; as contagens são 0 e `sheets` é nulo fora do XLSX), `error` (`{ code, message, sqlState }` e as chaves da importação, nulas, só no `failed`), `reason` (`person` ou `connectionDeleted`, só no `canceled`), `startedAt` e `finishedAt` em UTC.
- **O registro** (`Transfers/Services/TransferService`, `Singleton`, criado na subida pelo `UseApi`). Até 3 trabalhos em andamento (`running`; o que terminou não conta). Cada um roda num `Task.Run` com a conexão só dele e guarda a geração do cofre: o cofre que fecha (o evento `Locked`) cancela e esquece os de outra geração, e o cofre seguinte não os vê. Um temporizador do `TimeProvider` confere o registro a cada 15 s: o trabalho que ninguém consulta (`GET` do item) há 5 minutos é cancelado e esquecido, em qualquer estado; o que roda sem progresso (uma fase nova ou um lote escrito) há 2 horas termina na hora como `failed` `EXPORT_STALLED`, mesmo que a conexão não responda ao cancelamento. Excluir a conexão (`DeleteConnectionHandler`, depois da exclusão gravada) cancela os trabalhos dela com `connectionDeleted` (na cópia, também os em que ela é o destino). A API que encerra cancela tudo e espera até 10 s. Quem apaga o arquivo do trabalho que sai do registro (esquecido, abandonado, do cofre que fechou, a API encerrando) se decide sob a trava, pelo `Closed` que o fim do trabalho marca depois de fechar o arquivo: antes dele, o fim apaga; depois, quem tirou o trabalho apaga (nunca pelo `Task.IsCompleted`, que só vem depois do log do fim). Os prazos ficam em `TransferSettings` (interno), e os testes os trocam.
- **A leitura** (RN-EXPORT-017, `IDatabaseConnection.BeginExportAsync`, `CountExportAsync`, `StartExportReadAsync`, `ReadExportRowsAsync`, na base `AdoDatabaseConnection`). `BeginExportAsync` manda o prazo de trava e, no PostgreSQL, `DateStyle = 'ISO, YMD'`, `extra_float_digits = 3`, `bytea_output = 'hex'` e `BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ READ ONLY`: a contagem e a leitura veem o mesmo instante. A contagem roda num `SAVEPOINT prism_count` e, recusada, volta a ele: o total vem nulo e a leitura segue. A leitura é puxada em lotes (até 1.000 linhas ou 1 MiB de valores), cada lote um `Send` próprio da conexão, para a falha do disco nunca se misturar com a do banco; o último fecha o leitor com o `COMMIT`. Cada valor vem inteiro (`CellFormatter.ForExport`, sem o corte da grade): no PostgreSQL com `SequentialAccess` e `GetChars` em pedaços de 64 Ki caracteres, o lógico em `true`/`false` e o `bytea` em bytes; no Db2 e no Informix, pelo valor inteiro do driver. O valor acima de 64 MiB (o texto em bytes de UTF-8) ou a linha acima de 256 MiB param a leitura (`ExportOversize`) e o trabalho termina com `EXPORT_VALUE_TOO_LARGE`, com a coluna e a linha na mensagem. As colunas dos Registros e do resultado são conferidas pela posição e pelo nome (`EXPORT_COLUMNS_CHANGED`). O erro do banco vai como veio, com o SQLSTATE (decisão 4 da raiz): `DATABASE_CONNECTION_FAILED` ao conectar, `SQL_EXECUTION_FAILED` depois.
- **O arquivo temporário** (RN-EXPORT-014 e 018, `Transfers/Clients/TransferFileClient`, com o único `try` do disco). Pasta `<PRISM_DATA_DIR>/transfers`, modo 0700, criada (e esvaziada) na partida; cada arquivo, modo 0600, tem o nome **só do identificador** do trabalho: `<id>.part` enquanto é escrito e `<id>.ready` depois de completo, com `Flush(true)` antes de renomear. O BOM vem antes do texto; com o .zip, o arquivo vai dentro dele com o `entryName` que a tela mandou (e o BOM dentro da entrada). A falha, o cancelamento e o trabalho esquecido apagam o arquivo. O disco cheio (`ENOSPC` no Unix, 39 e 112 no Windows) tem a frase dele; as outras falhas, o motivo do sistema sem o caminho; as duas são `EXPORT_WRITE_FAILED`. A área de transferência é um arquivo também, com o teto de 10 MiB (`EXPORT_CLIPBOARD_TOO_LARGE`).
- **Os escritores** (`Transfers/Writers`). `ExportWriter` é a abstração: `Begin`, `Write(linha)`, `End`, `Flush` e as contagens (`ExportCounts`: valores cortados, caracteres tirados, linhas puladas, planilhas); `TextExportWriter` escreve UTF-8 sem BOM, com o par substituto solto em U+FFFD. Os escritores não guardam as linhas (o TXT guarda um lote, para a largura), não leem o banco e não abrem arquivo. O CSV e o TXT escrevem cada campo direto no `TextWriter`, em pedaços (`ExportText.WriteCsvField`, que o `CsvField` das fixtures usa; os espaços e os traços do TXT de um texto fixo), sem montar a linha num texto só: um valor de 60 MiB não é copiado de novo para ganhar as aspas, o apóstrofo e os separadores. `ExportText` (uma classe `partial`: `ExportText.cs`, `.Sql.cs`, `.Xml.cs` e `.Xlsx.cs`) tem as funções puras de cada regra, que as fixtures conferem. **As expressões regulares dela terminam em `\z`, e não em `$`**: o `$` do .NET aceita uma quebra de linha antes do fim, e o do JavaScript não (`-1` com a quebra no fim passava por número simples do CSV, sem a proteção). Os formatos:
  - CSV (RN-EXPORT-007), TXT (008), HTML e Markdown (009), JSON e Código fonte em PHP (010).
  - **SQL** (011, `SqlExportWriter`). Os literais são os da tela, `sqlLiteral` e `scriptLiteral` (`ExportText.SqlLiteral` e `ScriptLiteral`), com o mesmo texto: o filtro de uma linha recusa o caractere abaixo de U+0020 e o DEL (o C1 vai entre aspas, como na tela); o número sem aspas só numa coluna `number` e no `plainNumber` dela (`5.` e `.5` passam); no Informix o lógico `'t'`/`'f'` e a data e hora em `DATETIME (…) YEAR TO FRACTION(5)`, com as casas acima de cinco só se forem zeros. O binário (`BinaryLiteral`, só da API): `decode('…', 'hex')` no PostgreSQL; no Db2, pelo tipo da coluna (`GetDataTypeName`, o nome que o driver da IBM dá): `BX'…'`, a constante binária, no `BINARY` e no `VARBINARY`; `BLOB(X'…')` no `BLOB`; e `X'…'`, a hexadecimal, no texto binário (`CHAR () FOR BIT DATA`, `VARCHAR () FOR BIT DATA`) e no resto, em pedaços de 16.336 bytes unidos por `||` (em todos, porque as duas constantes têm esse teto qualquer que seja a coluna); no Informix, nenhum. **A hexadecimal é um texto** (`VARCHAR` na página de código do banco), e o Db2 não a atribui a uma coluna `BINARY` ou `VARBINARY` (SQL0408N, SQLSTATE 42821): só o texto `FOR BIT DATA` é compatível com o binário. Até a correção de 2026-10-17 o `VARBINARY` saía em `X'…'` e o arquivo não voltava ao Db2. Várias linhas por comando: `INSERT INTO "e"."t" ("a", "b") VALUES`, cada linha na seguinte com dois espaços de recuo, separadas por vírgula, até o `;` (também o comando que acabou com uma linha só, que o escritor em fluxo não sabe antes); com uma linha por comando, ou no Informix (sempre uma, mesmo que o pedido chegasse com mais), um `INSERT` numa linha só. A linha com um valor sem literal fecha o comando em andamento e vira `-- Linha N não exportada: …` com a frase do motivo (`ESqlSkipReason`: o binário no Informix; o controle que não é quebra, retorno de carro nem tabulação; senão, a data e hora do Informix, porque o lógico do Informix chega sempre `true`/`false`), `N` na ordem da origem a partir de 1, sem dado do banco. As colunas que o banco calcula não são do escritor: a tela as tira das colunas que manda (RN-EXPORT-011). **O retorno de carro no PostgreSQL** (`PostgreSqlEscapeLiteral`, emenda da RN-EXPORT-011 de 2026-10-17): o texto com `\r` vira um literal só, `E'…'`, com o retorno de carro como `\r`, a barra invertida e a aspa dobradas, e a quebra de linha e a tabulação cruas; continua sem tipo, e por isso volta para uma coluna `json`, `xml` ou de lista (a forma de antes, `' || CHR(13) || '`, é uma expressão `text`, que essas colunas não aceitam sem conversão). O Db2 e o Informix continuam com `CHR(13)`. O "Gerar SQL" da tela escreve o mesmo, a fixture `sql-literal` confere os dois lados, e `TransfersTests.Export_Sql_CarriageReturnInJsonAndList_RunsBackIntoACopyOfTheTable` prova a volta no PostgreSQL.
  - **XML e DbUnit** (012, `XmlExportWriter` e `DbUnitExportWriter`). Os nomes de elemento e de atributo passam pelo `XmlConvert.EncodeLocalName` (`ExportText.XmlName`): ele escapa também o `_x` que já parece um escape, com x minúsculo ou maiúsculo, e o caractere fora do plano básico vira `_xHHHHHHHH_`; o nome nunca perde nada, e a volta (`DecodeName`) é exata. No DbUnit, as maiúsculas (`ToUpperInvariant`, que deixa o `ß`) vêm antes, e os atributos passam pelo `UniqueKeys` do JSON depois do nome do XML (`id` e `ID` em maiúsculas viram `ID` e `ID_2`). O texto e o atributo são `XmlText` e `XmlAttribute` (os de `text-escape.ts`, com o `isXmlChar` tirando e contando o que o XML 1.0 não aceita). O `DOCTYPE` declara cada nome uma vez, também a coluna que se chama como a raiz ou `DATA_RECORD`; o modelo do `DATA_RECORD` é o do DBeaver, `(a?,b?)+`, com a coluna repetida repetida.
  - **XLSX** (013, `XlsxExportWriter`, que não é texto). Escreve direto no arquivo (o validator recusa BOM, .zip e área de transferência para ele) um `ZipArchive` em `Create`, com deflate: `_rels/.rels` e `xl/styles.xml` no `Begin`, a planilha como uma entrada aberta do começo ao fim dela (um `StreamWriter` sobre a entrada, que o `Flush` de cada lote leva ao arquivo, e é o tamanho do progresso), e `[Content_Types].xml`, `xl/workbook.xml` e `xl/_rels/workbook.xml.rels`, que dependem do número de planilhas, no `End`. Sem `dimension` (diria o tamanho antes de ele existir) e sem textos compartilhados (pediriam todos na memória): cada texto é `inlineStr`, com `xml:space="preserve"`. As regras são as do `to-xlsx.ts` (`SheetNameOf`, `SpreadsheetNumber`, `XlsxText`, `WithinCell`, `ColumnLetters`); o número sai como o `String` do JavaScript o escreve, montado dos dígitos significativos do texto (com até 15, são os do `double`), sem passar pelo `double.ToString`. Passando de 1.048.576 linhas com o cabeçalho, a planilha fecha e a seguinte abre com o cabeçalho, com o nome de `NextSheetName` (o da primeira cortado para o sufixo ` (2)` caber nos 31 caracteres, sem espaço no fim do corte, e cortado mais um caractere se repetir outro). `SheetRowLimit` (interno, `init`) é a costura do teste, que não escreve um milhão de linhas para ver a segunda planilha (um teste escreve, com uma coluna, em cerca de um segundo).
  - **Um formato novo**: uma classe `XxxExportWriter : ExportWriter` (ou `TextExportWriter`) em `Transfers/Writers`, que recebe o `ExportWriterContext` (colunas com `Type` e `Kind`, nome da origem, banco, opções) e o fluxo; uma linha no dicionário `Writers` de `ExportFormats`; as opções num record de `Transfers/Models/ExportOptions.cs` e um ramo no `ExportOptionsReader`; as funções puras numa parte de `ExportText`, com fixture em `src/test-fixtures/export/` (compartilhada quando a regra existe também na tela); e os testes. O que não é texto entra no `ExportFormats.IsText`.
- **O log** (RN-LOG-001). O começo e o fim de cada trabalho: o identificador, a conexão, o formato, a contagem pedida, as linhas, os bytes, a duração, o código do erro e o SQLSTATE. ## Importação de dados: a leitura do arquivo, a conversão e as prévias (seção 36: RN-IMPORT-003 a 011, 017 e 028; rotas `imports/read` e `imports/preview`)

A primeira parte da importação de dados: os leitores do arquivo em fluxo, a conversão dos valores, o mapeamento e as duas prévias do assistente. O carregador, o trabalho da importação (`POST api/user/transfers/imports`) e a cópia para outro banco (`copies`) estão na seção seguinte. O arquivo, quem escolhe e copia é o processo principal do Electron (`<fileId>.in` na pasta `transfers`, RN-IMPORT-018); a API só o lê pelo identificador, nunca por um caminho da tela.

- **O arquivo** (RN-IMPORT-008 e 017, `Transfers/Clients/ImportFileClient`, com o único `try` do disco dele). `Open(fileID)` abre `<transfers>/<fileID:D>.in` só para leitura, com `FileShare.ReadWrite | FileShare.Delete`: a prévia atrasada não impede a troca de nome do começo da importação nem a limpeza. Recusa (`ImportFileRefusal`) o que não está lá (também a pasta que sumiu: `Missing`, 404 `IMPORT_FILE_MISSING`), o que passa de 2 GiB (`TooLarge`, com o tamanho; 422 `IMPORT_FILE_TOO_LARGE`, "O arquivo tem 2,4 GB, e o Prism importa até 2 GB.", no mínimo "2,1 GB" para não escrever o próprio limite) e o que o sistema não deixa ler (o `HResult`, sem o caminho). `Check` é a mesma conferência sem deixar o arquivo aberto. A limpeza da partida (`TransferFileClient.Prepare`) já apaga o `.in` que sobrou. O `fileID` chega conferido pelo validator (36 caracteres em minúsculas com os hifens, `ImportRequestRules.IsFileID`) antes de virar nome.
- **Os leitores** (`Transfers/Readers`). `ImportReader` é a abstração, como o `ExportWriter`: `ImportReader.Open(format, options, stream, logger, token)` lê o que vem antes da primeira linha (a codificação, o separador, o cabeçalho, a forma do JSON e as chaves, as partes da pasta de trabalho) e devolve o leitor ou a `ImportReadFailure`; `Next(token)` entrega uma `ImportRecord` por vez (`Line`, um `ImportValue` por coluna do arquivo, `Problem` da linha e `Short`), ou nula no fim. O leitor é dono do fluxo e o fecha. `Info` (`ImportReadInfo`: codificação, separador, chave da lista, planilhas, a lida, as colunas), `Position` e `Size` (o progresso, RN-IMPORT-014), `SkippedLines` e `FormulasWithoutValue` (o aviso do fim, RN-IMPORT-020) são o que o trabalho vai ler dele. **O `Send` da base tem o único `try` da leitura**: as recusas do fundo do leitor saem como `ImportReadException` (interna, nunca sai do leitor) e voltam como `ImportReadFailure` (`Reason` em `encoding`, `format`, `sheet`, `limits` ou `system`, a frase da regra sem caminho, `Line` quando se sabe, e `ValueTooLarge`/`Column` no valor acima de 64 MiB ou na linha acima de 256 MiB); a `JsonException`, a `XmlException`, a `InvalidDataException` e a falha do disco também; o cancelamento sobe como veio. O log leva a classe e o `HResult`, nunca a mensagem. O `ImportValue` diz de onde o valor veio (`EImportValueSource`: `Plain` e `Quoted` no CSV; `Text`, o texto do JSON e do XLSX; `Canonical`, o número, o lógico e a data que já vêm na forma canônica; `Json`, o objeto ou a lista dentro de um valor; `Null`), porque o nulo, a proteção contra fórmula e os formatos dos valores dependem disso, e da coluna de destino: o leitor não converte nada.
  - **CSV e TSV** (RN-IMPORT-004, `CsvImportReader` sobre `TextSource`). `TextSource` decodifica em blocos de 64 KiB, sem montar o arquivo: o UTF-8 pelo `Utf8.ToUtf16` sem troca por U+FFFD, o UTF-16 à mão (o par substituto inteiro), o Windows-1252 pela tabela dos 32 de 0x80 a 0x9F e o ISO-8859-1 byte a byte; a sequência inválida devolve `Invalid` depois dos caracteres válidos antes dela, e o leitor recusa com a linha. A codificação automática (`TextSource.Detect`) percorre o arquivo inteiro uma vez (BOM; senão UTF-8 sem byte zero; senão Windows-1252) e volta ao começo; o separador automático conta os quatro fora das aspas em até 100 linhas ou 1 MiB e fica com o de contagem igual no maior número de linhas (o desempate é a ordem `;`, `,`, tabulação, `|`). O cabeçalho é o primeiro registro que não é vazio, com o apóstrofo da proteção tirado (quando a opção vale) e os nomes de `ImportText.ColumnNames`. A linha de cada registro é a física em que ele começa; a com menos valores é completada com `ImportValue.Null` e marcada `Short`; a com mais valores que não estão vazios é um `Problem`.
  - **JSON** (RN-IMPORT-005, `JsonImportReader`). Um `Utf8JsonReader` recriado a cada token sobre um espaço que cresce até o tamanho de um token (no máximo 6 × 64 MiB, o texto de 64 MiB todo em `\u00XX`), com o estado do anterior (que leva a linha e a posição das mensagens do .NET); o UTF-8 de cada bloco é conferido antes, para a recusa dizer a linha. O texto ou o número **sem escape** acima de 64 MiB é recusado no próprio token (`Oversized`), sem virar `string`; o com escape é desfeito e conferido depois. Os escapes são desfeitos à mão (o `GetString` recusaria o par substituto solto, que a conversão recusa no valor). Sem `keys`, o `Begin` percorre o arquivo todo para juntar as chaves e abre de novo; com elas (as que o `imports/read` devolveu), a posição de cada coluna é a da lista.
  - **XLSX** (RN-IMPORT-006, `XlsxImportReader`, `XlsxPackage`, `XlsxCells`). `XlsxPackage.Open` confere o `.zip` antes do `ZipArchive` (o `.xls` e a planilha com senha pelo `D0 CF 11 E0`; o fim do diretório central e o do ZIP64; até 10.000 entradas e 4 MiB de diretório, contados e com o nome repetido recusado por ele mesmo) e abre só as entradas usadas, cada uma num `CountingStream` com o teto dela (16 MiB, 64 MiB para os estilos, 1 GiB para os textos compartilhados e 16 GiB para a planilha; o declarado acima do teto recusa antes). O `XmlReader` é sem DTD e sem resolvedor, e toda leitura dele passa pelo `Next` e pelo `Skip` do leitor, que recusam o elemento que abriria o 65º nível (`MaxDepth`, contando o de fora como o primeiro) com a frase própria dele (`TooDeepMessage`, motivo `limits`, emenda da RN-IMPORT-008 de 2026-10-17): o `XmlReader` não tem teto e guarda um nó por nível aberto. **O texto de uma célula é lido em pedaços** (`ReadValueChunk`, no `ReadContent`) por um `XlsxTextDecoder` (em `ImportText.cs`), que desfaz o `_xHHHH_` no caminho e para ao passar do teto: o `v` e o texto em linha de uma célula param nos 64 MiB, e os textos compartilhados, no que falta dos 256 MiB (em UTF-16, e cada texto conta também `SharedStringOverhead`, 32 bytes, para os milhões de textos vazios pararem no teto: emenda da RN-IMPORT-008 de 2026-10-17). O `ImportText.XlsxText` é o decodificador com um pedaço só. O número é escrito pelo `double` no texto mais curto, a data pelo formato do estilo (`XlsxCells.KindOf`, os embutidos e o código próprio, com o tempo decorrido como número) e pelo sistema de datas (`XlsxCells.DateText`, o de 1900 com o 29/02/1900 recusado, e o de 1904), a célula `t="d"` pela ISO 8601 (`IsoDateText`); o erro do Excel e o valor fora das colunas são o `Problem` da linha, com a coluna quando é de uma célula. A fórmula sem resultado guardado chega vazia e conta em `FormulasWithoutValue`.
- **A conversão** (RN-IMPORT-010, `Transfers/Imports/ImportValues`, `ImportColumns`). `ImportColumns.Of(engine, column, baseType)` dá a classe (`EImportClass`) pelo tipo do catálogo de cada banco, o tipo do número, as casas da coluna no Db2 e no Informix (`Scale`, `Fraction`), o fuso (`TimeZone`) e se a coluna recebe valores (`Importable`/`Reason`: a calculada pelo banco e, no Db2 e no Informix, a classe "outra"); no PostgreSQL, a coluna de domínio usa o tipo-base, e o padrão `nextval(...)` vira `byDefault`, como no `edit-target`. `ImportValues.Convert(engine, column, value, rules, formats)` faz os cinco passos da regra, na ordem dela, e devolve `ImportConverted` (`Text`, o canônico como a prévia o mostra; `Parameter`, o `EditParameter` que a carga liga ao comando; `Unguarded`, que conta para o aviso do fim) ou a frase da recusa, com o valor entre aspas angulares (`ImportText.Quoted`, até 200 caracteres). `ImportValueRules` são as opções do CSV que valem na conversão (o texto do nulo, também entre aspas quando ele tem o separador ou a aspa, o vazio, as pontas, a proteção); o JSON e o XLSX usam `ImportValueRules.None`. O número, a data e o lógico `Canonical` não passam pelos formatos da etapa Arquivo. O passo 5 no Db2 e no Informix é o `EditValues.Convert` da edição, com a frase dela citando o valor como veio do arquivo; as casas a mais são recusadas antes, quando não são zero, como os campos depois do último do `DATETIME YEAR TO DAY`, `YEAR TO HOUR` e `YEAR TO MINUTE` do Informix (`EndsAt`, `WithinLastField`, emenda da RN-IMPORT-010 de 2026-10-17: os que são zero saem, e a prévia mostra o valor até o último campo), e o expoente que nem cabe num `long` (a expressão aceita quantos dígitos vierem) é "fora da faixa da coluna", sem lançar. As expressões que olham um valor inteiro não voltam em tempo quadrático no valor longo que não casa (o dígito obrigatório do `LooksLikeANumber` é conferido à frente, e não entre dois `[0-9.,]*`): um valor vai até 64 MiB. As funções puras (`CanonicalNumber`, `CanonicalTemporal`, `CanonicalBoolean`, `BinaryOf`, `ImportText.Unguard`) são as que as fixtures conferem.
- **O mapeamento** (RN-IMPORT-009, `ImportMapping`). `Suggest(columns, byName, table)`: com cabeçalho e no JSON, pelo nome (igual, letra por letra; senão `Normalize`, sem maiúsculas, acentos, espaço, hífen e sublinhado, e só quando uma coluna casa); sem cabeçalho, pela posição; nunca uma coluna desabilitada, e a primeira coluna do arquivo fica com a da tabela. `Refusal(mapping, fileColumns, table)` é a primeira recusa do mapeamento pedido, com o caminho do campo (`mapping[3].source` para a posição além das colunas do arquivo; `mapping[3].target` para a coluna que a tabela não tem, a calculada e a de tipo que não se importa).
- **A tabela de destino** (RN-IMPORT-009, 011 e 012, `IDatabaseConnection.DescribeImportTargetAsync` e `CheckImportCastsAsync`, na base `AdoDatabaseConnection`). A descrição é a consulta da edição (`EditRelationQuery`, com o nome entre aspas), as chaves que apontam para a tabela (`ReferencedBySql`, a mesma do catálogo) e, no PostgreSQL, o tipo-base das colunas de domínio (`DomainBaseTypesSql`, seguindo domínio de domínio); nula quando a tabela não existe (`ImportCatalog`). A conferência da conversão é só do PostgreSQL (`ImportCastSql` nula nos outros, e então nada vai ao banco): numa transação só de leitura desfeita no fim, um `SELECT CAST($n AS <tipo do catálogo>)` por linha (em partes de até 1.000), cada linha num ponto de salvamento, e, na recusada, um `SELECT` por célula para achar qual; a recusa é a resposta (`refusalIsTheAnswer`) e volta como texto por célula; a conexão que cai e o cancelamento são a falha. O PostgreSQL liga o valor da importação num parâmetro sem tipo e o binário em `bytea` (`BindImportParameter`); o Db2 e o Informix, como no "Salvar" (`BindEditParameter`).
- **As prévias** (`Transfers/Services/ImportPreviewService`, `Transfers/Imports/ImportPreviews`). `ReadAsync` lê até 20 linhas de dados num `Task.Run` (a leitura é síncrona e pode percorrer o arquivo inteiro) e monta a prévia do arquivo (`ImportPreviews.FileRows`: o nulo que o arquivo e as opções dizem, sem a conversão, e o resto como veio). `PreviewAsync` lê o arquivo, abre uma conexão à parte com o prazo de trava, descreve a tabela (a que não existe e a que não é tabela, nos termos da edição: a visão, a materializada, a estrangeira, e "não é uma tabela comum"), usa o mapeamento pedido (conferido) ou o automático, converte (`ConvertedRows`), pede ao banco a conferência das células que o Prism converteu e junta as recusas dele (`WithDatabaseProblems`). As duas respostas levam as células cortadas nos 1.000 caracteres (o binário em `0x` e 32 bytes) e só as primeiras colunas que cabem em 8 MiB de células (`Fit`, `shownColumns`); os nomes das colunas vão todos.
- **As rotas** (`UserTransfersController`, corpo até 8 MiB). `POST api/user/transfers/imports/read` (`ReadImportFile`) e `POST api/user/transfers/imports/preview` (`PreviewImport`), com as respostas e as recusas da seção 6 e das notas da seção 36 (DTOs em `Transfers/Models/Dtos/ImportDtos.cs`, a tradução das enumerações em `ImportMappings`, os erros em `ImportErrors`). Os validators recusam a forma do pedido toda de uma vez, com `IMPORT_OPTIONS_INVALID` no campo e pelo caminho em camelCase (`ImportRequestRules`: `FileRefusals`, `ValuesRefusals`, `TargetRefusals`, `MappingRefusals`); as opções do leitor são lidas à mão do `JsonElement` (`ImportReaderOptionsReader`, como o `ExportOptionsReader`), com o padrão do Prism no que falta e o tipo errado recusado no campo (`reader.nullText`, `reader.keys`). O handler da prévia segue a ordem do começo da importação (RN-IMPORT-014): o arquivo, a conexão, o banco de dados pedido (a regra da exportação), o usuário e a senha (no campo, com "importe de novo"), o driver e o somente leitura pela proteção do cofre agora, e só então o banco. A falha do banco vai como veio (`DatabaseSessionErrors.From`); `IMPORT_FILE_UNREADABLE` leva `reason` e `line`. O valor acima de 64 MiB, nas prévias, é `IMPORT_FILE_UNREADABLE` com o motivo `limits`.
- **O log** (RN-LOG-001). As prévias registram o formato e as contagens; nunca o nome do arquivo, um caminho, o nome da tabela ou das colunas, os valores nem a mensagem do banco. Os commands, os DTOs, as opções (o texto do nulo é dado da pessoa), os registros, os valores e as falhas sobrescrevem o `ToString()`.
- **As fixtures** (RN-IMPORT-028, `src/test-fixtures/export/`, escritas à mão, nunca regeradas). Compartilhadas com a tela: `import-unguard` (a volta da proteção: a tela confere que o `csvFieldOf` escreve `field` de `value`; a API lê `field` do CSV e confere que `ImportText.Unguard` devolve `back`; o caso `lossy` é o apóstrofo de verdade). Só da API, prontas para quando a tela tiver a regra: `import-csv-field` (as aspas dobradas, a aspa no meio, o texto depois da aspa que fecha, as três quebras de linha), `import-xlsx-text` (o `_xHHHH_`; a API também lê de volta o `xlsx-text` da exportação), `import-value-order` (o nulo, a proteção e as pontas, os caracteres que nenhum banco grava, o lógico e o binário), `import-numbers` e `import-dates` (cada formato, com o texto canônico ou a recusa). O `ImportFixturesTests` as lê todas.
- **Testes**. Unidade (`Transfers/Imports`): `CsvImportReaderTests`, `JsonImportReaderTests`, `XlsxImportReaderTests` (pastas de trabalho montadas na memória; o texto acima de 64 MiB e o escape na divisa dos pedaços), `XlsxCellsTests`, `ImportValuesTests`, `ImportMappingTests`, `ImportFixturesTests` (também o `XlsxTextDecoder` cortado em qualquer ponto), `ImportPreviewsTests`, `ImportFileClientTests` (numa pasta temporária de verdade: renomear e apagar com o arquivo aberto, o arquivo esparso acima de 2 GiB), `ImportPreviewServiceTests` (o arquivo de verdade e o banco do Moq), `ImportRequestTests` (os validators e o leitor das opções) e `PreviewImportHandlerTests`. Integração (Docker): `Api/ImportsTests` (as duas rotas contra o PostgreSQL com a carga `loja`: a codificação e o separador automáticos, o JSON e o XLSX, as recusas com os códigos, a prévia convertida com a recusa do banco e a do Prism, a visão, a tabela que não existe, o mapeamento no campo e a conexão somente leitura). São eles que provam, contra o contêiner, a descrição da tabela (`DescribeImportTargetAsync`, com a consulta do tipo-base dos domínios) e a conferência pelo `CAST` (o parâmetro sem tipo do Npgsql inferido pelo `CAST`, o ponto de salvamento na transação só de leitura); o `ImportPreviewServiceTests` usa uma conexão do Moq. No Db2 e no Informix não há teste de integração das prévias.

## Importação e cópia: o carregador, o trabalho e as rotas (seção 36: RN-IMPORT-012 a 016 e 022 a 027; rotas `imports`, `copies/preview` e `copies`)

A importação (o arquivo para uma tabela) e a cópia para outro banco (a origem da exportação para a tabela de outra conexão) são trabalhos do mesmo registro da exportação, com `kind` `import` e `copy`, e gravam pelo mesmo carregador. Nada vai a um banco antes do 202.

- **O carregador na conexão** (RN-IMPORT-015 e 016, `IDatabaseConnection`: `BeginLoadAsync`, `LoadRowsPerCommand`, `BeginLoadTransactionAsync`, `EmptyTableAsync`, `InsertRowsAsync`, `CommitLoadAsync`, na base `AdoDatabaseConnection`). `BeginLoadAsync` manda só o prazo de trava (`LockTimeoutSql`): nada sobre o modo só de leitura, e a recusa 25006 do banco configurado assim é a resposta. A transação é a do driver, no mesmo campo do "Salvar" (`_editTransaction`), e os comandos da carga rodam com `continuesTheCursor: true`, para o `RunAsync` não a desfazer entre um comando e outro; a recusa do banco é a resposta (o `Send` com `refusalIsTheAnswer`), e só então a transação é desfeita, pelo `DisposeCursorAsync`. O `INSERT` leva só as colunas mapeadas, com os nomes entre aspas (`LoadTarget`): no PostgreSQL, um comando de uma linha (`$1, $2`) por linha, num `DbBatch` de até 500 (`LoadsInBatches`), com o valor sem tipo e o binário em `bytea` (`BindImportParameter`), e a linha recusada pelo `DbException.BatchCommand` (o índice vira `DatabaseFailure.Change`; a coluna do erro, `ColumnName`), que o Npgsql só preenche com `IncludeFailedBatchedCommand` ligado na string de conexão (`PostgresConnection.CreateConnection`): sem ele o `BatchCommand` vem nulo, e a recusa perdia a linha; no Db2, `INSERT … VALUES (?, ?), (?, ?)` de até 500 linhas e 10.000 parâmetros (`RowsPerLoadCommand`), preparado uma vez e reaproveitado enquanto o texto é o mesmo, e, na recusa das classes 22 e 23, a volta linha por linha na mesma transação até a recusada (`Change` é a posição dela no comando); no Informix, uma linha por comando, e o texto de mais de 16.350 caracteres vai como `LONG VARCHAR` até os 32.767 bytes dele (`InformixConnection`): o driver da IBM o mandaria como `CLOB`, que o Informix não converte em `LVARCHAR`. O comando de uma linha só (no Informix, todos; no Db2, o último antes de uma confirmação ou o fechado pelos 16 MiB) aponta a linha dele (`Change` 0) em toda falha, também na conexão que cai: é a linha que a RN-IMPORT-016 diz "do comando". `CommitLoadAsync` tira a transação do campo antes do `COMMIT`, conta como executada desde o começo e não recebe o token: o cancelamento não a interrompe. O `COPY` e a cópia em massa da IBM ficam de fora, pela própria regra.
- **O carregador do trabalho** (`Transfers/Services/TableLoader`, o mesmo da importação e da cópia). Recebe uma linha convertida por vez (`AddAsync(row, line)`), junta até o tamanho do comando da conexão, fecha antes quando os valores passam de 16 MiB (`MaxCommandBytes`) e nunca atravessa uma confirmação: com "A cada N linhas", a linha que completa N manda o comando e confirma, e a transação seguinte abre na hora; com `commitEvery` nulo, uma só, confirmada no `FinishAsync` (fase `committing`). No banco sem log (`OneAtATime` da descrição), nenhuma transação, e cada comando conta como confirmado. Antes de cada comando confere o cancelamento e o cofre naquele instante (`TargetStop`, de `TransferConnections.StopNow`, RN-PROT-006), e para como a sessão recusaria o comando: a conexão que passou a ser somente leitura termina `canceled` com `reason: readOnly`; a excluída antes de o cancelamento dela chegar, com `connectionDeleted`; e o cofre que não responde, sem ler a proteção, como o cancelamento. Na falha, a linha é a do arquivo (ou o número na leitura da origem), pela posição que a conexão diz; sem ela, as linhas do comando contam em `rows`, para a tela compor o intervalo. `uncertain` é verdadeiro na confirmação que cai com a conexão (ou volta sem SQLSTATE) e, sem log, no comando ou no esvaziamento que cai. Enquanto a confirmação roda (`CommitGuard`), o cancelamento não chama o `Cancel` da conexão.
- **A importação** (`ImportRun`). Conecta, manda o prazo de trava, descreve a tabela (`LoadSteps.DescribeAsync`: `IMPORT_TABLE_NOT_FOUND`, `IMPORT_TARGET_NOT_TABLE`, e `IMPORT_TABLE_CHANGED` para a coluna mapeada que sumiu, passou a ser calculada ou não se importa), abre o arquivo do trabalho (`<id>.in`) pelo leitor das prévias e recusa a posição do mapeamento além das colunas do arquivo (`IMPORT_MAPPING_INVALID`), antes de gravar. Com `check`, lê o arquivo inteiro com as conversões dos tipos dessa leitura, sem transação (fase `checking`), e o abre de novo; `bytes` fica com o que a conferência leu até a fase `loading`, que o zera na mesma mudança (`TransferProgress.Phase(fase, bytes)`). Então a primeira transação, a tabela descrita de novo (a coluna que converte de outro jeito, `ImportTargets.ConvertsTheSame`, é `IMPORT_TABLE_CHANGED`), o esvaziamento (fase `emptying`) e a carga (fase `loading`). O problema da linha e a recusa da conversão são `IMPORT_VALUE_INVALID`, com a linha e a coluna do arquivo; o valor acima do teto, `IMPORT_VALUE_TOO_LARGE`; o resto da leitura, `IMPORT_FILE_UNREADABLE`; o leitor interrompido pelo cancelamento (`ImportReadFailure.Canceled`) é o cancelamento. No item, `bytes` é o lido do arquivo, `size` o tamanho dele, `rows` as linhas gravadas e `committed` as confirmadas.
- **A cópia** (`CopyRun`). Duas conexões à parte, mesmo com a mesma conexão do cofre: a de leitura nas regras da exportação (`BeginExportAsync`, a contagem, `StartExportReadAsync`, `ReadExportRowsAsync`, as colunas conferidas pela posição e pelo nome nos Registros e no resultado, os tetos de 64 MiB e 256 MiB) e a de gravação nas do carregador. A contagem é obrigatória (`ForcedCount`) quando a origem é Db2 ou Informix no mesmo servidor, porta e banco do destino (`TablePlaces.SameServer`): `CountExportAsync(sql, required: true)` não engole a recusa nem o "não contável", e a leitura que passa de `total + max(total / 10, 1.000)` linhas para com `IMPORT_SOURCE_GROWING`. Cada valor passa por `ImportValues.ConvertCopied` (RN-IMPORT-024 e 026): o nulo é o da origem; o binário vai só para coluna binária, em bytes; no PostgreSQL de destino o texto vai como veio, com as recusas do que o banco faria em silêncio (a hora numa coluna só de data, o fuso de um texto numa coluna sem fuso) e o fuso do `timestamptz`/`timetz` do PostgreSQL de origem tirado numa coluna sem fuso; no Db2 e no Informix de destino, o `Convert` da importação com `EImportValueSource.Copied` (sem o texto do nulo e sem as pontas, nos formatos canônicos). A leitura da cópia pede o texto canônico dela (`ExportReadPlan.Copy`, `CellFormatter.ForCopy`): a data e hora do driver da IBM vai com as 7 casas de fração (`aaaa-mm-dd hh:mm:ss.fffffff`, RN-IMPORT-026), e não com as 6 da grade e dos arquivos. A falha da leitura é `side: source`; a da gravação e a recusa de um valor, `target`. No item da cópia, `bytes` e `size` vêm nulos e `total` é a contagem.
- **O registro** (`TransferService.StartImport` e `StartCopy`). Sob a trava: o cofre que mudou, o limite (3 em andamento, das três espécies juntas) e a tabela ocupada por outra importação ou cópia em andamento, pela regra da própria origem (`TablePlaces.SameTable`: o servidor sem diferenciar maiúsculas, a porta, o banco, o esquema e o nome letra por letra; 409 `IMPORT_TARGET_BUSY`, com "importação" ou "cópia" pela que ocupa). A importação toma o arquivo ali mesmo (`ImportFileClient.Take`, `<fileId>.in` → `<id>.in`; o que sumiu é 404 `IMPORT_FILE_MISSING`), e o `.in` sai no fim do trabalho e na limpeza (`TransferFileClient.Delete`). A falta de progresso termina com `IMPORT_STALLED`; ela e o `DELETE` que desiste de esperar, no meio de uma confirmação (ou de um comando sem log), deixam `uncertain` (`Transfer.InDoubt`). O `DELETE` do que terminou `done` apesar do cancelamento só esquece na hora a exportação: a importação e a cópia ficam, para a tela ler o fim. Excluir uma conexão cancela os trabalhos em que ela é a origem ou o destino. No fim, o `error` ganha `committed`, `uncertain` e `side` (`target` quando o passo não disse). A importação e a cópia não lançam (o que falha é o fim delas), e o `SafelyAsync` é a rede para o defeito que lançar mesmo assim: o trabalho termina `failed` com `INTERNAL_SERVER_ERROR` (o código das exceções não previstas da seção 6) e uma frase fixa, o arquivo sai e a tabela e a vaga ficam livres; o log leva a classe e a pilha, nunca a mensagem. O log (RN-LOG-001) leva o identificador, as conexões, o formato, as contagens, a duração e o código com o SQLSTATE; nunca nomes, valores, o comando, o nome do arquivo ou a mensagem do banco.
- **As rotas** (`UserTransfersController`, corpo até 8 MiB). `POST api/user/transfers/imports` (`StartImport`, 202 `{ id }`): o validator usa os `ImportRequestRules` da prévia com o mapeamento obrigatório, a carga (`load`, lida à mão por `ImportRequestRules.Load`, com o padrão do Prism no que não vem: `empty` falso, `commitEvery` 10.000, `check` verdadeiro; `commitEvery` nulo é uma transação só, e o inteiro vai de 1 a 1.000.000) e o `windowID` acima de zero, tudo com `IMPORT_OPTIONS_INVALID` no campo; o handler segue a ordem da RN-IMPORT-014 (o arquivo, a conexão, o banco de dados, o usuário e a senha no campo com "importe de novo", o driver e o somente leitura do cofre, e então o registro), e relê a conexão depois de o trabalho entrar, como a exportação. `POST api/user/transfers/copies/preview` (`PreviewCopy`, 200 `{ table, mapping }`): a origem nas formas da exportação, as colunas pedidas, a tabela de destino e o mapeamento, opcional (ausente, o sugerido pelo nome); só a tabela de destino é lida, numa conexão à parte (`ImportPreviewService.PreviewCopyAsync`). `POST api/user/transfers/copies` (`StartCopy`, 202 `{ id }`): o `load` sem `check` (`load.check` é recusado), as regras da origem da exportação (`ExportRequestRules.SourceRefusals` e `ColumnsRefusals`), a posição do mapeamento além das colunas pedidas (`IMPORT_MAPPING_INVALID` em `mapping[i].source`, antes das conexões), a origem e o destino (`CopyChecks`: a conexão, o banco de dados, as credenciais no campo `source.userName` ou `target.password` com "copie de novo", o driver, o somente leitura do destino) e a tabela de destino que é a própria origem (422 `IMPORT_TARGET_IS_SOURCE`, também na prévia). Nas três rotas, a conexão à parte do trabalho é a gravada no cofre com o banco de dados pedido (`TransferConnections.SettingsOf`).
- **O item** (`TransferDto`, a forma única dos três trabalhos). `kind` é `export`, `import` ou `copy`; `connectionID` é a origem (na importação, o destino) e `targetConnectionID` o destino; `phase` ganha `checking`, `emptying`, `loading` e `committing`; `committed` e `uncertain` valem na importação e na cópia; `reason` ganha `readOnly`. `summary` tem sempre as 12 chaves, `{ rows, bytes, sheets, cutValues, removedCharacters, skippedRows, committed, emptied, shortRows, skippedLines, unguarded, formulasWithoutValue }`, e `error` as 8, `{ code, message, sqlState, line, column, side, committed, uncertain }`, nulas na exportação. A mensagem não leva a linha: a tela compõe "na linha N" e "nas linhas X a Y" de `line`, `committed` e `rows`.
- **Testes**. Unidade: `Databases/AdoDatabaseConnectionLoadTests` (a base sobre um driver de mentira que tem lote: o `INSERT` de várias linhas, o comando reaproveitado, a volta linha por linha das classes 22 e 23, o `BatchCommand` do lote, o `DELETE`, a confirmação que o cancelamento não interrompe e a recusada sem `ROLLBACK` depois), `Transfers/TransferServiceLoadTests` (os dois trabalhos com uma conexão de mentira e o `FakeTimeProvider`: a carga a cada N e numa transação, a conferência, a linha e a coluna, o somente leitura no meio, o cancelamento e a queda na confirmação, a tabela ocupada, o catálogo que mudou, o banco sem log, a origem que cresce, a conexão excluída), `Transfers/Imports/StartImportHandlerTests`, `CopyHandlersTests`, `LoadRequestTests`, `ImportValuesCopiedTests`, e os casos novos de `TransferHandlersTests` e de `ImportFileClientTests` (`Take`). Integração (Docker): `Api/ImportJobsTests` e `Api/CopiesTests` (as rotas até o fim contra o PostgreSQL, conferindo o que ficou na tabela) e `Infrastructure/Databases/PostgresLoadTests`, `Db2LoadTests` e `InformixLoadTests`, sobre `DatabaseLoadContractTests` (o comando de várias linhas com parâmetros, o texto longo e o binário, a linha recusada, o esvaziamento desfeito; no Informix, também o banco sem log e o texto longo no `TEXT` e no `CLOB`, dos dois lados dos 32.767 bytes do `LONG VARCHAR`). Só eles provam o que os drivers de mentira não provam: o `BatchCommand` do erro no lote do Npgsql (a primeira execução mostrou que ele vem nulo sem o `IncludeFailedBatchedCommand`), o `INSERT` de várias linhas do Db2 com `CLOB` e `BLOB` em parâmetros, e o `BYTE` e o `LVARCHAR` longo do Informix por parâmetro (a primeira execução mostrou o "No cast from text to lvarchar" do texto de 20.000 caracteres).

## Testes

- `Prism.UnitTesting` (xUnit) e `Prism.IntegrationTesting` (NUnit) usam fakers e pacotes de `Prism.TestingCore`, que não tem testes. Não há `Moq.Dapper` porque não há Dapper.
- `Prism.TestingCore` tem `Extensions/ObjectsExtensions.cs` (`JsonEquals`), `Extensions/DatabaseConnectionExtensions.cs` e `Fakers/Vault/VaultFakers.cs`. Ele enxerga os internos de `Prism.Infrastructure` (`InternalsVisibleTo`) por um caso só: `ExecutePastTheTransactionControlRefusalAsync`, que leva o teste de integração da rede de segurança ao caminho depois da recusa de controle de transação; `Prism.IntegrationTesting` continua sem enxergar nada interno. Teste de unidade que deriva chave usa `VaultFakers.CreateOptions(pasta)`, com Argon2id de 8 MiB e uma passada; com os parâmetros padrão (o que o `ApiHost` usa) cada entrada custa cerca de 0,3 s, e um teste de integração pode reduzi-los com `services.Configure<VaultOptions>(...)` no `configure` do `ApiHost.StartAsync`.
- `ApiHost` (`tests/Prism.IntegrationTesting/Api/`) sobe a API real em porta efêmera, com token e pasta de dados temporária próprios, e com o Argon2id pequeno (8 MiB, uma passada) por padrão; `CreateUserAsync` cria o usuário pela rota de verdade e deixa o cofre dele aberto. `ProcessHostingTests` inicia a `Prism.Api.dll` como processo, como o Electron faz, pelo `Api/Support/ApiProcess`.

O Informix não tem comando que grave e devolva linhas: o `WriteReturningRows` dele é um `EXECUTE FUNCTION` da carga.

O contador de execuções da `CountedQuery` é lido na mesma conexão; no PostgreSQL é uma sequência temporária, a única que a transação só de leitura deixa avançar.

## O que não existe aqui, e por quê

- **`AddCore` e `IDatabaseFactory`.** Não há banco do produto: os dados são o cofre (decisão 2 da raiz). O `Prism.Core` é só `ApiErrorDto`, `ApiSuccessDto`, `ResultExtensions`, `StringExtensions`, `DomainDto` e o mediador.
- **Políticas de autorização, papéis, `ICurrentUser`.** Não há Keycloak nem JWT (decisão 1). A autenticação é o token de lançamento; a liberação dos dados é o cofre aberto (RN-API-005: rotas `api/user/...` respondem 401 `VAULT_LOCKED` sem ele), e as rotas `api/public/...` exigem só o token.
- **Rate limiting, Turnstile, cabeçalhos de proxy, HTTPS e background jobs.** A API só existe em loopback para o próprio app (decisão 7). Não há biblioteca de jobs: os serviços em segundo plano são o `ParentProcessWatcher` e o registro das transferências (`TransferService`), cujos trabalhos vivem só na memória desta execução, com as tarefas e o temporizador dele (o que uma queda deixa no disco, a partida seguinte apaga).
- **Dapper.** As consultas de catálogo passam pelo mesmo caminho de leitura das consultas do usuário, nos drivers.
- **`try`/`catch` no caminho de uma requisição.** Falha prevista é `Result`; só o `Send` de um client de integração captura. Estão fora dessa regra o `Program.cs` (inicialização), o `ParentProcessWatcher` (o pai já pode não existir) e o `RequestMediator`, que registra a exceção do handler e a relança com `throw;` (RN-LOG-001: o nome do command e a exceção, nunca o command).
